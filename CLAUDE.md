# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm test                        # run all tests (Node test runner, no build needed)
node --test test/foo.test.mjs   # run a single test file
npm run package                 # build versioned zip for distribution (browsa-vX.Y.Z.zip)
npm run build                   # bundle vendor libs via esbuild (only needed after changing build/build.mjs)
bash check-compat.sh            # static compatibility check
```

When bumping a version, update both `manifest.json` and `package.json`.

## Architecture

**Chrome MV3 extension** — side panel chat UI. No build step is required for the JS source; all extension files are loaded directly by Chrome.

### Message flow

```
page content scripts  →  chrome.runtime.sendMessage  →  background.js (SW)
                                                              ↓
sidepanel.js  ←  navPort (browsa-nav long-lived port)  ←  background.js
sidepanel.js  ←  streamPort (browsa-chat, opened fresh per turn)  ←  background.js
sidepanel.js  ←  subChatPort (browsa-subchat, opened fresh per send)  ←  background.js
```

- **`background.js`** is the service worker and single message router. All `chrome.runtime.onMessage` handling flows through one `handle()` switch — still the single exported dispatcher (tests import it), but the bodies of the biggest cases live elsewhere: `lib/handlers/chat-handler.js` (`handleChat`, the `CHAT` case), `lib/handlers/subchat-handler.js` (`handleSubchat`/`handleSubchatAbort`, the `SUBCHAT`/`SUBCHAT_ABORT` cases), and `lib/handlers/session-handler.js` (`handleSession`, dispatching all 7 session-drawer cases — `SAVE_SESSION`/`GET_SESSIONS`/`LOAD_SESSION`/`DELETE_SESSION`/`RENAME_SESSION`/`CLEAR_ALL_SESSIONS`/`GET_SESSION_FULL` — internally, since each is a thin pass-through to `lib/storage.js` with no other logic). `lib/handlers/provider-resolver.js` (`resolveProvider`/`resolveInferenceParams`) holds the shared active-provider-resolution + inference-params-parsing logic that `chat-handler.js` and `subchat-handler.js` both import instead of each duplicating those two guards inline. The shared stream/approval state Maps (`streamPorts`, `streamState`, `chatControllers`, `idleTimerResetters`, `activeRunIds`, `pendingApprovals`, `pendingClarifications`, `subChatControllers`, `subChatPorts`) plus `pushChunk`/`pushSubChatChunk`/`initStreamState`/`appendToStreamState`/`clearStreamState` live in `lib/state.js` — `background.js` imports and re-exports them, so `import { streamPorts, ... } from '../background.js'` in tests still resolves to the same Map instances. The 9 site content-script push messages (`YOUTUBE_DATA`/`JUEJIN_ARTICLE`/etc.) route through one generic case driven by `SITE_MESSAGE_MAP` (a `{msgType: {site, field}}` table next to `SITE_CACHES`) instead of 9 separate case blocks. `ATTACH_PAGE` and all other small cases stay inline in `background.js` (entangled with the `SITE_CACHES` subsystem defined later in the same file).
- **`sidepanel.js`** connects `browsa-nav` once on init (receives NAVIGATED, XHS notes, SELECTION_ACTION). `browsa-chat` (main chat streaming) and `browsa-subchat` (detail-thread streaming, see below) are each opened **fresh per turn/send** instead — see "Port lifecycle" below for why that distinction matters. `sidepanel.js` itself is now the UI orchestrator (init/onSend/history/approval-clarify cards/screenshot crop) — the Markdown rendering pipeline, sessions drawer, message search, multiselect, and detail-thread are all split into `lib/sidepanel/*.js` modules (see "sidepanel.js module split" below) and imported back in.
- **`lib/storage.js`** wraps `chrome.storage.local`. History is a **global flat array** (not per-tab).
- **Response envelope**: most background responses use `{ ok: true, data: result }` on success / `{ ok: false, error, code, hint }` on thrown error — unwrap with `res.data?.ok` ONLY for handlers that themselves return an inner `{ok, ...}` object (e.g. `APPROVAL_RESPOND`/`CLARIFY_RESPOND`, which catch relay failures internally). Handlers that just `throw` on failure and return plain data otherwise (e.g. `CHAT`, `SUBCHAT`) are correctly checked via the outer `res.ok` directly — check which pattern a given case actually uses before assuming.
- **`lib/constants.js`** holds shared constants (e.g. `PAGE_CONTEXT_PREFIX`) imported by background, sidepanel, storage, and page-extractor. Content scripts run in MAIN world and cannot import ES modules, so they do not use this file.

### `sidepanel.js` module split (`lib/sidepanel/`)

Twelve modules, each imported by `sidepanel.js` — none of them import `sidepanel.js` back (avoids ES module cycles; modules that need `sidepanel.js`-owned mutable state get it via an `initX(deps)` call from `init()` instead):

- `render.js` — the Markdown/Mermaid/ECharts/Markmap/KaTeX pipeline: `renderStreamingSafe`/`renderSafe` (marked + DOMPurify), `makeStreamRenderer`, `addCodeCopyButtons`/`highlightDiffBlocks`, `renderMermaid`/`renderEcharts`/`renderMarkmap`. `renderMarkmap` follows the exact same "model emits a fenced code block, `render.js` detects the language and swaps it for a live render" pattern as `renderMermaid`/`renderEcharts` — ported from auditing BiliNote's markmap-based mind-map notes, deliberately with **no new UI button**: `CAPABILITY_HINTS` (background.js) just teaches the model to emit a ` ```markmap ` block (a plain Markdown heading/list outline, not Mermaid syntax or JSON) when the user asks for a mind map, and it renders automatically. Unlike mermaid/echarts, `renderMarkmap` must `pre.replaceWith(wrapper)` *before* calling `Markmap.create()` (markmap-view needs a DOM-attached `<svg>` to measure text extents during layout) — so its catch block replaces `wrapper`, not the by-then-detached `pre`, on failure. `markmap-view` wires its own zoom/pan via d3-zoom internally (transform applied to its inner `<g>`), so there's no custom wheel-zoom/drag-pan code the way mermaid has — but it still gets a hover-revealed toolbar (`_markmapToolbar`, reusing the `.mermaid-toolbar`/`.mermaid-btn` CSS classes like `_echartsToolbar` does) for 放大/缩小/重置/复制代码/导出SVG. Zoom/reset buttons drive markmap-view's *own* `.rescale(scale)`/`.fit()` API — reusing mermaid's viewBox-mutation zoom functions here would fight markmap-view's own transform instead of cooperating with it. **`mm.rescale(t)` is a RELATIVE multiplier on the current transform, not an absolute target** — a real bug found via live testing: an earlier version passed `rescale(currentScale * factor)`, which then got multiplied by the current scale *again* inside `rescale()` itself, squaring it; since the diagram starts auto-fit below 1×, squaring a sub-1 number makes it smaller, so both the `+` and `−` buttons visibly shrank the diagram. Fixed via `_markmapZoomBy(mm, svgEl, factor)`, which computes the desired absolute target (clamped to `[0.2, 4]`) and passes `target / current` — the relative factor `rescale()` actually needs to land exactly on it. `renderMarkmap` must capture `Markmap.create()`'s return value (`const mm = ...`) rather than discarding it, since the toolbar needs `mm` to call `.fit()`/`.rescale()`. The relative +/- zoom step reads the live scale off `svgEl.__zoom?.k` (the field d3-zoom itself stashes on the DOM node, same one `d3.zoomTransform(node)` reads internally) rather than importing d3 separately for one lookup. Export reuses `_mermaidExportSvg` unmodified (it only depends on `wrapper.querySelector('svg')` + `XMLSerializer`, no mermaid-specific DOM assumptions) — passed the markmap `wrapper` div. A `ResizeObserver` on `wrapper` calls `mm.fit()` on size changes, mirroring `renderEcharts`'s `chart.resize()` pattern. **Vendor loading**: `getMarkmapLib()`/`getMarkmapView()` (1.7MB + 80KB, independent of each other) are loaded via `Promise.all(...)` inside `renderMarkmap` rather than sequential `await`s, so the smaller bundle's fetch/parse doesn't wait behind the larger one. `preloadChartVendors()` (exported) speculatively kicks off `getMermaid()`/`getEcharts()`/`getMarkmapLib()`/`getMarkmapView()` — fire-and-forget, never awaited — from `sidepanel.js`'s `onSend()` the moment a turn starts, so by the time the reply's DONE chunk arrives and a diagram needs rendering, the vendor bundle is very likely already sitting in the module cache instead of costing a multi-MB cold `import()` right when the user is watching. Every `getXxx()` is independently idempotent (checks its own module-level cache before importing), so calling `preloadChartVendors()` on every single turn — including turns with no diagram at all — is a cheap no-op after the very first call. **`renderSafe` is `async`** (it awaits the KaTeX worker/threshold decision below) — every caller must `await` it; `renderStreamingSafe` (the per-tick streaming path) stays synchronous since it skips KaTeX entirely. `makeStreamRenderer`'s returned closure is also `async` for the same reason, and exposes a `.destroy()` method that must be called before reassigning it mid-stream (RETRY, tab-switch DOM-identity change) to stop an abandoned reveal-pacer. Three sanitization gotchas: `renderMermaid()` pipes Mermaid's SVG output through the vendored `stream-markdown-parser` package's `sanitizeMermaidSvg()` before `innerHTML` — `securityLevel:'loose'` (needed for `$$...$$` KaTeX math in node labels) also permits `foreignObject` HTML/click-binding content otherwise. DOMPurify's `ALLOWED_URI_REGEXP` does NOT govern `data:` URIs on `<img>`/`video`/`audio` tags (they're in DOMPurify's own `DATA_URI_TAGS` allow-list, validated by an internal check that bypasses the custom regex entirely — confirmed empirically) — blocking `data:image/svg+xml` (which can carry its own `<script>`) instead uses a `DOMPurify.addHook('uponSanitizeAttribute', ...)` registered once at module load. **Never pass `ALLOWED_URI_REGEXP` directly as a `sanitize()` option** — a real bug, found via a live user report (a numbered list's second block rendered as "1." instead of continuing at "2."): DOMPurify applies that regexp to the *value* of every allowed attribute not on its own internal "safe" list (`id`/`class`/`style`/`title`/`alt`/... — see `ADD_URI_SAFE_ATTR` in DOMPurify's source), not just `href`/`src`. A strict allowlist regexp (`https?:|mailto:|tel:|data:image/|#`) then silently strips anything whose value doesn't look like one of those schemes — `<ol start="N">` (a bare number), `<td colspan="N">`, `<input type="checkbox">`. Fixed by moving the check into the `uponSanitizeAttribute` hook, scoped to an explicit `URI_ATTRS` set (`href`/`src`/`action`/`formaction`/`poster`/`cite`/`background`/`xlink:href`) — everything else is left to DOMPurify's own defaults.
- `reveal-pacer.js` — `createRevealPacer(onReveal)`, a thin wrapper around the vendored `markstream-core` package's `createSmoothMarkdownStream`. Paces how fast enqueued deltas become visible (self-terminating internal `requestAnimationFrame` loop, confirmed via source read — no leak risk even if `destroy()` is skipped, though calling it is still correct hygiene). Used by both `render.js`'s `makeStreamRenderer` and `detail-thread.js`'s own inline accumulate loop.
- `katex-threshold.js` / `katex-worker-client.js` / `katex.worker.js` — KaTeX Web Worker offload for `renderSafe`'s final render pass. `katex-threshold.js` ports a small heuristic (`recommendNForSamples`) deciding whether a message's formula count is worth offloading; small/typical messages (1-3 short formulas) stay fully synchronous with zero added latency. `katex-worker-client.js`'s `renderMathBatch(mathParts)` batches ALL of one message's formulas into a single `type: 'module'` Worker call (`katex.worker.js`, which `import`s the same vendored `katex.bundle.js`), with an in-memory cache and automatic fallback to sync rendering on worker construction failure/timeout — never a partial worker/sync mix within one message. Also applies `normalizeKaTeXRenderInput` (replaces `·`→`⋅`, `℃`→`°C` — glyphs KaTeX can't render correctly) before rendering, caching, or dispatch.
- `mermaid-utils.js` — `estimateMermaidPreviewHeight`/`clampMermaidPreviewHeight` (sets the raw code-fence placeholder's height before the async render starts, reducing the jump when it's swapped for the real diagram) and `escapeSequenceTextSemicolons` (works around a real mermaid.js parser bug: a bare `;` inside sequence-diagram message/Note text — e.g. dialogue quoting SQL — breaks the parser; escaped to `#59;` on retry via `renderMermaidWithRetry`, which never touches semicolons that legitimately start a new mermaid statement).
- `sessions-ui.js` — sessions drawer (list/rename/export/delete/load); `loadSession` needs `initSessionsUI({ cancelActiveStream, renderHistory, scrollToBottom, clearPendingImages })`.
- `multiselect.js` — bulk-delete mode; `deleteSelectedMessages` needs `initMultiselect({ decrementNextHistoryIdx })` to keep `sidepanel.js`'s history-index counter in sync.
- `msg-search.js` — Ctrl+F in-conversation search. Fully self-contained.
- `detail-thread.js` — the "select text → 细聊" side-conversation card (see below). Fully self-contained; wires its own `mouseup`/`scroll` listeners on import.
- `icons.js` / `ui-utils.js` — leaf modules with no dependencies on the others: the `ICONS` SVG map, and `$`/`escM`/`_copyText`/`showToast`/`showConfirmDialog`/`sendMessage`/`_findCard`/`_insertCard`.

### Extraction quality improvements (no new UI)

Three backend-only improvements ported from the Python scraping library Scrapling, applied transparently to the existing pipeline (see also the firecrawl-ported improvements further below):

- **Prompt-injection defensive sanitization**: `extractInPageWorld` strips `<template>` elements and HTML comments from the Readability clone before parsing — a page can hide instructions meant for an LLM reader in markup a human never sees, and this removes them before they reach the model. It also marks CSS-hidden elements (`display:none`/`visibility:hidden`/`opacity:0`/`font-size:0`/zero-dimension boxes) on the **live** document before cloning — `getComputedStyle` needs rendering info the detached clone doesn't have — then strips them from the clone via the marker attribute, immediately un-marking the live DOM afterward so the page itself is never left mutated. `NOISE_SELECTORS`'s `[hidden]`/`[aria-hidden="true"]` only catch attribute-based hiding; this closes the stylesheet-driven blind spot (same threat model — a page can hide boilerplate or an actual injection payload from a human reader while still feeding it to the LLM). Only elements carrying non-empty `textContent` are checked, to bound cost and avoid false positives on empty containers awaiting JS hydration. All of `extractInPageWorld`/`extractDomTreeInPageWorld`/`extractFullInPageWorld` also strip zero-width chars (U+200B/200C/200D/2060/FEFF), control characters, and (ported from auditing browser-use's `sanitize_surrogates`) UNPAIRED UTF-16 surrogate code units (U+D800-DFFF) from their final text output — real-world pages sometimes leak broken emoji/symbol encodings as lone surrogate halves, which can break JSON encoding of the request body or get rejected outright by a provider's API. The regex (`/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/g`) must be pair-aware — a naive blanket `[\uD800-\uDFFF]` strip would also destroy legitimate emoji/astral characters, which are themselves valid high+low surrogate pairs.
- **Repeated-structure item markers** (`extractDomTreeInPageWorld`): when a container has ≥3 structurally-similar children (same tag + primary class token — e.g. 20 `.product-card` divs, or a `<ul>/<li>` list), walk() inserts `— Item N —` boundary markers before each item, so the LLM can see where one item ends and the next begins rather than receiving a flat interleaved wall of title/price/link fields with no grouping. Only triggers when the similar group makes up ≥60% of the container's visible children, to avoid spurious markers on navigation menus or mixed-content layouts. Concept: `fingerprint(el)` (tag + first class) + `findRepeatedGroup(children)` (Map-based majority grouping) inlined into the self-contained MAIN-world function. Automatically active in auto/dom modes, no user configuration.
- **`lib/dom-similarity.js`** — pure, Node-testable module: `stringRatio` (Dice-coefficient bigram similarity), `scoreDescriptors` (weighted element descriptor similarity), `cleanText` (zero-width/control char stripping). No longer used by production page-extraction code directly — `_relocateXhsAnchorsInPageWorld` (below) inlines its own copy per the MAIN-world constraint. Kept as the tested reference implementation; if either copy is changed, sync the other.
- **XHS adaptive relocation** (`tryXhsAnchorRelocation`/`_captureXhsAnchorFingerprintsInPageWorld`/`_relocateXhsAnchorsInPageWorld` in `page-extractor.js`): scoped narrowly to XHS's `#detail-title`/`#detail-desc` DOM-anchor fallback path. On every successful DOM-path extraction, saves the anchors' structural fingerprint to `chrome.storage.local`; on a future selector miss (site redesign), attempts structural relocation before falling through to Readability. Not applied to the other 9 sites (they rely on XHR interception). Fully invisible to the user — no UI, no new message types.
- **Same-origin iframe / open shadow-DOM extraction** (idea ported from auditing Alibaba's `page-agent` extension): all three MAIN-world extraction paths used to treat `<iframe>` as pure noise (`NOISE_SELECTORS`/`SKIP`) and never traversed shadow DOM, silently dropping any page content embedded that way. One level of traversal only (no recursion into nested iframes/shadow roots), gated on non-trivial text (>40 chars) and capped at 20 embeds per extraction, to bound cost on pathological pages. Cross-origin iframe access is wrapped in `try/catch` (throws or returns an inaccessible document depending on engine — same-origin policy, expected and unavoidable); closed shadow roots are unreachable by design (`el.shadowRoot` returns `null`). Per-function implementation: `extractDomTreeInPageWorld`'s `walk()` recurses into `el.contentDocument.body` for same-origin iframes and `el.shadowRoot.children` for open shadow hosts (safe unconditionally — `el.textContent` never includes shadow-tree content, so no double-counting). `extractFullInPageWorld` appends captured shadow/iframe `textContent` to its raw text dump. `extractInPageWorld` (Readability path, the default) captures embeds on the **live** document before cloning (same `mark → clone → unmark` pattern as the CSS-hidden pass above, since `cloneNode(true)` doesn't clone shadow trees and can't reach into a live iframe's `contentDocument`), then injects the captured HTML into the clone **before** the `NOISE_SELECTORS` strip — critically, iframe hosts are `replaceWith`'d (not just have content appended into them) since the `<iframe>` tag itself is in `NOISE_SELECTORS` and would otherwise be removed wholesale along with any injected content inside it; shadow-DOM hosts survive that strip so their content is just appended as a child. This ordering means captured content flows through the same noise/template/comment stripping as native page content, preserving the file's prompt-injection defense posture.

Four more improvements ported from auditing firecrawl (a heavy-backend scraping API service) — only the pure/local pieces of its content-cleaning logic apply; its Playwright/queue/remote-LLM infrastructure has no equivalent in a no-backend extension:

- **Turndown GFM plugin** (`turndown-plugin-gfm`, vendored as `lib/vendor/TurndownPluginGfm.iife.js`): plain Turndown collapses `<table>`/`<del>`/task-list checkboxes into unstructured text. `ensureReadabilityInjected` now also injects this plugin (best-effort — a `getVendorSrc(...).catch(() => null)` means a fetch failure here never blocks the *required* Readability/Turndown injection), and `extractInPageWorld` calls `td.use(TurndownPluginGfm.gfm)` only when it's actually present (`typeof TurndownPluginGfm !== 'undefined' && TurndownPluginGfm.gfm`), so extraction still works — just without GFM tables — if injection failed for any reason. **A real regression found while rebuilding `Turndown.iife.js`** to add this: turndown 7.2.4's CJS entry does `module.exports = TurndownService` directly (the constructor itself), not the `{TurndownService: ...}`/`{default: ...}` wrapper shape the old bundle apparently had — the existing `tGlobal.TurndownService || tGlobal.default` resolution silently produced `undefined`. Fixed by adding a final `|| tGlobal` fallback. **Rebuilding this vendor requires `npm install turndown turndown-plugin-gfm --no-save` inside `build/_deps/` first** — `build/_deps/node_modules` is gitignored/ephemeral, and a bare `npm run build` will otherwise skip both (source not found) and leave the committed bundles untouched; installing there is not additive — npm prunes whatever `build/_deps` packages aren't in that install's own dependency list as "extraneous" (same gotcha hit earlier with markmap-lib), so any *other* `_deps`-sourced vendor (marked, DOMPurify) needs reinstalling too if you need to rebuild it later.
- **`postProcessMarkdown(markdown)`** — a markdown-level cleanup pass run after `td.turndown(...)` inside `extractInPageWorld`: strips inline base64 `<img>` data URIs down to a `(<image-removed>)` placeholder (pure token waste — this is plain text sent to the model, not a vision attachment, so the model never "sees" the pixels either way), strips "Skip to Content" a11y anchors (boilerplate on most CMS/framework themes), escapes newlines inside multi-line link text, and (ported from auditing `browser-use`'s `_preprocess_markdown_content`) strips SPA-embedded JSON state/config blobs — LinkedIn/Facebook-style component-driven sites leave large `{"key":"value",...}` blobs sitting in otherwise-readable DOM text, which Readability doesn't recognize as noise since it's real text content, not markup. Three size-gated regex passes (JSON inside a code span, `{"$type":...}` blobs, nested `{"key":{...}}` objects — each requires ≥100 chars so small legitimate inline JSON examples in real article prose survive) plus a per-line `JSON.parse` sanity check before dropping any remaining long line that merely starts with `{`/`[` (a prefix check alone isn't enough since Markdown links/images also start with `[`). **A real test-infra gotcha hit while adding this**: `test/page-extractor.test.mjs`'s `loadSiblingFn` extracts a function's source via naive char-by-char `{`/`}` depth counting, with zero awareness of regex literals, string literals, or comments — a regex like `[^}]{100,}` or a comment containing a lone `'{'` introduces an unmatched brace count that throws `"unbalanced braces"` (or silently truncates the extracted source) even though the actual JS is perfectly valid. Fixed by writing the JSON-blob regexes' structural braces as `\x7B`/`\x7D` hex escapes instead of literal `{`/`}` (only the self-balanced `{100,}`-style quantifiers stay literal), using `charCodeAt(0) === 0x7B/0x5B` instead of `[0] === '{'`/`'['` string comparisons, and avoiding lone brace characters in the surrounding comments — the general lesson: any new regex/string added to a MAIN-world-injected nested function must keep the *raw source text's* brace count balanced, not just be valid JavaScript. **Declared as a function nested inside `extractInPageWorld`, not a module-level sibling** — see the `countImages` note below for why that distinction matters for MAIN-world injection.
- **`NOISE_SELECTORS` additions + `img[srcset]` highest-resolution picking**: two small `extractInPageWorld` tweaks. `NOISE_SELECTORS` gained `.lang-selector`/`.language`/`#language-selector` and `.breadcrumbs`/`#breadcrumbs`. Separately, before the noise strip, `docClone.querySelectorAll('img[srcset]')` picks the highest-resolution candidate (parses each `url descriptor` pair, keeps the max parsed-float score) and rewrites `src` to it — lazy-loaded pages often ship a low-res placeholder in `src` with the real image only reachable via `srcset`, and Turndown converts `<img>` using `src`. `w`/`x` descriptors are never mixed within one `srcset` per spec, so comparing raw floats within one image's own candidate list is safe even though the two descriptor kinds aren't cross-comparable in general.
- **`lib/markdown-chunker.js`** — pure, Node-testable utility module (no chrome/DOM deps) with two exports: `findSafeTruncationPoint(text, cap)` and `splitIntoMarkdownChunks(text, chunkSizeChars)`. Ported from auditing browser-use's `chunk_markdown_by_structure`. `findSafeTruncationPoint` replaces the raw `.slice(0, cap)` calls in `pdf-extractor.js` (two sites: wasm path and pdf.js path) — it scans lines forward tracking fence parity and table-row state, returning the rightmost `\n` position ≤ `cap` that is not inside an open fence block and not on a `|` table row line, falling back to `cap` when no such position exists (degrades gracefully for plain text). `splitIntoMarkdownChunks` replaces the call to `splitIntoChunks` in `attach-summarizer.js`'s `summarizeLongText` — it uses the same line-by-line greedy packing as the original, but pre-collects fenced code blocks (``` or ~~~ delimited) and table runs (consecutive `|` lines) into atomic units that are never split across chunks. Oversized atomic units become their own chunk rather than being dropped (same behavior as `splitIntoChunks` for single overlong lines). When a table overflows into a new chunk, its header+separator rows are prepended to the next chunk so the LLM can read the column names. **Three inline helpers in `page-extractor.js`** (not imported from `markdown-chunker.js` — MAIN-world `chrome.scripting.executeScript` constraint): `findSafeCutPoint` nested in `extractInPageWorld` (full fence+table tracking, same algorithm as the module version, written with `\x60`/`\x7B`/`\x7D` hex escapes and brace-balanced for `loadSiblingFn`), `findDomTreeCutPoint` nested in `extractDomTreeInPageWorld` (scans backward for `— Item ` or `#` heading boundary, falls back to last `\n`), and a short inline `\n\n`/`\n` boundary finder in `extractFullInPageWorld`. `old splitIntoChunks` export in `attach-summarizer.js` is kept (existing unit tests reference it directly).
- **Local re-attach change detection** (`lib/handlers/attach-change-tracker.js`): `checkAndRecordAttachChange(key, text)` hashes (FNV-1a, no crypto needed) the extracted text and compares it against the last snapshot stored under `key` in `chrome.storage.local` (key = `${mode}::${url}`, capped at 50 entries, oldest evicted first — deliberately NOT keyed by URL alone, since reader/dom/full modes naturally yield different text for the same page and would otherwise produce false "changed" signals). Wired into `background.js`'s `ATTACH_PAGE` case right after mask rules are applied, skipped for `selected`/`pdf-url`/`screenshot` modes (a text selection differs every time by design; PDF/screenshot text is a fixed placeholder, not real content) and for near-empty text (<50 chars). When changed, `ctx.changedSinceLastAttach = {previousAttachedAt, previousLength}` flows into `buildPageContextText`, which appends a `Note: this page's content has changed since it was last attached (...)` line to the header — **model-facing only, no new UI chip/badge**, consistent with this section's "no new UI" theme. Unlike firecrawl's `change-tracking-diff.ts` (which stores the full previous markdown and computes a real unified diff), browsa only needs a cheap "did this change at all" boolean, so a hash+length+timestamp per key is sufficient and avoids doubling `chrome.storage.local` usage for every attached page.

**`countImages` — a real, separate production bug found and fixed while adding the above** (unrelated to the firecrawl port itself, but directly adjacent code): it used to be a module-level sibling function that `extractInPageWorld` called directly. `chrome.scripting.executeScript`'s `func` injection only serializes the ONE function it's given (`Function.prototype.toString()` of just that function, re-evaluated in the page's own realm) — a call to a sibling top-level function throws `ReferenceError` in real Chrome the moment Readability actually succeeds. This only ever appeared to work in this file's own tests because the test harness (`runExtractInPageWorldOnLiveDoc` in `test/page-extractor.test.mjs`) manually concatenated both function bodies into one `vm` context — something the real `chrome.scripting.executeScript` call never does. Fixed by nesting `countImages` inside `extractInPageWorld` (same treatment as the new `postProcessMarkdown`), and the test harness was simplified to stop separately concatenating it. **General rule reinforced by this bug**: any helper a MAIN-world-injected function depends on must be declared *inside* that function's own body (or duplicated inline, as the XHS/dom-similarity functions already do) — never as a module-level sibling, no matter how obviously "shared" it looks in the source file.

Two more firecrawl-inspired features, added in a later pass, each with a genuine architectural finding baked into the design:

- **PDF client-side text extraction** (`pdfjs-dist`, vendored as `lib/vendor/pdf.bundle.js` + `lib/vendor/pdf.worker.bundle.js` — two independent `VENDORS` entries in `build/build.mjs`, since pdf.js spawns its own Worker at runtime by URL string, not a static `import` esbuild can inline into one file). **Key finding**: pdf.js's `getDocument()` needs a real `window` (its internal worker-init code touches `window.location`) — it cannot run in the bare service worker (`background.js` has no `window`) or in a plain dedicated Worker (workers have `self`, not `window`). `sidepanel.js` already has a `window` and is already open whenever 📎 can be clicked, and this codebase already has an exact precedent for spinning up a same-origin Worker from an extension page (`lib/sidepanel/katex-worker-client.js`'s `new Worker(chrome.runtime.getURL(...), {type:'module'})`) — so `lib/sidepanel/pdf-extractor.js`'s `extractPdfText()` runs there, needing **zero new permissions** (existing CSP already has `worker-src 'self'`) and **no `chrome.offscreen`**.
  - **Flow** (fail-open at every stage — every failure mode collapses back to exactly the pre-existing placeholder behavior, never a new stuck state): `tryPdfExtraction` (`lib/page-extractor.js`) tries `_fetchPdfBytesInPageWorld` via `chrome.scripting.executeScript({world:'MAIN'})` — **must run in-tab, not from the service worker**, so the fetch carries the page's own cookies (same reasoning as `fetchImageBase64` for XHS images; a service-worker-side fetch of an arbitrary site is cross-origin and would be CORS-blocked for anything login-gated). Success (and under `MAX_PDF_BYTES` = 30MB) → returns `{mode:'pdf-pending', pdfBase64}` **without storing to history yet** (mirrors the existing screenshot-mode early-return in `background.js`'s `ATTACH_PAGE` case exactly). Any failure (fetch error, oversized, thrown exception) → falls through to the pre-existing placeholder-text result, unchanged code path.
  - `sidepanel.js`'s `onAttachPage()` sees `ctx.mode === 'pdf-pending'`, calls `extractPdfContent()` (see below — the wasm-primary/pdf.js-fallback orchestrator, not `extractPdfText()` directly) raced against a 45s timeout; on success sends the new `ATTACH_PDF_CONFIRM` message; on total failure/timeout (corrupt/encrypted/scanned-image-only PDF) falls back to building the SAME placeholder text itself and sending it via the same message — `background.js`'s `ATTACH_PDF_CONFIRM` case (mirrors `ATTACH_SCREENSHOT_CONFIRM`) never needs to know a failure happened, it just stores whatever text it's given via `buildPageContextText` + mask rules.
  - **`pdf-inspector-wasm` layered on top (later pass)**: `lib/sidepanel/pdf-extractor.js`'s `extractPdfContent()` is now the actual entry point `onAttachPage()` calls — it tries `@firecrawl/pdf-inspector-wasm` (Firecrawl's Rust PDF-to-Markdown engine, compiled to WASM, published on the public npm registry — verified via `npm view`/`npm pack`, not something we wrote) FIRST, falling back to the pdf.js text-join above (`extractPdfText()`, kept completely unchanged as the fallback) only when the wasm path is unavailable or its result fails a usability check. **Why wasm over porting the Rust logic to JS**: researching `/mnt/data/work/pdf-inspector` (a separate, sibling Firecrawl repo from the main scraping API) found that its highest-value features — bordered/ruled-line table detection, image-anchored reading order, geometric underline detection, struct-tree tables — all require PDF vector-graphics/image operators that pdf.js's `getTextContent()` doesn't expose; porting them to JS would mean re-implementing a slice of PDF content-stream parsing. The repo already ships a complete WASM binding (`pdf-inspector/wasm/`) running the *entire* Rust engine (layout/table/heading/reading-order reconstruction) directly on raw PDF bytes via `processPdf(bytes, options) -> {markdown, pdfType, confidence, pagesNeedingOcr, layout, ...}` — every feature for free, zero new PDF-parsing code.
    - **Vendoring**: `pdf_inspector_wasm_bg.wasm` (4.84MB) + `pdf_inspector_wasm.js` (wasm-bindgen `--target web` ESM glue, verified to reference only `globalThis`, never `window`/`document` — safe inside a Worker) are copied as-is into `lib/vendor/` by a new `RAW_COPIES` step in `build/build.mjs`, separate from the `VENDORS`/esbuild loop — esbuild can't bundle a `.wasm` binary, and the glue is already a clean dependency-free ESM file that doesn't need bundling.
    - **CSP**: `manifest.json`'s `script-src` gained `'wasm-unsafe-eval'` (Chrome/Edge 103+, within the 114+ baseline) — required for `WebAssembly.instantiate` under MV3's default-restrictive CSP.
    - **Worker pattern**: `processPdf()` is synchronous/CPU-bound (its own README recommends a Worker for large documents) — `lib/sidepanel/pdf-inspector.worker.js` + `lib/sidepanel/pdf-inspector-worker-client.js` mirror `katex.worker.js`/`katex-worker-client.js`'s exact shape (`type:'module'` Worker, sticky `workerFailed` flag, timeout-resolves-`null` so the caller falls through rather than hanging) — one PDF per call, no batching needed (unlike KaTeX's per-message formula batches).
    - **Quality gate** (`isUsableWasmResult` in `pdf-extractor.js`): a wasm result is only accepted if `pdfType !== 'Scanned'` and `markdown` is non-empty after trimming. **Tuned empirically, not by assumption**: an earlier version also rejected results where `pagesNeedingOcr` covered every page, but a real single-page test fixture with genuinely-extracted, genuinely-correct text (`"Hello World"`) still came back with `pagesNeedingOcr: [1]` — the engine's OCR-need heuristic is a conservative low-confidence signal, not a reliable "extraction actually failed" signal, so the gate deliberately does not key off it. This is the concrete fix for the earlier open question "what if PDF extraction silently returns wrong/lost content" — `pdfType`/`confidence` are signals plain pdf.js text-join has no equivalent of.
    - **Testing**: unlike pdf.js (needs `DOMMatrix`/a real Worker, structural-tests-only), plain `WebAssembly.instantiate` runs directly in Node — `test/lib-pdf-inspector-wasm.test.mjs` does **real execution tests** (`initSync({module: bytes})` against the actual vendored `.wasm`, tiny hand-built PDF fixtures, asserting on real returned `markdown`/`pdfType`) rather than just checking the module's shape. `test/lib-pdf-extractor-content.test.mjs`/`test/lib-pdf-extractor-fallback.test.mjs` are split into **two separate files** (not two `test()` cases in one file) specifically because `pdf-extractor.js`'s internal `import('./pdf-inspector-worker-client.js')` is not cache-busted, so the worker-client's module-level `worker` singleton persists across every test case within one process — only a separate file (node's test runner isolates each file into its own process) gets a truly fresh singleton for the "wasm result is unusable, must fall through" scenario.
  - `_fetchPdfBytesInPageWorld` is a module-level MAIN-world function with two nested helpers (`toRawPdfUrl`/`fetchAsBase64`) — still safe under the `countImages` lesson (no sibling module-scope calls; only browser built-ins `fetch`/`Blob`/`btoa`/`URL`). Two refinements over a plain `fetch(location.href)`: (1) **GitHub `/blob/` rewrite** — `github.com/{owner}/{repo}/blob/{ref}/{path}` serves the GitHub web UI (`text/html`), not the file bytes, so fetching it returns HTML, fails PDF parsing, and falls back to the URL-only placeholder (the exact reason a GitHub-hosted `book.pdf` attached as `[PDF file - agent should fetch and read directly]` wasn't parsed). `toRawPdfUrl` rewrites it to `raw.githubusercontent.com` (serves the bytes, sends `Access-Control-Allow-Origin: *`); that cross-origin fetch MUST use `credentials:'omit'` — raw sends no `Access-Control-Allow-Credentials`, so `'include'` is browser-blocked (and the public raw endpoint needs no auth). Same-site fetches still use `'include'` for login cookies. (2) **HTML viewer detection** — if the response `Content-Type` is `text/html`, return an error instead of base64-encoding HTML for the parser (a real PDF served as `application/pdf`/`application/octet-stream`/`text/plain` still passes; only `text/html` is rejected). The 4 pre-existing vm-sandbox tests mock `fetch` with no `headers` field and no `URL` global, so the content-type read is guarded `(resp.headers && resp.headers.get(...)) || ''` (degrades to "not HTML, proceed") and `toRawPdfUrl`'s `try/catch` silently skips the rewrite when `URL` is absent — the two new tests pass `URL: globalThis.URL` and a `headers.get` mock to exercise both new paths. `MAX_PDF_BYTES` is 30 MiB (raised from 20) to admit ~20 MiB real-world PDFs like the GitHub book that prompted this; the tradeoff — base64 inflates 30 MiB to ~40 MB through `chrome.runtime` messaging, and wasm/pdf.js parsing is slower — is why the wasm worker `TIMEOUT_MS` went 45s->90s and `onAttachPage`'s race timeout 45s->150s (raised again from 120s to give the figure pass - scanning up to 200 pages + rendering up to 30 figures - room after wasm text extraction) (a timed-out wasm call still leaves room for the pdf.js fallback within the outer budget).
  - **PDF figure preservation (vision-capable providers)**: both wasm markdown and pdf.js `getTextContent()` are text-only - raster images and vector diagrams are silently dropped, losing information the model can't recover from text alone for figure-heavy PDFs (textbooks, papers with plots). `extractPdfContent()` takes an opt-in `opts.extractFigures` (passed by `sidepanel.js`'s `onAttachPage` PDF branch); when set, `extractPdfFigures()` detects figure-bearing pages, CROPS the actual figure regions (not whole-page renders), pairs each with its caption, and returns `result.figureImages` as `[{url, caption, page}]`. **Detection** (`classifyPageOps`, pure exported): one `getOperatorList()` per page (no rendering during detection) counts raster image ops (`paintImageXObject`/`paintImageMaskXObject`/`paintInlineImageXObject`/`paintImageXObjectRepeat`), vector paint ops (`constructPath`/`stroke`/`fill`/`eoFill`/`fillStroke`/...), and text-showing ops (`showText`/`showSpacedText`/`nextLineShowText`). A page is figure-bearing if it has any image op, OR vector paint ops >= 40 alongside text ops < 40 (a diagram/chart signature, not body text with rules). The ONE case that gate misses is a high-text vector page (vecOps>=40 AND textOps>=40): a matplotlib-style chart whose many axis/legend labels push textOps over the threshold, so the gate reads it as body text. Such a page is a real figure IFF it carries a "Figure N" caption - confirmed via `getTextContent()` ONLY on those ambiguous pages (not every page, to bound cost), which also drops high-text vector pages WITHOUT a caption (tables, ruled pseudocode boxes) that a naive vecOps-only gate would falsely admit and that would displace real figures under the budget. **Selection is in DOCUMENT order (page-ascending), not by density** - a real bug found in the earlier signal-desc design: `signal` (image ops weighted 3x + vector ops) let vector charts (signal 50-200) dominate raster figures (signal 3-6), so under a tight budget EVERY raster figure was cut in favor of vector pages. With a budget meant to cover most of a document's figures, reading-order selection is fairer across figure types; the budget, not density, decides what gets dropped (the latest-chapter figures, predictably). The figure budget is `FIGURE_MAX_IMAGES=30` (each figure is a ~1K-token image resent every chat turn, so 30 is already ~30K tokens/turn on a vision model - the user-picked ceiling for figure-heavy docs), scanning up to `FIGURE_MAX_SCAN_PAGES=200` pages, capped `FIGURE_MAX_PER_PAGE=2` so a multi-figure page (e.g. one with both Figure 3.3 AND 3.4) keeps both. `Array.sort` is stable in Chrome 114+, so same-page figures retain their within-page reading order; the output sort is the same page-ascending, so selection order = output order. (The earlier signal-desc design's separate output re-sort was where the 51,22,22,13,13,63-vs-13,13,22,22,51,63 ordering bug surfaced - now moot since selection itself is page-ascending.) **Extraction** (the part that needs a real browser - pdf.js + canvas - so untested in CI): three pure exported helpers do the math, only `extractFiguresFromPage`/`extractPdfFigures` orchestrate the render. `extractFigureBboxes(fnArray, argsArray, OPS)` walks the operator list tracking a graphics-state CTM stack and returns each raster image's default-user-space bbox as the accumulated CTM applied to the unit square [0,1]² (an image XObject is always painted in the unit square; the preceding `cm` scales/positions it). **`transform` POST-multiplies (canvas convention `CTM' = CTM × args`, NOT PDF-textbook prepend `args × CTM`)** - a real, central bug found via live testing of a LaTeX book (book.pdf): the prepend version composed the scale into the translate, throwing every bbox ~25x off-page, so EVERY figure degenerated to a whole-page fallback render. The visible symptoms that first looked like three separate bugs - duplicate identical thumbnails, "Figure 1.1" not detected, figures rendered as whole pages - were ALL this one root cause. `save`/`restore` push/pop the stack; the fix is `multiplyMatrix(stack[last], args)` (m1×m2 standard product, column-vector convention), verified end-to-end against real pdf.js operator lists for book.pdf pages 13/15/22/51 (bboxes now land 10-15% on-page and take the crop path, not the whole-page fallback). pdf.js's operatorList does NOT bake in the page's default matrix (MediaBox/CropBox + `/Rotate`) - that's applied separately at render via `Viewport.transform` - so tracked bboxes are in "default user space" (origin bottom-left, pre-rotation), the SAME space `getTextContent()` item positions live in, which is what lets bboxes and captions be matched directly with no viewport conversion. `mergeBoxes(boxes, gap)` collapses overlapping/nearby image placements (a subpanel a/b/c figure arrives as separate placements and should crop as one; fixpoint loop for transitive merges). `dedupeBoxesByName(boxes)` (pure, exported, runs BEFORE mergeBoxes and the per-page cap) drops same-image duplicates: `extractFigureBboxes` tags each box with `name` = `paintImageXObject`'s `args[0]` (the image XObject's objId), and two paints with the same objId are the SAME image at two positions (a repeated logo/watermark/decoration, or the same figure referenced twice). Keeps the largest-area box per name (the real placement, not a tiny repeat); `paintImageMaskXObject`/`paintInlineImageXObject` carry no resolvable name so are left untouched. A second, content-based safety net runs at the END of `extractPdfFigures`: any figure whose cropped JPEG data URL is byte-identical to an earlier one is dropped - this catches the same image embedded as two DIFFERENT XObjects (same pixels, different objId, which name-based dedup misses), and also collapses multiple whole-page fallbacks on one page to one. `toDataURL('image/jpeg', q)` is deterministic, so pixel-identical crops produce identical URLs. Both dedupes run before the page-ascending output sort. `findCaptions(textItems, figureBboxes, {maxDist})` pairs each figure with its nearest text run matching `^(figure|fig\.?|table|图|表)\s*\d+` (point-to-RECTANGLE distance from the caption text-item's position to the nearest EDGE of the figure's bbox, gated by maxDist = 15% page height - NOT distance to the bbox center: captions are left-aligned at the page margin / the figure's left edge, not centered under the figure, so a center metric over-penalizes the horizontal offset and silently dropped perfectly good captions - on book.pdf page 15, "Figure 1.1" sitting 19u below the figure's left edge measured 119u to-center and was rejected, breaking the whole caption-anchoring bridge until this was fixed). `extractFiguresFromPage` renders the page ONCE at `FIGURE_RENDER_WIDTH=1000`px (scale capped 2x, white background fill - PDFs have none; transparent/vector pages would render black-on-black in JPEG), then for each bbox: skip if <2% page area (decorative), whole-page-render if >=60% (full-page figure) or if the crop is degenerate (<20px - a wrong bbox), else `drawImage`-slice the bbox region (10px pad, clamped to canvas) into its own canvas. `paintImageXObjectRepeat` carries its own transform in `args[3]` (not via the cm stack) so its bbox is approximate (one tile). Vector-only figure pages (no raster bboxes - a flowchart/diagram) fall back to a whole-page render. Each figure JPEG's longest edge is downscaled to `FIGURE_MAX_LONG_EDGE=1568`px (`cappedJpeg`) - vision-model token cost scales with resolution and figures are resent every turn from history, so the cap compounds across the session. Fresh byte buffer per call (pdf.js detaches the buffer it's given; the wasm path may have already consumed `bytes`). **Caption anchoring (the positional-correspondence design)**: the caption is the bridge between the figure and the body - the body text references "Figure 3" and the figure is labeled with its detected caption "Figure 3: ...", so the model matches them by label, exactly how a human navigates figures. This gives figure<->text correspondence WITHOUT page markers, sidestepping the wasm-has-no-page-boundaries blocker (see Known limitation history below). **Storage** (`background.js`'s `ATTACH_PDF_CONFIRM`): `figureImages` (objects, or bare strings from older callers, normalized to `{url}`) are filtered to `{url, caption, page}`; when non-empty, a `## Figures` section listing the captions/labels in order (`1. Figure 3: ...\n2. Figure on page 7` for a no-caption figure) is appended to `finalText` BEFORE `buildPageContextText`, so it sits inside the page-context block the model reads. The history entry's `content` then becomes a multimodal array `[{type:'text',text: contextText (body + figures section)}, ...{type:'image_url',image_url:{url}}]` - image_url blocks in the SAME order as the figures section, preserving the caption<->image pairing - exactly mirroring `ATTACH_SCREENSHOT_CONFIRM`, so `buildMessages` (which pushes history entries through unchanged) resends the figures on every turn to a vision-capable provider. Empty/absent figures keep the plain-string `content` shape, so history stays uniform. Figure `image_url` blocks now reach BOTH provider paths: `buildMessages` (non-Hermes `/v1/chat/completions`) passes them through unchanged, and `buildRunsConversationHistory` (Hermes `/v1/runs`) converts them to `input_image` parts - see "Hermes inline images in conversation history" below. A non-vision backend model ignores them without error. **Summarize interaction** (`lib/handlers/attach-summarizer.js`): `maybeSummarizeAttachment` rewrites `entry.content` to a text-only rebuilt string on above-threshold PDFs - which would silently drop the figure `image_url` blocks. Fixed by preserving any existing `image_url` blocks through the rewrite (`[{type:'text',text: condensed}, ...original image_url blocks]`), so figures survive auto-summarize. The captions live in the text (figures section) and are condensed along with the body; since they're short labeled facts the summarizer usually keeps them, but it's not guaranteed - if condensed away, the entry degrades to "condensed body + unlabeled images in order" (still no worse than a text-only PDF), and the image ordering still pairs them with any body "Figure N" references the summarizer preserved. **Known limitation**: caption detection is heuristic - a figure with no numbered caption (or whose caption pdf.js split across text items) falls back to a page-label anchor (`Figure on page N`), which gives order-based but not figure-number-based correspondence; multi-column reading order is not reconstructed (single-column y-sort only, matching the rest of v1). True reading-position interleaving (figure inserted at its exact body position, not appended after) remains out of reach for the same reason it was before: `processPdf()` returns one markdown blob with NO page boundaries (no `\f`/`---`/`# Page N` - just `\n\n` indistinguishable from paragraph breaks, confirmed by probing the vendored wasm with a 2-page fixture), and `processPdf(bytes, {pages:[i]})` per-page extraction re-parses the whole PDF each call (~10x one-call measured, unscalable for large PDFs); pdf.js per-page text IS cheap and would give true markers+interleave but sacrifices wasm's table/heading quality. Caption anchoring is the deliberately-chosen middle path that keeps wasm quality AND gives correspondence without needing those boundaries. **Testing**: `test/lib-pdf-extractor-figures.test.mjs` covers `classifyPageOps`, `extractFigureBboxes` (CTM math: single transform, save/restore isolation under the post-multiply convention - the save/restore test is convention-distinguishing so a regression to prepend is caught, `paintImageXObjectRepeat`'s args[3] map, no-image-ops, mask/inline carry no `name`), `dedupeBoxesByName` (same-name collapses to largest, different names + unnamed survive, three-same-name -> one, empty), `mergeBoxes` (overlap/within-gap/far/empty), and `findCaptions` (nearest-match, maxDist gating, no-caption, Figure/Fig/Table/图/表 regex, point-to-rect left-edge-caption pairing - the regression guard for the center-metric bug) - all pure, synthetic fn/text arrays, no pdf.js - plus `extractPdfContent`'s figure wiring via an injected `opts._extractFigures` test seam (the real `extractPdfFigures` needs a browser, same "pdf.js can't run in bare Node" constraint as the content/fallback tests). `test/attach-pdf-confirm.test.mjs` covers the caption-anchored multimodal storage (figures section + captions + page-label fallback), bare-string normalization, and figures-survive-summarize. The `FIGURE_TIMEOUT_MS=90_000` race in `extractPdfContent` clears its timer in a `finally` (otherwise the pending 90s timer stalls Node's test runner).
  - Explicitly out of scope for the first pass: no `attach-change-tracker` wiring for PDF text yet (keyed generically off `ctx.text`/`ctx.mode` and could be added later without re-touching this flow); no OCR support.
- **DOM relevance-based item reordering** (`extractDomTreeInPageWorld`'s repeated-group branch, `lib/page-extractor.js`): the existing hard `htmlCap` truncation cuts content strictly by DOM position — if a page has many repeated items (product cards, search results) and the total exceeds the cap, whichever items are later in the DOM are silently dropped regardless of relevance. `query` (whatever's currently typed in the input box, opportunistically read at the moment 📎 is clicked — **browsa's UX is strictly "attach first, type question later"**, confirmed via code trace, so there is no dedicated moment where "the question" and "the attach action" coexist; this reuses whatever's already there rather than changing that UX) is threaded through `sidepanel.js`'s `ATTACH_PAGE` message → `background.js` → `extractActiveTab` → `runGenericExtraction` → `extractDomTreeInPageWorld({htmlCap, query})`. When `query` is empty (the common/intended flow), this is a **provable no-op** — the reorder's stable sort with all-equal (zero) scores keeps the original DOM order byte-identical.
  - **`bm25ScoreItems(texts, queryText)` + `tagPriorityWeight(el)`** (nested inside `extractDomTreeInPageWorld`, never module-level siblings, per the `countImages` lesson) — replaced the original `scoreTextByQuery` character-bigram Dice-coefficient cosine (ported from auditing crawl4ai's `BM25ContentFilter` instead): proper Okapi BM25 (k1=1.5, b=0.75) with term-frequency + document-length normalization + inverse-document-frequency, scored over the CURRENT repeated-group's items as the corpus (N = group size). Uses `tokenizeBigrams` (character bigrams, **not** firecrawl's/crawl4ai's whitespace-tokenized+stemmed words) as BM25's "terms" — deliberately adapted for browsa's primarily-Chinese UI, since CJK text has no whitespace word boundaries and bigrams sidestep the need for a stemmer entirely. `tagPriorityWeight` multiplies the BM25 score by a gentle factor (h1=1.5, h2=1.35, h3=1.2, h4-h6=1.1, none=1.0) when an item's `querySelector('h1,h2,h3,h4,h5,h6')` finds a heading — much gentler than crawl4ai's page-wide h1×5, since repeated-group items are all the same type of thing (e.g. product cards), not a mixed document tree. The `if (query)` gate and `{child, itemNum}` true-DOM-order labeling below are unchanged.
  - **Reordering preserves two invariants tested explicitly**: (1) each item's printed `— Item N —` label always reflects its TRUE DOM-order position, never its position in a reordered output slot (so "what's item 5" always means the same thing to the user, regardless of relevance reordering) — achieved by capturing `{child, itemNum}` pairs before sorting, and only permuting which item's *content* fills each fixed slot; (2) non-group "outlier" siblings interspersed among group items (e.g. a "Load more" button) keep their exact original position — the `el.children` walk loop structure is unchanged, only the group-item content assigned to group slots is reordered.
  - Only `dom`/`auto`-falling-into-dom-tree modes are affected; `reader`/`full` mode truncation (a dumb `.slice(0, htmlCap)`) is unchanged — out of scope, they have no "repeated items" concept to reorder.
- **Link-to-citation numbering** (`postProcessMarkdown`'s final step, `lib/page-extractor.js`, ported from auditing crawl4ai's `convert_links_to_citations`): on link-dense pages, `[text](https://long-url...)` repeating the full URL inline wastes tokens for no benefit to the model. When a page has **≥6 unique `http(s)` link URLs**, every occurrence of `[text](url)` is rewritten to `text⟨N⟩` (Unicode angle brackets — not `<N>`, which a markdown/HTML renderer could interpret as a tag, and not `[N]`, which reads as another markdown link) and a `## References` list mapping number→URL is appended. Below the 6-link threshold the markdown is left untouched — the marker+footer overhead isn't worth it for a couple of citation links. A negative lookbehind (`(?<!!)`) excludes image syntax `![alt](url)`. Confirmed safe from a UI-rendering standpoint: `PAGE_CONTEXT_PREFIX`-tagged attach text is explicitly skipped by `sidepanel.js`'s `renderHistory` before it ever reaches the markdown renderer — this transform only affects what the model (and `sessions-ui.js`'s plain-text export placeholder) sees, never chat-UI-rendered HTML.
- **Virtualized/windowed-feed scroll-and-restore** (`preExtractCleanup`'s Step 3 extension, `lib/page-extractor.js`, ported from auditing crawl4ai's `_handle_virtual_scroll`): distinct from ordinary lazy-load (which only ever *appends* content) — a virtualized feed (e.g. a react-window-style infinite list, common on the Twitter/小红书/知乎 sites in browsa's XHR-interception list) *replaces* off-screen items in the DOM as the user scrolls, so most items are never simultaneously present; the existing lazy-load loop alone would silently lose everything except whatever's rendered at the final scroll position. `findFeedCandidate()` (nested, nothing shared with `extractDomTreeInPageWorld`'s `findRepeatedGroup` despite the near-identical fingerprint concept — these are separate `executeScript` injections with no shared closure) scans for a container with ≥3 same-`tag+firstClassToken` children covering ≥60% of its visible children, with `scrollHeight` meaningfully taller than `clientHeight`. Before each of Step 3's existing scroll rounds, `snapshotFeedItems()` clones (`cloneNode(true)`) any not-yet-seen matching children into a `Map<contentHashKey, clone>` (capped at `MAX_RESTORED = 30`; hash key = first 150 trimmed chars of `textContent`, cheap dedup). After all scroll rounds finish (same point Step 3 already restores `scrollY`), any snapshotted item whose hash key is no longer present among the container's LIVE matching children gets its clone appended back as a real DOM child — `style.cssText = 'position:absolute;left:-9999px;top:-9999px;'` (not `display:none`/`hidden`, which `extractDomTreeInPageWorld`'s `isHidden()` would treat as noise and strip) plus `data-browsa-restored="1"`, so it's invisible/no-layout-shift for the user but still a legitimate child of the correct container for the later, separate extraction pass to pick up via `el.children` — correctly grouped under the same fingerprint/numbering scheme. **This is a real (if invisible) mutation of the live page** — accepted deliberately as a lower-risk variant of the same live-DOM-mutation category `preExtractCleanup` already performs unconditionally (cookie-banner dismissal and read-more expansion are both *permanent*, no-revert mutations; restored clones are strictly additive and invisible, never removing/clicking anything). Heuristic, not deterministic: may miss real virtualized feeds with an unrecognized layout pattern, or (rarely) restore an unrelated element whose children legitimately changed for other reasons (e.g. a rotating ad slot) — both failure modes degrade gracefully, matching this function's existing best-effort philosophy. `actions.feedItemsRestored` is only set on the returned result object when a feed candidate was actually found and at least one item was restored.
- **Pre-extraction page cleanup** (`preExtractCleanup` in `lib/page-extractor.js`, concept from auditing firecrawl's in-page "actions" system — reimplemented from scratch since firecrawl's implementation lives entirely in a remote Playwright service): async MAIN-world function injected before the main extraction starts, runs within a 3.5-second hard budget. Four steps: (1) dismiss cookie/consent banners — **container-gated** (only clicks within elements matching the `NOISE_SELECTORS` cookie pattern `.cookie/.cookie-banner/[class*="cookie" i]` etc.) + **danger-word veto** (skips any button whose text matches purchase/delete/confirm/pay keywords, even inside a matched container) — the two gates together prevent misclicking destructive buttons; (2) expand collapsed "read more" sections — clicks `[aria-expanded="false"]` and `[class*="read-more" i]` elements, capped at `MAX_EXPAND = 8`; (3) scroll to bottom and wait for lazy-loaded content to appear (up to `MAX_ROUNDS = 3` if page keeps growing), always restores original `scrollY` afterward so the user's view isn't disrupted; (4) virtualized-feed item restore — see the dedicated bullet below for full design. **Unconditional, no user-facing setting** (`runGenericExtraction`'s `preClean` param always defaults `true` — there was briefly an `autoCleanBeforeExtract` options.html toggle, removed per explicit user request to just hardcode the default behavior instead of adding a switch nobody asked for). Only runs inside `runGenericExtraction` (i.e., only for generic reader/dom/full/auto modes — site-specific XHR-cache fast-paths for YouTube/Bilibili/XHS etc., plus PDF/screenshot/selected short-circuits, all return early in `extractActiveTab` before `runGenericExtraction` is reached). **`loadSiblingFn` regex updated** to handle `async function` declarations: the original `function NAME(...)` regex omitted the `async` keyword, so extracting `preExtractCleanup` (which uses `await` internally) would have produced a non-async function body, causing a SyntaxError at test runtime. Fixed with `(?:async\s+)?function NAME(...)` — backward-compatible (non-async functions still match fine), and benefits any future async MAIN-world injected function.
- **GitHub `/blob/` raw fast-path** (`tryGithubExtraction` in `lib/page-extractor.js`, wired into `extractActiveTab` right before `runGenericExtraction`): a `github.com/{owner}/{repo}/blob/{ref}/{path}` URL is the GitHub file viewer - a JS-heavy UI, not an article. Its nav mega-menus (Platform/Solutions/Resources/Open Source/Enterprise), branch picker (×2), file-search combobox, and hamburger toggle are **all** `[aria-expanded="false"]` controls - 13 of them on a typical blob page. `preExtractCleanup`'s Step 2 clicks up to 8, which in a real browser **opens those mega-menus/pickers** (the visible "browsa自动去操作了很多东西" churn a user reported) AND adds their overlay DOM to the live page, so the clone `extractInPageWorld` then hands Readability is polluted and the extracted article is wrong. Verified empirically: the vendored Readability run on the **clean** GitHub HTML (no `preExtractCleanup`) correctly extracts the 18,671-char README - so Readability is fine on GitHub; `preExtractCleanup` corrupts it. (The codebase already half-knew - `extractDomTreeInPageWorld`'s line-710 comment lists "github" among sites that "return nothing useful".) The fix fetches the file's **raw source** from `raw.githubusercontent.com` directly and returns it, bypassing `preExtractCleanup` (no page mutation) **and** Readability (no corruption). `raw.githubusercontent.com` serves `access-control-allow-origin: *` + `text/plain; charset=utf-8` for text files (verified - .md/.py/.toml/.json/.js all come back as `text/plain`), so the service worker can `fetch` it directly with `credentials:'omit'` (raw sends no `Access-Control-Allow-Credentials`, so `'include'` is browser-blocked - same reasoning as the PDF path) - no MAIN-world/cookie dance, unlike XHS image fetches. The blob->raw rewrite (`^/([^/]+)/([^/]+)/blob/(.+)$` -> `raw.githubusercontent.com/{1}/{2}/{3}`) mirrors `_fetchPdfBytesInPageWorld`'s `toRawPdfUrl` exactly. Raw source is also **better content** than Readability's plain-text output: markdown for READMEs and source for code files preserve code fences / link URLs / tables that Readability flattens. Fail-open at every stage: 404 (private repo / missing file), non-`text/*` content-type (images/PDFs come back as `image/*`/`application/pdf`), a null byte in the first 4 KB (binary disguised as text), a network throw, or an empty body all return `null`, and the caller falls through to the generic cascade - which still works for private repos via the authenticated page (Readability on the user's logged-in DOM). PDFs never reach here: `tryPdfExtraction` (with its own raw rewrite) runs first in `extractActiveTab`. `gist.github.com` is a different URL shape and is NOT handled (falls through to generic). **The broader concern this surfaces** - `preExtractCleanup`'s Step 2 clicking every `[aria-expanded="false"]` on ANY site is risky for any page with disclosure widgets (nav dropdowns, accordions) - is deliberately NOT addressed globally here; the GitHub fast-path sidesteps it for the reported case, and taming Step 2 generally (e.g. scoping it to content-area containers, or skipping sites where aria-expanded controls are clearly chrome) is a separate, lower-priority cleanup. Tested in `test/lib-github-extraction.test.mjs` (URL rewrite incl. `www.github.com` and slash-bearing refs, non-github/non-blob -> null with no fetch, 404/image/pdf/null-byte/network/empty fail-open, textCap truncation, credentials:'omit').


### MV3 service worker gotchas

- The SW sleeps after ~30s idle. **Module-level Maps reset on every restart** — do not store durable state there.
- `setTimeout` inside the SW is unreliable after message handling returns — the SW may sleep before it fires. Use `chrome.alarms` or `chrome.storage.session` instead.
- `chrome.storage.session` persists across SW restarts within a browser session. Used for pending SELECTION_ACTION delivery.
- Any open port (`browsa-nav`, or a `browsa-chat`/`browsa-subchat` port currently mid-turn) disconnects when the SW sleeps. `browsa-nav` reconnects after 1s via `onDisconnect` — the new port object must have all `onMessage` listeners re-attached, via the named `connectNavPort()` function pattern, not inline `addListener` inside `init()` only. `browsa-chat`/`browsa-subchat` don't need this: being per-turn already, a fresh one just opens on the next send (see "Port lifecycle" below).

### navPort reconnect pattern (critical)

`onMessage` listeners bind to a specific port object. On SW restart, a new port is created. Always re-attach listeners:

```js
function onNavPortMessage(msg) { /* handler */ }

function connectNavPort() {
  navPort = chrome.runtime.connect({ name: 'browsa-nav' });
  navPort.postMessage({ type: 'NAV_HELLO', tabId: currentTabId });
  navPort.onMessage.addListener(onNavPortMessage);   // re-bind every time
  navPort.onDisconnect.addListener(() => {
    navPort = null;
    setTimeout(() => { if (!navPort) connectNavPort(); }, 1000);
  });
}
```

### Port lifecycle: persistent (navPort) vs per-turn (browsa-chat, browsa-subchat)

Two different, deliberate port patterns coexist — don't mix them up:

- **`browsa-nav`**: connected ONCE at panel init, reconnected on disconnect via the `connectNavPort()` pattern above. Correct for a port that represents "whichever tab the panel is currently watching" — re-registering it under a new tabId on tab-switch (`NAV_FOLLOW`) is exactly what you want.
- **`browsa-chat`** (main chat) and **`browsa-subchat`** (detail-thread side conversations, see below): opened **fresh for every single turn/send**, with an explicit HELLO → wait-for-ACK handshake before the actual chat message is sent (mirrors `onSend()`'s `STREAM_HELLO`/`STREAM_HELLO_ACK`). A persistent, connect-once port was tried for `browsa-subchat` and caused a real bug: if the SW went idle while the user was reading before opening a detail-thread card, `sendMessage({type:'SUBCHAT'})` wakes the SW almost instantly, but the persistent port's reconnect fires on a delayed timer — early deltas got silently dropped before the port re-registered. Opening fresh + waiting for ACK avoids this race entirely. If you add another streaming feature, default to this per-turn pattern, not a persistent one.

### `onSend()` vs `resumeInFlightStream()` — formerly two independent DONE handlers, now shared via `wireChatStreamPort()`

`sidepanel.js` used to have **two separate, hand-maintained copies** of the "stream finished" handling logic: one inside `onSend()`'s `port.onMessage` listener (the common path — user sends a message, this side panel opened the port), and one inside `resumeInFlightStream()`'s own `port.onMessage` listener (the side panel reconnects to a stream that's *already running* — triggered by `STREAM_PEEK` reporting `inFlight:true` on panel init, e.g. after an SW sleep/restart, a tab switch, or the panel being briefly closed and reopened mid-reply). Being independently written meant every feature added to one's `DONE` branch had to be manually mirrored into the other's, or it silently only worked on the "lucky" path where the panel never disconnects mid-stream.

**Found via a real user bug report** (video-note `[mm:ss]` timestamps not seeking): the user's reply took long enough to generate that the SW went idle mid-stream, so the reply completed via `resumeInFlightStream()`'s DONE handler — which was missing the `dataset.videoSrc` stamp entirely (present in `onSend()`'s). Auditing the rest of that handler for the same class of drift found two more gaps (interactive `CHOICE_REQUEST` buttons, the "已达上限" max-turns `→ 继续` button) and a fourth (`ERROR`/`ABORTED` did a raw `el.textContent = ...` instead of the safe-render pipeline, leaving literal markdown and a stuck blinking cursor).

**This class of drift is now structurally impossible for the shared parts**: `wireChatStreamPort({ port, tabId, getEl, getRenderer, state, stopKeepAlive, onRetry, afterDone, onAborted })` holds the ONE implementation of CHUNK/TOOL_PROGRESS/TS_STATUS/APPROVAL/CLARIFY/DONE/ERROR handling, called by both `onSend()` and `resumeInFlightStream()`. Only the genuinely different bits stay as caller-supplied hooks: `onRetry` (onSend wipes the bubble and rebuilds the renderer; resume just shows a toast), `afterDone`/`onAborted` (resume also calls `setStreamingUI(false)`/disconnects the port, onSend's own `port.onDisconnect` already covers that). The STREAM_HELLO/ACK handshake is similarly shared via `waitForStreamHelloAck(port, tabId, { onAck })`.

**If you add a new field to the DONE chunk or a new post-DONE side effect, it now only needs to go in `wireChatStreamPort()` once** — both callers pick it up automatically. The one thing that can still drift is the caller-specific hooks (`onRetry`/`afterDone`/`onAborted`/`getEl`/`getRenderer`) — if a new feature genuinely needs different behavior on resume vs a fresh send, that's exactly where it belongs, and `test/lib-sidepanel-resume-streaming.test.mjs` still exists to catch anything that should have been shared but wasn't.

**Related, independently-discovered bug while adding those regression tests**: `.msg.assistant:last-of-type` (used in `getOrCreateAssistantBubble()`, `ensureAssistantEl()`, and the resume port's `onDisconnect` handler to re-find "the current assistant bubble" after a possible DOM-identity change) is a fragile selector — `:last-of-type` requires the element to be the last **DIV** among its siblings by tag name, not just the last `.msg.assistant` found. Once a sibling `<div>` is inserted right after the bubble — `renderChoiceRequest`'s `.choice-request` wrap, or `appendMsgAction`'s action row, both real and both reachable from this exact resumed-DONE handler — the assistant bubble silently stops matching `:last-of-type` for any *later* lookup in the same resumed session, causing the next turn's re-discovery to spawn a stray empty bubble instead of finding the real one. Fixed by replacing all three call sites with `[...messagesEl.querySelectorAll('.msg.assistant')].pop()` — takes the last element of the already-filtered set, immune to intervening sibling tags of the same name. If you're tempted to use `:last-of-type`/`:first-of-type` anywhere near message bubbles, use this pattern instead — those pseudo-classes only work as "the last of this literal thing" when you can guarantee no same-tag-name sibling ever gets inserted nearby, which the message list can't promise.

### Refactoring principles (applied across an 8-item cleanup pass, keep following these)

When you notice near-identical code blocks (copy-pasted case statements, hand-rolled test mocks, independently-written handlers of the same message protocol), don't just leave a comment about it — extract it, following whichever of these patterns fits:

- **N near-identical `switch` case blocks that differ only by 1-2 literal values** → one const lookup table (`{msgType: {field1, field2}}`) + a single case with fallthrough labels (`case 'A': case 'B': ... case 'Z': { ... }`) reading from the table. Example: `background.js`'s `SITE_MESSAGE_MAP` replacing 9 copy-pasted `YOUTUBE_DATA`/`JUEJIN_ARTICLE`/etc. cases. Adding a new entry becomes "one line in the table" instead of "copy-paste a whole case block and hope you didn't typo a field name."
- **N functions that build different content but share an identical trailing/leading shape** → factor out just that shared shape into a small helper the N functions call, passing only what varies. Example: `makeSynthResult(mode, meta, text, extra)` in `lib/site-synthesizers.js` replacing a duplicated `truncated: {...}` footer across 9 `synthesize*Result` functions. Don't try to unify the whole function — only the part that's actually identical.
- **A message-handling case in `background.js`'s `handle()` switch whose body is genuinely a self-contained feature (not just 1-2 lines)** → extract to `lib/handlers/<feature>-handler.js`, mirroring `chat-handler.js`/`subchat-handler.js`. `handle()` should stay a thin dispatcher; each handler file owns its own imports and logic. Group related small cases into ONE handler file with an internal dispatch (see `session-handler.js`'s 7 cases) rather than one file per case — a file per case is overkill for thin pass-throughs.
- **Two functions independently implementing the same wire protocol/handshake** (e.g. two `port.onMessage` listeners for the same message types, both hand-written) → this is the highest-risk duplication, because bugs from it are invisible until the "unlucky" code path is exercised (see the DONE-handler drift trap above). Extract a single shared function taking the callers' differences as parameters/callbacks (`wireChatStreamPort`'s `getEl`/`getRenderer`/`onRetry`/`afterDone`/`onAborted` hooks). Never leave "these are two independently-maintained copies, keep them in sync manually" as the long-term plan — that's a stopgap, not a fix.
- **A file that has grown to hold multiple unrelated responsibilities** (e.g. `lib/page-extractor.js` mixing MAIN-world-injected extraction functions with plain site-synthesis functions) → split along the responsibility boundary, checking constraints first. MAIN-world-injected functions (passed to `chrome.scripting.executeScript`) MUST stay self-contained per file — no calling a sibling module-level function (see the `countImages` lesson elsewhere in this doc) — so those can't be pulled out. Plain functions with no such constraint (like the 9 `synthesize*Result` functions, which never run via `executeScript`) can move freely into their own module (`lib/site-synthesizers.js`). This same split was applied again later to pull three more groups out of `page-extractor.js` (2322 -> 1569 lines): `buildPageContextText`+`buildMessages` (-> `lib/message-builder.js` - pure message assembly, no DOM), `ensureReadabilityInjected`+`getVendorSrc`+the vendor-source caches (-> `lib/readability-injector.js` - runs in the SW, not MAIN world), and the 7-function XHS group (-> `lib/xhs-extractor.js` - the 3 MAIN-world functions move as self-contained `func:` references that still serialize alone; `gradeXiaohongshuResult` moves too as a tested reference, same pattern as `lib/dom-similarity.js`). **Test-infra note for any future move out of `page-extractor.js`**: `test/page-extractor.test.mjs` extracts function bodies from source by regex + brace-matching (`loadSiblingFn(name, file = '.../page-extractor.js')`), file-path-hardcoded - a move requires updating `loadSiblingFn`'s `file` arg (it already accepts one) AND the `readFile` paths in the two XHS sandbox helpers (`runXhsInSandbox`/`runXhsWithStateInSandbox`).
- **Hand-rolled test mocks repeated across multiple test files** (e.g. 4+ files each defining an identical `makeFakePort()`/`chrome.tabs`/`chrome.storage` mock) → extract to `test/helpers/*.mjs`, but preserve every file's actual behavioral differences as explicit parameters (don't silently unify subtly-different mocks — e.g. `trackDisconnect: false` for the one file that deliberately needs a no-op `onDisconnect`). Verify each migrated file's tests pass individually before running the full suite, since these mocks sit underneath everything sidepanel.js does.
- **Before extracting, grep for zero-call-site dead exports** in the same area — `getActiveProvider` in `lib/storage.js` and `MERMAID_PREVIEW_MIN/MAX_HEIGHT`'s `export` in `mermaid-utils.js` were both found this way. `grep -rn "functionName" --include="*.js" --include="*.mjs"` across the whole repo (including `test/`) before deciding a function is dead — a function only used by tests is not automatically dead: `lib/dom-similarity.js`'s `scoreDescriptors` has zero production call sites (the MAIN-world-injected `_relocateXhsAnchorsInPageWorld` in `lib/xhs-extractor.js` inlines its own copy instead, since it can't import), but the file's own header comment says it's deliberately kept as "the tested source of truth for the scoring algorithm" that the inlined copy must stay in sync with — read the surrounding comments before deleting a test-only export, not just the grep count.
- **After every extraction, run the full test suite AND `check-compat.sh`**, not just `node --check` — a passing syntax check does not catch a wrong field name in a lookup table or a subtly different default value.



### Tab switching

`chrome.tabs.onActivated` in the side panel **must not touch the DOM** — Chrome keeps the side panel document alive across tab switches. Only update `currentTabId`, page-meta text, and send `NAV_FOLLOW` to the nav port.

### Provider selection

`populateProviderSelect` (`sidepanel.js`) sorts the dropdown reachable-first (stable sort — ties keep `DEFAULTS.providers`' original order), not configured-first: Hermes ships with a non-empty default `baseUrl`, so "has a baseUrl" is never a strong enough signal that the user actually intends to use it. `pingCard` (`options.js`) auto-switches `activeProvider` the first time a provider transitions from not-reachable to reachable (a real successful ping) — this is what actually prevents the "configured OpenAI-compatible but the dropdown silently stayed on Hermes" trap, since ping state (not baseUrl presence) is the signal. Re-pinging an already-reachable provider does **not** re-trigger the switch, so it won't clobber a deliberate switch between multiple already-verified providers. `saveCard` unconditionally clears `_pingState[name]` on every save — capture `wasReachable` *before* calling `saveCard`, not after, or the check is always false.

### Hermes inline images in conversation history (`buildRunsConversationHistory`)

`handleChat` (`lib/handlers/chat-handler.js`) splits on `provider.isHermes`: Hermes providers go through `runsApiStream` -> `/v1/runs` (richer: approval/clarification/tool/thinking events), everyone else through `chatStream` -> `/v1/chat/completions`. The two paths handle history images differently, and this was a real bug:

- **Non-Hermes** (`/v1/chat/completions`): `buildMessages` (`lib/message-builder.js`) pushes history entries through **unchanged**, so `image_url` vision blocks (XHS images, PDF figures, screenshots, pasted images) reach the provider every turn. Inline images always worked here.
- **Hermes** (`/v1/runs`): history is sent as a separate `conversation_history` field. It used to be **flattened to text-only** - every `image_url` block was dropped, so attached page images never reached Hermes at all (only same-turn pasted images in `input` survived, and only for one turn). This was the "Hermes's text-only flattening" referenced elsewhere in this file.

`buildRunsConversationHistory(history)` (exported pure helper, extracted for testability - `handleChat` itself needs a heavier chrome.storage mock than the suite provides) replaces that flatten. It converts each history entry's content into the `/v1/runs` part schema: `text`/`input_text` -> `input_text`, and `image_url` -> `input_image` (accepting both the OpenAI `{image_url:{url}}` shape browsa stores and the bare-string `{image_url:'...'}` shape `/v1/responses` uses). Image-only turns are **kept** (not dropped, not replaced with a placeholder); empty turns are dropped. The result is `[{role, content: string | [input_text/input_image...]}]`.

**Verified against a live Hermes endpoint** (`http://101.47.17.208:8642`, the default in `lib/storage.js`): with a vision-capable model, inline images are read natively on all three endpoints - `/v1/runs` `input`, `/v1/chat/completions` `messages`, and `/v1/responses` `input` (a solid-color image was correctly identified as red/blue, and a bar-count image was counted correctly for small counts). `conversation_history` images (history) are also read natively. **History note**: an earlier server config pointed the `vision_analyze` tool at a text-only model, which made current-turn `input` images fail ("my active model doesn't support image input" / "vision analysis failed (Model only support text input)") while `conversation_history` images still worked (native tokens bypass the tool) - that asymmetry is now resolved by switching the server to a vision-capable model. If `input` images ever fail again with that message, the fix is server-side (the model), not browsa.

`buildHermesTurn(msg, history)` (exported pure helper, extracted for testability alongside `buildRunsConversationHistory`) builds the current turn: pasted images (`msg.images`) go directly into `input` as `input_image` parts alongside the text (a structured `[{role:'user', content:[input_text, input_image...]}]`), and `conversation_history` is just the built prior history (via `buildRunsConversationHistory`). The real text+images turn is persisted to history after the turn, so the NEXT turn's `buildRunsConversationHistory` carries it normally. (An earlier version routed pasted images into a synthetic trailing `conversation_history` turn to work around the broken `vision_analyze` tool described above - no longer needed now that the server runs a vision-capable model, and that split was less semantically correct than keeping text+images together.) Non-Hermes `/v1/chat/completions` passes `image_url` blocks through unchanged via `buildMessages`, so `buildHermesTurn` is Hermes-only.

`openai-client.js`'s `chatStream` passes `messages` through to `/v1/chat/completions` verbatim (`body = { messages, stream: true, ... }`), so the OpenAI inline-image format `{type:'image_url', image_url:{url:'data:...'}}` is exactly what Hermes (and any OpenAI-compatible gateway) receives - no transformation needed on that path. `runsApiStream` sends `{input, instructions, conversation_history, session_id, ...}` to `/v1/runs`.

### Screenshot attach undo

`appendAttachSystem(text, relatedEl)` takes an optional second argument — the DOM element the attach-system message's "撤销" (undo) button should remove on a successful `UNDO_ATTACH`, in addition to fading its own label text. For the screenshot mode specifically, `onAttachPage`'s confirm callback calls `appendScreenshot(dataUrl)` (which now returns the `.screenshot-preview` element it created) *before* `appendAttachSystem`, so the preview element can be passed in as `relatedEl` — otherwise undoing a screenshot attachment left the image visibly stuck in the chat even though the label correctly showed "（已撤销）". ### Attach-in-progress visual feedback

`onAttachPage` previously gave almost no visible feedback while an extraction was in flight — just `attachBtn.disabled`/`opacity:0.5` and a `title` hover tooltip (invisible unless the user hovers and waits out the native tooltip delay), which matters because worst-case latency is real: `preExtractCleanup` alone budgets 3.5s, and PDF extraction is raced against a 45s timeout. `chrome.runtime.sendMessage` (used for `ATTACH_PAGE`) is strictly one request/one response — true backend stage-by-stage progress (like the `browsa-chat` streaming port) would require restructuring `ATTACH_PAGE` into a port, which was explicitly out of scope for this pass. Both the button state and the progress pill are restored/removed in the existing `finally` block, covering success, error, and thrown-exception paths uniformly.

### Video note timestamps (`[mm:ss]` in-place seek + auto-rewrite)

Video notes (youtube/bilibili page context attached via 📎, then "总结…") get clickable `[mm:ss]` timestamps that seek the video page's `<video>` in place, plus an automatic rewrite so the notes actually contain them.

- **`videoSrc` is the single source of truth.** `ATTACH_PAGE` (`background.js`) stamps `historyEntry.videoSrc = { platform: ctx.mode, url: ctx.meta?.url || '', tabId }` on the page-context user turn when `ctx.mode === 'youtube' || 'bilibili'`. `handleChat` (`lib/handlers/chat-handler.js`) scans history newest-first for the most recent entry with `videoSrc`; that drives both the prompt hint and the stamp on the stored assistant turn + DONE chunk. `onSend` does NOT auto-attach page context - the user must click 📎 first, or no `videoSrc` is present and none of this fires.
- **`videoNoteHint`** (English, appended to `effectiveSystemPrompt` only when `videoSrc` is set) asks the model to organize notes into sections and append each section's start time at the end of its heading as `[mm:ss]` (or `[h:mm:ss]` over an hour), keeping the exact bracket form so it can be linked. It MUST be declared before `effectiveSystemPrompt` - that const references it, so a declaration below it is a TDZ crash at runtime (green tests don't prove the CHAT case actually ran - see memory `tdz-decl-order-in-handler`).
- **`linkifyTimestamps(el)`** (`lib/sidepanel/render.js`, exported) wraps bracketed timestamps - `[mm:ss]`, `[h:mm:ss]`, and BiliNote's `*Content-[mm:ss]` prefix (stripped in display) - in `<span class="browsa-ts" data-s="<seconds>" role="button" tabindex="0">`. It deliberately matches ONLY bracketed forms (regex `/(?:\*Content-)?\[(?:(\d+):)?(\d{1,2}):(\d{2})\]/g`), not bare `mm:ss`, to avoid false positives on version numbers/ratios. It uses a `TreeWalker` over text nodes and skips `SCRIPT`/`STYLE`/`<a>` parents; the wrapper is a `<span>`, not an `<a>`, so `decorateLinks`'s `target=_blank` doesn't fire on it. Runs inside `makeStreamRenderer`'s `isDone` path (after `decorateLinks`) and in `renderHistory`.
- **`dataset.videoSrc`** is stamped on the assistant bubble so a click knows which tab/URL to seek: the live path gets it from the DONE chunk's `videoSrc` field; `renderHistory` gets it from the stored `m.videoSrc`. `onTimestampClick(ts)` reads `ts.dataset.s` + `JSON.parse(ts.closest('.msg')?.dataset.videoSrc)`, sends `SEEK_VIDEO` (tabId + seconds), and on `!res.ok` falls back to `chrome.tabs.create({ url: appendTimeParam(vs.url, seconds) })` (`?t=`/`&t=`) so a closed video tab still jumps to the moment.
- **`SEEK_VIDEO`** (`background.js`) uses `chrome.scripting.executeScript({ world: 'MAIN' })` because YouTube's `#movie_player.seekTo(s, true)` is a page-attached custom method unreachable from the ISOLATED-world DOM wrapper (same reason active-fetch uses `world:'MAIN'`). B站 has no equivalent API, so it sets `video.currentTime = s` and dispatches `seeking`/`timeupdate` so the custom progress bar / danmaku sync. Wrapped in try/catch returning `{ok:false}` on any error (tab closed, no `<video>`).
- **Auto timestamp rewrite** (`handleChat`, after the stream loop, inside the main `try` before CHOICE_REQUEST extraction): if the model's first reply (v1) lacks `[mm:ss]`, the background silently asks it ONCE to reformat with them. The gate is conservative because `videoNoteHint` fires on *any* video-page reply - so the rewrite requires ALL of: `videoSrc` set, `!/\[(?:\d+:)?\d{1,2}:\d{2}\]/.test(fullReply)` (same shape `linkifyTimestamps` matches), the user's message matches a notes/summary keyword regex (`总结|笔记|纪要|要点|大纲|概要|梳理|summary|summarize|notes?|outline|takeaways?|key points`), and `fullReply.length > 50`. A specific question like "这个视频作者是谁？" is therefore NOT reformatted. The rewrite reuses `doStream({ silent: true })` - `doStream` takes an `opts` arg whose `silent` variant accumulates deltas into `streamState` and keeps the idle timer alive but does NOT push `CHUNK` to the UI. The rewritten v2 is delivered as the DONE chunk's `full`, which the side panel's DONE handler re-renders the whole bubble from (`renderStream(finalText, true)` does `el.innerHTML = await renderSafe(delta)`) - so v2 seamlessly replaces v1 with no bubble-wipe machinery. A `TS_STATUS` chunk shows a transient `⏱ 正在补充时间戳…` indicator above the bubble via `showToolProgress` (NOT pushed to `toolEvents`, so DONE's `renderToolHistory` won't render it; cleared by DONE's existing `clearToolProgress`). On abort (user Esc) or any error during the rewrite, v1 is kept and still stored + DONE'd - the user never loses the notes they saw stream in (`pushChunk`'s `safePost` makes the DONE a no-op if `cancelStream` already disconnected the port; v1 is still persisted to history). Only ONE rewrite attempt - no recursion if v2 also lacks timestamps. The CHOICE_REQUEST extraction + `appendToHistory` + `DONE` run AFTER the rewrite on the final `fullReply` (v2 or v1); the literal `await storage.appendToHistory({ role: 'assistant', content: fullReply, ...(videoSrc ? { videoSrc } : {}) });` line is preserved so static-analysis tests still match.

### Auto-summarize long attachments (`lib/handlers/attach-summarizer.js`)

Ported from auditing BiliNote's chunk-summarize-merge pipeline. A 4-5 hour video's transcript (one `[mm:ss] text` line per caption, per `youtube-content-script.js`/`bilibili-content-script.js`) runs 60-80K+ characters. The real problem this solves: `buildMessages` (`lib/message-builder.js`) resends the **entire history** on every single turn — an oversized attachment isn't a one-time cost, it's resent in full on every message for the rest of the session, and can silently exceed a smaller-context provider's window (browsa's own `maxTextChars` cap defaults to 1,000,000 chars, far above what many self-hosted/local providers can handle).

- **No UI changes needed.** The raw attach text is never rendered in the chat bubble (the UI only shows a small "已附加" chip, driven by `PAGE_CONTEXT_PREFIX` detection, not by rendering `content`) — so replacing the stored entry's `content` after the fact is a pure storage-side enhancement. This is why the whole pipeline can run **fire-and-forget, after** `ATTACH_PAGE` has already responded — no "compressing…" progress UI, no port/stream lifecycle to get wrong.
- **Flow**: `background.js`'s `ATTACH_PAGE` case computes `willSummarize = all.autoSummarizeAttachments !== false && shouldSummarize(ctx.text, all.summarizeThresholdChars)` *before* `appendToHistory`; if true, stamps `historyEntry.attachId = crypto.randomUUID()` (same "extra field on the entry" pattern as `videoSrc`) so the entry can be found again later. After `appendToHistory` and right before the `return`, calls `maybeSummarizeAttachment({ attachId, ctx, provider })` **without awaiting it** — `ATTACH_PAGE`'s response latency is completely unaffected.
- **`maybeSummarizeAttachment`** (`lib/handlers/attach-summarizer.js`) does the real work: `summarizeLongText` splits `ctx.text` via `splitIntoChunks` (greedy, line-respecting — never splits a transcript line in half), runs one `chatStream()` call **per chunk in parallel** (`Promise.all` — chunks are independent, `chatStream` has no shared module-level state), then one final merge `chatStream()` call combining the chunk summaries in order. Each call passes `onDelta: () => {}` (never surfaced to any UI — this isn't tied to any chat turn's port/streamState) and `signal: AbortSignal.timeout(90_000)` (bounds worst case; `AbortSignal.timeout` is already an established pattern here, see `chat-handler.js`'s `fetchLlmsTxt`). Then re-reads `storage.getHistory()` fresh, finds the entry by `attachId`, and replaces just that entry's `content` (rebuilt via `buildPageContextText({...ctx, text: summarized})`, same header format) plus stamps `summarized: true`.
- **Video-mode timestamp preservation is the one place this is genuinely easy to get wrong**: the chunk-summary and merge prompts for `mode === 'youtube' || 'bilibili'` explicitly instruct the model to keep every kept point's original `[mm:ss]` marker exactly (earliest timestamp when merging lines) — never invent/renumber/drop timestamps. Without this constraint, condensing a timestamped transcript would silently break `linkifyTimestamps`/`SEEK_VIDEO`'s clickable-jump feature (wrong or missing anchors). Non-video attachments get a generic "preserve key facts/names/numbers/quotes, drop repetition" prompt instead.
- **Fails open, never corrupts**: `maybeSummarizeAttachment` catches everything (provider not configured → `console.warn` + no-op; network error/timeout; empty result) and simply leaves the original raw entry untouched on any failure — identical to today's pre-existing behavior, never a partial/garbled write. If the entry was removed by the time summarization finishes (user hit 撤销, deleted it via multiselect, or it fell out via `MAX_HISTORY`/`MAX_TOTAL_CHARS` trimming), `history.findIndex` returns `-1` and it's a silent no-op — not an error.
- **Config**: `autoSummarizeAttachments` (default `true`) and `summarizeThresholdChars` (default `0` = use the built-in 40,000-char fallback, same "0 means use default" convention as `maxTextChars`/`textCap`) live in `lib/storage.js` DEFAULTS, editable in options.html's "Content limits" card.
- **`ATTACH_PDF_CONFIRM` (`background.js`) gets the exact same `willSummarize`/`attachId`/`maybeSummarizeAttachment` wiring as `ATTACH_PAGE`** (added after a real gap was found: PDF attachments used to bypass this feature entirely — no threshold check, no attachId stamp — so a 50-100 page PDF's extracted text, comfortably under `pdf-extractor.js`'s own `DEFAULT_MAX_CHARS` = 500K lossy-truncation ceiling but well over the 40K summarize threshold, was stored in full and resent on every turn forever, unlike an equally-sized webpage attachment). The two length caps serve different purposes and neither substitutes for the other: `DEFAULT_MAX_CHARS` is a hard, lossy truncation safety valve against pathological sizes; `summarizeThresholdChars` triggers an LLM-based compression pass that preserves key facts. `pdf` mode uses the generic (non-video) summarize/merge prompts — PDFs have no `[mm:ss]` timestamps to preserve.

### History image compaction (`lib/handlers/history-compactor.js`)

After the model has seen attached images on the turn it answers, `image_url` pixel blocks in stored history are replaced with **labeled text placeholders**, so subsequent turns resend cheap text instead of ~1K-token-per-image pixels every turn (figure-heavy PDFs were ~30K tokens/turn). Modeled on hermes-webui's `_compact_session_image_parts_for_persistence` (which compacts to `[screenshot]`); browsa uses the figure's own label instead of a generic placeholder so multiple images stay distinguishable.

- **When**: `handleChat`'s success path only, AFTER the assistant turn is persisted + DONE pushed + `clearStreamState` (so DONE isn't delayed). Gated by `mayHaveImages` (pasted this turn OR history already had `image_url` blocks) to avoid a storage read on image-less turns. On abort/error it does NOT run (leaves pixels for retry). Failure is fire-safe (warn + continue, never breaks the turn).
- **Label source** (the "how to distinguish multiple images" answer): PDF figures already carry a `## Figures` section in the entry's text block (built by `ATTACH_PDF_CONFIRM` from the same `figures` array as the `image_url` blocks, so label[N] matches image[N]). `parseFigureLabels` extracts the `N. <label>` lines; the Nth `image_url` becomes `[<label>]` (e.g. `[Figure 3: training pipeline]`, `[Figure on page 7]`). Non-PDF images (XHS / screenshot / pasted, no figures section) get `[image N]` (1-indexed within the entry).
- **No new stored fields**: labels are derived from existing text, so `buildMessages` (which pushes raw entries) and `buildRunsConversationHistory` (rebuilds `{role,content}`) are untouched - nothing extra reaches the API. Compacted entries are pure text arrays, which both builders already handle natively.
- **Idempotent**: an entry with no `image_url` parts is returned by reference unchanged, so re-running is a no-op (and the gate skips the call entirely on image-less turns).
- **Accepted tradeoff**: later turns can't see figure pixels, only the label/caption - "what's in Figure 3" is answerable from the caption, "what's the y-axis label of Figure 3" is not. (Re-attaching pixels on explicit later-turn visual questions - "option 3" - was considered and deferred.) Bonus: compaction shrinks stored history (data URLs -> tiny text), easing `MAX_TOTAL_CHARS` pressure.
- **Testing**: `test/history-compactor.test.mjs` covers `parseFigureLabels` and `compactEntryImageParts` (PDF labels, non-PDF `[image N]`, extras-beyond-labels fallback, idempotency, string/null/no-image entries, image-only, mixed part types) - all pure, no chrome/storage. The `compactImagePartsInHistory` I/O wrapper is thin (read -> map -> write-if-changed).

### Content scripts

Site-specific interceptors (`lib/content-scripts/*-content-script.js`) run in **MAIN world** at `document_start` and wrap `window.fetch` / `XMLHttpRequest` to capture SPA API responses. They send messages to the background, which stores results in `SITE_CACHES` (a registry object in `background.js` — one `Map` per site, keyed by `tabId`). Adding a new site only requires a single entry in `SITE_CACHES`; restore, lookup, and cleanup iterate it automatically. XHS is the one exception — it uses a separate `xhsXhrCache` Map with its own push logic instead of a `SITE_CACHES` entry. `lib/content-scripts/selection-toolbar.js` runs in ISOLATED world at `document_idle` on all `https://` pages.

MAIN-world content scripts can't use ES module imports, so URL matchers there must resolve relative paths against the page: use `new URL(url, location.origin)`, not `new URL(url)` — a bare relative fetch/XHR path (e.g. `fetch('/api/...')`) throws and gets silently swallowed otherwise.

Extension resources used inside Shadow DOM or injected pages (e.g. `icons/icon16.png`) must be declared in `web_accessible_resources`. `ShadowRoot` supports both `querySelector('#id')` and `getElementById('id')` in current Chrome — prefer `querySelector` for consistency with the rest of the codebase.

### YouTube content script critical lessons (confirmed 2026-07-25)

- **`chrome.runtime` is undefined in MAIN world** — `installYouTubeInterceptor()` must NOT guard on `chrome.runtime`; use only `typeof window !== 'undefined'`.
- **YouTube loads the current video's captions via XHR, not fetch** — `XMLHttpRequest.prototype.send` must be wrapped to intercept `/api/timedtext`. The fetch wrapper only catches recommended/sidebar video pre-fetches (whose responses are often HTML error pages or empty).
- **timedtext URLs require a PO token (`exp=xpe`)** — re-fetching the URL from our own code returns 200 + empty body (missing browser-level auth headers). The only reliable path: intercept the XHR response body at the moment the player itself makes the request, parse it, store in `window.__browsaTranscriptCache[videoId]`.
- **Do not modify `fmt=` in the baseUrl** — even though `fmt` is not in `sparams`, re-fetching with a modified URL still fails. Parse the original response body directly (supports both json3 and srv3/ttml XML).
- **`/player` uses ANDROID client, `/next` uses WEB client** — ANDROID `/next` returns `singleColumnWatchNextResults` with `elementRenderer` blobs (unparseable). Fire both in parallel via `Promise.allSettled`.
- **YouTube SITE_CACHES is always skipped** — the passive interceptor runs in MAIN world without `chrome.runtime`, so `SITE_CACHES` never gets YouTube data. `page-extractor.js` always falls through to `activeYouTubeFetch`.

### Detail-thread ("SUBCHAT") side conversations

Selecting text inside an assistant reply opens an inline card scoped to that excerpt (`lib/sidepanel/detail-thread.js`: `openDetailThread`, `findBlockAnchor`; `lib/handlers/subchat-handler.js`: `handleSubchat`/`handleSubchatAbort`, dispatched from `background.js`'s `SUBCHAT`/`SUBCHAT_ABORT` cases). Rules that are easy to accidentally violate when touching this code:

- **Never call `storage.appendToHistory`** for SUBCHAT — the whole point is that closing the card discards everything, main history stays clean. Covered by a dedicated test in `test/subchat.test.mjs`.
- **Always `chatStream()`, never `runsApiStream()`** — no tool/approval flow needed for a side question, and reusing the main chat's Hermes session would mix it into the agent's main-task context.
- **`CHOICE_REQUEST_HINT` must stay out of SUBCHAT's system message** — it's a separate constant from `CAPABILITY_HINTS`, appended only to CHAT's `effectiveSystemPrompt`. SUBCHAT has no UI to parse/render the resulting buttons, so including the instruction leaks raw `CHOICE_REQUEST:{...}` JSON into replies.
- Rendering reuses `.msg.user`/`.msg.assistant` classes directly (not a parallel CSS ruleset) so it can't silently drift from the main chat's look — remember to add the `.done` class manually when a bubble finishes streaming, or the `.msg.assistant::after` blinking-cursor pseudo-element never goes away.

### Testing

Tests use Node's built-in test runner. They mock the `chrome` global before importing extension modules. Tests are a mix of static-analysis/integration tests against `handle()` and real jsdom-based execution tests (import the real module, drive real DOM events, assert on real DOM output — using the actual vendored `marked`/`DOMPurify`/`katex`/`highlight.js` bundles, not stand-ins) for the `lib/sidepanel/*.js` modules. There is no real browser in any of this — jsdom stands in for the DOM. `sidepanel.js` itself has zero exports (it just calls `init()` at module load and only exposes behavior through DOM events), so its own tests (`test/lib-sidepanel-streaming.test.mjs`, `test/lib-sidepanel-resume-streaming.test.mjs`, `test/lib-sidepanel-status-dot.test.mjs`) load the real `sidepanel.html` into jsdom, mock the `chrome.*` surface `init()` needs, import the real `sidepanel.js`, and drive it via simulated clicks/keydowns/port messages — the same black-box approach a browser would use, since there's no exported function to call directly. The test suite has 673 tests across 56 files. WebAssembly is the one exception to the "no real browser" rule above: unlike pdf.js (needs `DOMMatrix`/a real Worker), plain `WebAssembly.instantiate` runs directly in Node, so `test/lib-pdf-inspector-wasm.test.mjs` does real execution tests against the actual vendored `.wasm` binary instead of structural/mocked ones.
