## 消息路由与 SW 生命周期

### Message flow

```
page content scripts  →  chrome.runtime.sendMessage  →  background.js (SW)
                                                              ↓
sidepanel.js  ←  navPort (browsa-nav long-lived port)  ←  background.js
sidepanel.js  ←  streamPort (browsa-chat, opened fresh per turn)  ←  background.js
sidepanel.js  ←  subChatPort (browsa-subchat, opened fresh per send)  ←  background.js
```

- **`background.js`** is the service worker and single message router. All `chrome.runtime.onMessage` handling flows through one `handle()` switch — still the single exported dispatcher (tests import it); the biggest case bodies live in `lib/handlers/`: `chat-handler.js` (`CHAT`), `subchat-handler.js` (`SUBCHAT`/`SUBCHAT_ABORT`), `attach-confirm-handler.js` (five deferred-storage confirm cases, routed via one `ATTACH_CONFIRM_TYPES.has()` check), `mermaid-repair.js` (`REPAIR_MERMAID` — one-shot apiStyle-dispatched provider call; never enters chat history; the panel re-validates with a local mermaid parse before swapping the error card), `session-handler.js` (all 8 session-drawer cases, thin pass-throughs to storage), `provider-resolver.js` (shared `resolveProvider`/`resolveInferenceParams`), `agent-stream-session.js`, `prompt-assembly.js`, `site-cache-store.js`, `approval-relay.js`, `attach-*` family. `lib/sidepanel/media-headers.js` holds the shared ASR DNR header-injection recipe. `ATTACH_PAGE` and small cases stay inline (SITE_CACHES registry 外迁 site-cache-store.js 后 case 依赖变显式 import；同批抽了 relaySelectionAction / runInVideoTab / siteCacheCtx 三个 file-local helper，xhsXhrCache 仍留 background 因推送要摸 navPorts).
- **Rulings — do not re-propose** (wiki: Design-Decisions table + ADR-0001): **Media download UI REMOVED 2026-09-05** — headers on `chrome.downloads` requests are not reliably injectable (Chrome 「无法从网站上提取文件」) + YouTube PO-token anti-bot; out-of-core-loop feature hostage to third-party CDNs. The ASR/精读 pipelines (feeding the MODEL media) keep their own fetch machinery + `media-headers.js` — unaffected. **tabCapture「边播边录」ASR-fallback REJECTED 2026-09-28** — paused/skipped segments are silence, an unplayed video can't be transcribed; `tabCapture`/`offscreen` were never added to the manifest.
- ⚠ **`LOAD_SESSION` 约定**：`storage.loadSession` 未命中返回 **-1**（0 是合法空会话长度）；调用侧只读内层 `res.data.ok`（混层 `!res?.ok && !res?.data?.ok` 曾让失败分支永不命中 → 点开已删会话假成功）。
- **`agent-stream-session.js` (C4)**：`stopHermesRun` 是 Hermes `/stop` 的唯一实现（STREAM_ABORT / chat idle-stop / subchat SUBCHAT_ABORT 三处调用）；审批/澄清 pending 条目一律走 `agentPendingEntry` 工厂——**条目形状即 approval-relay 的分派接口，字段名勿改**（2026-10-15 并发审批堆叠起条目**追加** `data` 显示载荷——STREAM_PEEK 补挂卡片要用，relay 读的既有字段不变）；键生成/清扫走同文件 `agentPendingKey(scope)`/`sweepAgentPending(map, scope)`；闭包外壳与 chunk 推送名留在两个 handler（subchat.test.mjs 的 lockstep pin 锁着源码形状，改代码必改 pin）。**`prompt-assembly.js` (C5)**：CAPABILITY_HINTS/CHOICE_REQUEST_HINT 单份，/prompt 检视器显示=发送（镜像缺块曾出过事故）。**`approval-relay.js`**：per-kind relay 唯一 owner。**pending map 按 reqKey 堆叠（2026-10-15，勿退回 tabId/subId 单槽）**：曾按 tabId/subId 单槽键控——同一 surface 的第二个并发审批事件 set 覆盖第一条（requestId 永久丢失、agent 干等），面板 `removeAgentCards()` 又删掉旧卡，还有窄竞态：应答在途时槽位被覆盖，给 A 的「允许」错配到 B 的 requestId。现在每条 pending 键=`agentPendingKey(scope)`（`<tabId|subId>::<seq>`），APPROVAL/CLARIFY chunk 带 `reqKey`，卡片 dataset 也有，RESPOND 按 reqKey 精确路由；**答成即删（两侧同语义，失败保留供重试，卡片同样失败不销毁）**；回合收尾 finally/abort 用 `sweepAgentPending` 按 scope 清扫；面板侧卡片**堆叠**（按 reqKey 去重、按插入序排在最后一张卡后），`removeAgentCards` 只剩回合收尾用；STREAM_PEEK 的 in-flight 分支返回 `pendingAgentCards`（该 scope 名下未决条目），resume 路径据此补挂——重开面板不再出现「流停在等审批却没有卡可答」。行为地板：approval-clarify（reqKey 路由+答成删+PEEK 补挂+创建点 pin）与 lib-detail-thread（两事件→两卡→各答各的，变异验证）双侧；hermes clarify body 两条路径都 `String(response ?? '')` 规范化（background 曾发裸 null）。
- **`lib/llm-client.js`** is the wire-protocol layer (`chatStream` / `runsApiStream` / `responsesStream` / `anthropicStream` + apiStyle-aware `ping` — see "Provider API styles" below). 四条流共用一个 `openSseStream()` 骨架（C1：fetch/错误分类/预算协商/abort/切分/收尾），每协议只留 `buildRequest` + 纯事件解析；`<thinking>` 开合状态机单份。**`thinking: 'inline'|'omit'` option (default `'omit'`)**：'inline' 把推理过程包成**一个**内联 `<thinking>…</thinking>` 块；`chatStream` 另解析 DeepSeek 式 `reasoning_content`（含 `reasoning` 别名）。**ONLY chat-handler 和 subchat-handler 传 `thinking:'inline'`**（主聊天+追问卡要活折叠块）；其余消费者（attach-summarizer / mermaid-repair / selection-explain / agentic-extract）保持 omit——输出必须是干净文本，**勿翻默认**。
- **Hermes runs reasoning truth (ADR-0004, 勿「修」)**：`/v1/runs` 唯一的 reasoning 载体 `reasoning.available` 是步骤**答案**的 ≤500 字 replay（step 末尾发出），单步轮与已流式文本逐字节相同——llm-client 的 echo guard 丢弃它是正确的，显示它会复读答案。agent 实时推理 delta 不达任何 API 面（gateway `_create_agent` 不订阅 reasoning_callback）；真要暴露需 Hermes 侧补丁 + browsa 侧合并（叙事见 wiki Providers-and-Agents）。compat 层同理无 reasoning 面 → SUBCHAT 走 `runsApiStream` 专用 per-subId 会话（`subchatHermesSessions`，绝不用主聊天的存储会话）；abort 经 `subChatRunIds` 打服务端 `/v1/runs/{id}/stop`。

### MV3 service worker gotchas

- The SW sleeps after ~30s idle. **Module-level Maps reset on every restart** — do not store durable state there.
- `setTimeout` inside the SW is unreliable after message handling returns — the SW may sleep before it fires. Use `chrome.alarms` or `chrome.storage.session` instead.
- `chrome.storage.session` persists across SW restarts within a browser session. Used for pending SELECTION_ACTION delivery.
- Any open port (`browsa-nav`, or a `browsa-chat`/`browsa-subchat` port currently mid-turn) disconnects when the SW sleeps. `browsa-nav` reconnects after 1s via `onDisconnect` — the new port object must have all `onMessage` listeners re-attached, via the named `connectNavPort()` function pattern, not inline `addListener` inside `init()` only. `browsa-chat`/`browsa-subchat` don't need this: being per-turn already, a fresh one just opens on the next send (see "Port lifecycle" below).

### navPort reconnect pattern (critical)

`onMessage` listeners bind to a specific port object. On SW restart, a new port is created. Always re-attach listeners:

```js
function onNavPortMessage(msg) { /* handler */ }

function connectNavPort() {
  navPort = chrome.runtime.connect({ name: 'browsa-nav' });
  navPort.postMessage({ type: 'NAV_HELLO', tabId: currentTabId });
  navPort.onMessage.addListener(onNavPortMessage);   // re-bind every time
  navPort.onDisconnect.addListener(() => {
    navPort = null;
    setTimeout(() => { if (!navPort) connectNavPort(); }, 1000);
  });
}
```

### Port lifecycle: persistent (navPort) vs per-turn (browsa-chat, browsa-subchat)

Two different, deliberate port patterns coexist — don't mix them up:

- **`browsa-nav`**: connected ONCE at panel init, reconnected on disconnect via the `connectNavPort()` pattern above. Correct for a port that represents "whichever tab the panel is currently watching" — re-registering it under a new tabId on tab-switch (`NAV_FOLLOW`) is exactly what you want.
- **`browsa-chat`** (main chat) and **`browsa-subchat`** (detail-thread side conversations, see below): opened **fresh for every single turn/send**, with an explicit HELLO → wait-for-ACK handshake before the actual chat message is sent (mirrors `onSend()`'s `STREAM_HELLO`/`STREAM_HELLO_ACK`). A persistent, connect-once port was tried for `browsa-subchat` and caused a real bug: if the SW went idle while the user was reading before opening a detail-thread card, `sendMessage({type:'SUBCHAT'})` wakes the SW almost instantly, but the persistent port's reconnect fires on a delayed timer — early deltas got silently dropped before the port re-registered. Opening fresh + waiting for ACK avoids this race entirely. If you add another streaming feature, default to this per-turn pattern, not a persistent one.

### Tab switching

`chrome.tabs.onActivated` in the side panel **must not touch the DOM** — Chrome keeps the side panel document alive across tab switches. Only update `currentTabId`, page-meta text, and send `NAV_FOLLOW` to the nav port.

### Provider API styles (`apiStyle` + `lib/llm-client.js`)

**`lib/openai-client.js` was renamed to `lib/llm-client.js`** (2026) — the file already held Hermes `runsApiStream`, so the old name was misleading; it's now explicitly the wire-protocol layer for all providers. It holds `chatStream`, `runsApiStream`, `responsesStream`, `anthropicStream`, and `ping`.

Every **LLM** provider carries an **`apiStyle`** field (`'chat' | 'responses' | 'anthropic'`, default `'chat'`), editable via a compact dropdown on each options-page LLM card. **LLM providers are user-added, not presets**: `DEFAULTS.providers` ships only `hermes` (type:'agent', isHermes:true, apiStyle:'chat', alias:'Hermes Agent') — the fixed, non-deletable agent backend, which has **no** apiStyle dropdown (it always uses `/v1/runs`). The old `compatible`/`anthropic` presets are gone; instead the options page shows a render-only **reserved empty slot** (an `LLM 1` card, kept visible until a real llm-1 is committed to storage by filling it in and Saving — never persisted itself, so the sidebar dropdown stays clean); a **＋ Add Provider** button is always available and appends a fresh `{ type:'llm', apiStyle:'chat' }` card, each with its own **Alias** field (`alias`, shown as the card title and in the sidebar dropdown so multiple configs stay distinguishable), Base URL / API key / Model ID, the protocol dropdown, and a **delete** button. Deleting the active provider falls back to `hermes`. Stored user configs deep-merge over these defaults, so existing providers keep their values and just gain the new `apiStyle` field.

`doStream` (`lib/handlers/chat-handler.js`) dispatches on `provider.apiStyle` (Hermes/`isHermes` still wins for `runsApiStream`):
- **`chat`** → `chatStream` (`/v1/chat/completions`), `buildMessages` passthrough (OpenAI `image_url` blocks).
- **`responses`** → `responsesStream` (`/v1/responses`): `buildResponsesInput(msg, history)` builds `input` as `[{role, content: string | [input_text/input_image...]}]` (reuses `buildRunsConversationHistory`'s part schema); the system prompt goes in the top-level `instructions` field. SSE events are `response.output_text.delta` / `response.completed` / `response.failed`; `response.completed` with `incomplete_details.reason === 'max_output_tokens'` → `finishReason 'length'`. Sends `max_output_tokens` (not `max_tokens`).
- **`anthropic`** → `anthropicStream` (`/v1/messages`): `buildAnthropicMessages(msg, history)` drops system messages from the turn array (system is the top-level `system` field, returned separately) and converts `data:` image URLs into `{type:'image', source:{type:'base64', media_type, data}}` blocks — Anthropic can't consume OpenAI's data: `image_url` passthrough, so non-data URLs are skipped. History `image_url` parts are also converted when they carry a data URL; compacted/history parts without one are skipped. SSE events are `content_block_delta`/`text_delta`, `message_delta` (`delta.stop_reason === 'max_tokens'` → `finishReason 'length'`), `message_stop` (ends the read loop), `error`. **`max_tokens` is always sent** — Anthropic 400s without it, so `DEFAULT_MAX_TOKENS` (16384) is the fallback when the provider leaves it unset.

`ping()` (`lib/llm-client.js`) is apiStyle-aware: with a configured model it sends a real 1-token request to the matching endpoint (`/v1/chat/completions` / `/v1/responses` with `max_output_tokens:1` / `/v1/messages` with `max_tokens:1`), since `/v1/models` lists are unreliable. The options-page provider cards no longer expose **Temperature / Max tokens** fields (users never set them — the user-facing UI is compact; storage fields remain and `resolveInferenceParams`/per-stream defaults still govern). Provider display (`prettyProviderName`/`displayProviderName`) prefers the user-set `alias` and falls back to a readable internal name (`hermes` → 'Hermes').

SUBCHAT (`lib/handlers/subchat-handler.js`) also respects `apiStyle` — it always uses `chatStream`/`responsesStream`/`anthropicStream` (never `runsApiStream`, per the detail-thread rules) and splits the system prompt into `instructions`/`system` for responses/anthropic.

Tests: `test/llm-client-responses.test.mjs` (responsesStream SSE parse incl. truncation→`length`, failed event, non-ok, abort), `test/llm-client-anthropic.test.mjs` (anthropicStream SSE parse, required max_tokens, truncation→`length`, message_stop ends loop, error), `test/chat-handler-internals.test.mjs` (`buildResponsesInput`/`buildAnthropicMessages` incl. image→base64 conversion and system-drop), `test/options-provider-ping.test.mjs` (apiStyle-aware ping endpoints, reserved empty slot commits on Save, **Add Provider** appends a card with alias + protocol select + delete, no Temperature/Max tokens fields, deleting the active provider falls back to Hermes).

### Chat output length budget + truncation detection (v0.31.8)

**Room for a real user bug**: browsa used to send NO `max_tokens` on chat requests (`provider.maxTokens` 0/unset was "not sent"), so the server's model default output cap silently cut long replies in half — the user had to keep saying 「继续」 with no indication anything was wrong (same root cause class as the ASR `max_output_tokens` issue, applied to chat output). Two layers fixed in v0.31.8:

- **Default budget + auto-negotiation (2026-08-30)**: `resolveInferenceParams` (`lib/handlers/provider-resolver.js`) falls back to `DEFAULT_MAX_TOKENS` (now **32768**) when `provider.maxTokens` is unset/0. Servers that clamp (Ark) benefit silently; servers that REJECT an over-cap budget with a 400 (OpenAI/Anthropic) are handled by `renegotiateOutputCap` (llm-client.js, wired into chatStream/responsesStream/anthropicStream): `parseOutputCapFromError` extracts the real cap from the error text ("supports at most 16384" / "max_tokens: 100000 > 8192"), the request is retried ONCE with that cap (unparseable-but-mentions-max_tokens falls back to 16384; unrelated errors propagate untouched). A raw `Max output tokens` input lived on the provider card for one day (2026-08-29) and was removed — the user's reaction was 「其实我也不知道该设什么值」: a knob requiring per-model knowledge is a design bug; auto-negotiation + the auto-continuation below replace it. The storage-level `provider.maxTokens` override still works for anyone who set it before.
- **Auto-continuation (2026-08-29)**: when `finish_reason === 'length'`, `handleChat` runs ONE silent continuation pass before persisting — model sees its own partial + an anti-repetition continue instruction, deltas swallowed (`doStream({silent:true})`), `fullReply = v1 + 续写`, usage summed, `replyTruncated` re-derived from the continuation leg. Same silent-second-pass contract as the timestamp rewrite that follows it (continuation runs FIRST so the rewrite operates on the merged text; stream-state acc is reset before and set to the merged text after, for tab-switch PEEK). Hermes runs-path mirrors it via `runsInput`/`runsConvHistory`. One hop only — if the continuation also hits the cap, `outputTruncated` still rides DONE and the sidepanel shows the toast + a one-click `appendMsgAction` `→ 继续生成` button (sends 「继续」 as a normal turn). Why not just raise `DEFAULT_MAX_TOKENS` instead: OpenAI errors (400) when `max_tokens` exceeds the model's output cap (e.g. gpt-4o 16384), so a blanket raise trades silent truncation for hard errors on other providers; per-provider maxTokens + auto-continue covers both.
- **Detection + hint**: `parseSseEvent` now captures `choices[0].finish_reason` (last non-null wins — previously discarded), `chatStream` returns `{ full, usage, finishReason }`, `handleChat` sets `replyTruncated = finishReason === 'length'` (also from the silent timestamp-rewrite's second pass), and the DONE chunk carries `outputTruncated: true` → `sidepanel.js`'s DONE branch shows a non-blocking toast 「回复已达模型输出长度上限，可回复『继续』续写」. SUBCHAT mirrors it: `SUBCHAT_DONE` gets `truncated: true` → `detail-thread.js` toast. **Test gotcha**: `test/subchat.test.mjs` static-regEx-matches the exact `pushSubChatChunk(subId, { type: 'SUBCHAT_DONE', subId })` source line — adding the `...(…)` spread requires updating that regex in lockstep (the regex escapes `(`, `{`, `.`/`?` as needed).

### Large-context latency: context aging + Anthropic prompt caching + rewrite-pass trimming (2026-09-06)

Measured on the user's self-hosted Hermes (`/v1/runs`, qwen3.8-flash via Alibaba token-plan MaaS): a 79.5K-token context cost 16.2s cold / 7.0s warm TTFT, with a ~23.4K-token Hermes system prompt+tools riding EVERY prefill and the provider's implicit prefix cache being both 5-minute-TTL and non-guaranteed. Four browsa-side changes came out of that audit (server-side levers — `platform_toolsets.api_server` slimming, per-model `agent.reasoning_overrides` — live in the user's `~/.hermes/config.yaml`, not this repo):

- **Context aging — REMOVED (2026-10-14 KV-cache ruling, 用户死命令「缓存率必须保证」)**: `ageStaleAttachments` and its send-time cold-attach stubbing are deleted (`sendHistory = history` verbatim in handleChat). Mechanism (not a guess): provider prefix caches hit only on byte-identical prefixes; ANY mid-history rewrite — one stubbed attach, one label-compacted image — invalidates the cached state for the WHOLE suffix after it (later text included), so the aging/label-compaction token savings were bought with systematically low cache-hit rates (DeepSeek cache-hit ~1/10 pricing, Anthropic 0.1x, OpenAI 0.5x — resending verbatim bytes is cheaper than the re-prefill each rewrite caused). Regression floor: `test/lib-message-builder-aging.test.mjs` pins verbatim riding AND the cache invariant itself (every turn-N request message is byte-identical to the same-index message of turn N+1). Remaining rewrites are ONE-TIME and deterministic, never per-turn: `stubOversizedAttachments` (context-overflow self-rescue) and `boundUnseenImageBytes` (8MB storage-thumbnail budget). See ADR-0013 amendment.
- **Anthropic prompt caching** (`withAnthropicCacheControl` in `lib/llm-client.js`, wired into `anthropicStream`): Anthropic caches NOTHING without explicit `cache_control` breakpoints — unlike OpenAI-style implicit prefix caching — so anthropic-style providers were paying full prefill every turn. Two `ephemeral` breakpoints are now always sent: the system prompt (converted to a one-block array) and the LAST message (string content converted to a single text block; array content gets the breakpoint on its last block — image blocks accept it). Whitespace-only last-message content is left untouched (empty text blocks 400). Harmless under the ~1K-token cacheable minimum (no entry written, nothing billed). Gateways proxying /v1/messages (LiteLLM/OpenRouter) pass the field through.
- **Rewrite-pass trimming** (`buildTimestampRewriteHistory(history, videoSrc, userText, assistantReply)` in `chat-handler.js`): the auto timestamp-rewrite second pass used to resend the ENTIRE conversation a second time (up to ~2× wall time on big video-notes turns). It now sends only the videoSrc-stamped attach entry + the current user turn + the v1 reply — built from the RAW history (not the aged copy) so an aged transcript is still available to derive times from; falls back to the full history when the entry is missing (trimmed from the front by storage caps).
- **Continuation/rewrite rebuild for every apiStyle — real bug fixed in passing**: the auto-continuation and timestamp-rewrite branches used to rebuild ONLY the chat-style `messages` variable; for `apiStyle: 'responses'`/`'anthropic'` the `responsesInput`/`anthropicMessages` were never rebuilt, so a triggered second pass silently RESENT THE ORIGINAL REQUEST (regenerating the same reply instead of continuing/reformatting it). All styles now rebuild their own input shape (test-locked via source-regex in `chat-handler-internals.test.mjs`).
- **Waiting indicator** (sidepanel.js, `startWaitingIndicator`/`stopWaitingIndicator` next to `showToolProgress`): between send and the first CHUNK/TOOL_PROGRESS/reasoning event the background pushes NOTHING (measured: Hermes emits `reasoning.available` only at step end), so big-context turns showed a silent blinking cursor for the whole prefill+thinking window. A 1s tick renders 「思考中… Ns」 (`waitThinking` i18n key, en/zh) in the same pre-bubble slot `.tool-progress` uses (`.wait-indicator` shares its CSS); started once inside `wireChatStreamPort` (covers onSend AND resume), stopped on the first real event, in DONE/ERROR, the cancel path, and as a catch-all in `setStreamingUI(false)`.

### Hermes inline images in conversation history (`buildRunsConversationHistory`)

`handleChat` (`lib/handlers/chat-handler.js`) splits on `provider.isHermes`: Hermes providers go through `runsApiStream` -> `/v1/runs` (richer: approval/clarification/tool/thinking events), everyone else through `chatStream` -> `/v1/chat/completions`. The two paths handle history images differently, and this was a real bug:

- **Non-Hermes** (`/v1/chat/completions`): `buildMessages` (`lib/message-builder.js`) pushes history entries through **unchanged**, so `image_url` vision blocks (XHS images, PDF figures, screenshots, pasted images) reach the provider every turn. Inline images always worked here.
- **Hermes** (`/v1/runs`): history is sent as a separate `conversation_history` field. It used to be **flattened to text-only** - every `image_url` block was dropped, so attached page images never reached Hermes at all (only same-turn pasted images in `input` survived, and only for one turn). This was the "Hermes's text-only flattening" referenced elsewhere in this file.

`buildRunsConversationHistory(history)` (exported pure helper, extracted for testability - `handleChat` itself needs a heavier chrome.storage mock than the suite provides) replaces that flatten. It converts each history entry's content into the `/v1/runs` part schema: `text`/`input_text` -> `input_text`, and `image_url` -> `input_image` (accepting both the OpenAI `{image_url:{url}}` shape browsa stores and the bare-string `{image_url:'...'}` shape `/v1/responses` uses). Image-only turns are **kept** (not dropped, not replaced with a placeholder); empty turns are dropped. The result is `[{role, content: string | [input_text/input_image...]}]`.

**Verified against a live Hermes endpoint** (a private self-hosted instance; the default `baseUrl` in `lib/storage.js` is now empty so the URL ships nowhere): with a vision-capable model, inline images are read natively on all three endpoints - `/v1/runs` `input`, `/v1/chat/completions` `messages`, and `/v1/responses` `input` (a solid-color image was correctly identified as red/blue, and a bar-count image was counted correctly for small counts). `conversation_history` images (history) are also read natively. **History note**: an earlier server config pointed the `vision_analyze` tool at a text-only model, which made current-turn `input` images fail ("my active model doesn't support image input" / "vision analysis failed (Model only support text input)") while `conversation_history` images still worked (native tokens bypass the tool) - that asymmetry is now resolved by switching the server to a vision-capable model. If `input` images ever fail again with that message, the fix is server-side (the model), not browsa.

`buildHermesTurn(msg, history)` (exported pure helper, extracted for testability alongside `buildRunsConversationHistory`) builds the current turn: pasted images (`msg.images`) go directly into `input` as `input_image` parts alongside the text (a structured `[{role:'user', content:[input_text, input_image...]}]`), and `conversation_history` is just the built prior history (via `buildRunsConversationHistory`). The real text+images turn is persisted to history after the turn, so the NEXT turn's `buildRunsConversationHistory` carries it normally. (An earlier version routed pasted images into a synthetic trailing `conversation_history` turn to work around the broken `vision_analyze` tool described above - no longer needed now that the server runs a vision-capable model, and that split was less semantically correct than keeping text+images together.) Non-Hermes `/v1/chat/completions` passes `image_url` blocks through unchanged via `buildMessages`, so `buildHermesTurn` is Hermes-only.

### Per-model reasoning levels (`lib/reasoning-levels.js`, 2026-09-23)

**Do not confuse with llm-client's `thinking: 'inline'|'omit'`** — that is the DISPLAY policy for reasoning traces (ADR-0004); this is the reasoning EFFORT knob (how deep the model thinks) and is a request-body concern. Every vendor spells the knob differently AND uses a different value vocabulary (GLM/Kimi-class = {关, 开} toggle; Claude/GLM-x = {low, high, max}; GPT-5-class = {none … max}).

**Technique ported from ZCode's built-in provider registry** (github.com/zai-org/ZCode, `config/provider/zcode-builtin.json` — audited 2026-09-23; per **ADR-0003** this is a portable TECHNIQUE): TWO orthogonal rule tables keyed on the model id — (1) per-model **level vocabulary**, (2) (model × api-dialect) **wire maps** — so filling in a model id adapts both the picker and the request fields with zero further config. ZCode compiles maps from expression strings (`compileModelOptionMaps`); browsa's port uses plain JS functions (same semantics, no eval) and keeps family rules only (their registry tracks patch-version churn).

- **Engine (pure)**: `reasoningSpecFor(modelId)` (LAST matching rule wins; no catch-all — unknown models are INERT), `reasoningLevelOptions`, `resolveReasoningLevel` (precedence `provider.reasoningByModel[model]` → `provider.reasoningDefault` → `'auto'`; a pick outside the model's vocabulary degrades to `'auto'` — a stale card default must never send a level the model doesn't speak), `reasoningFieldsFor({provider, modelId, apiStyle})` (`'auto'` → `null` = send NOTHING — picking a level is opt-in), `parseReasoningRaw` (`provider.reasoningRaw` JSON merges LAST: the escape hatch for vendors the registry misses).
- **Dialect maps**: `responses` → `{reasoning:{effort}}`; `anthropic` → toggle-class `{thinking:{type}}`, effort-class `{thinking:{type:'adaptive'}, output_config:{effort}}` (current Anthropic effort API); `chat` → family-specific (`enable_thinking` for Qwen-class, `thinking.type + reasoning_effort` for DeepSeek-class, `reasoning_effort` for GPT-class) with a multi-shape default for unknown-but-vocab'd families (OpenAI-derived gateways ignore unknown body fields — strict backends should use `reasoningRaw` or stay on 'auto').
- **Wiring**: `llm-client`'s three stateless `buildRequest`s take `reasoning` and spread it at body top level (`chatStream`/`responsesStream`/`anthropicStream` thread it); `chat-handler` and `subchat-handler` pass `reasoning: reasoningFieldsFor({provider, modelId: resolveChatModel(...), apiStyle})` inside `dispatchStyleStream`'s `common`. Agent providers never send it (agents run their own inference config). `thinking: 'inline'` display wiring is unchanged — a longer reasoning run simply shows in the existing collapsible.
- **UI**: the LLM card (options) gains a 思考档位 select (`data-k="reasoningDefault"`, generic readCard/saveCard persistence) whose OPTIONS follow the card's model ids (`glm-5` → {关,开}; `gpt-5.6` → the effort ladder) and refresh live as model chips change — plus a `reasoningRaw` JSON input. Level labels render as raw tokens (protocol vocabulary).
- **Tests**: `test/lib-reasoning-levels.test.mjs` — vocabulary-follows-id, precedence + stale-pick downgrade, per-dialect field shapes (qwen `enable_thinking` / glm `thinking.type` / gpt `reasoning.effort` / claude adaptive+effort / deepseek combined), auto/unknown = null, raw merge + invalid-raw ignore.

### System prompt economics (CAPABILITY_HINTS, 2026-09-15; full pool every turn 2026-10-20)

Every CHAT turn sends `effectiveSystemPrompt` = user systemPrompt + reply-language line + the full `CAPABILITY_HINTS` + `CHOICE_REQUEST_HINT`; SUBCHAT sends the same full pool (no choice hint). `CAPABILITY_HINTS_ENTRIES` is the single text source; `SHARED_RENDER_RULES` (the same entries minus the chat-only file clause) is reused verbatim by `AGENT_RENDER_HINT` on the first agent turn. **2026-10-20 ruling: the same-day per-family gate was reverted** — dropping the contract to a 1,647-char base on casual turns removed the visual routing guidance and the model stopped drawing unless explicitly asked; the worker now passes the full `CAPABILITY_HINTS` (≈9.4K with the presentation/source-figure rules) to both handlers, and `/prompt` lists that block verbatim. The negative "Err on the side of NOT drawing" rule was deleted; two positive rules were added: `RICH_MARKDOWN_RULE` (default rich Markdown: headings/bold/inline code/lists/tables/blockquotes/language-tagged code fences; short replies may stay plain) and `FIGURE_PROACTIVITY_RULE` (proactively include a fenced figure when the content is inherently structural). **2026-10-21 user report「文档里的图片引用不上了」→ `SOURCE_FIGURE_RULE`**：主动配图与「引用随附的 [图N]」竞争，真机 A/B（同一篇文章 + 两张图）显示没有这条时模型自己画 mermaid、`[图N]` 命中 0；加上后同一问题产出 4–6 个 `[图N]` 引用、0 个自绘图，而无附件的问题仍产出 2 个围栏图。规则：**源材料已带编号图就优先用同款 `[图N]` 引用原图，源里没有可用图或自己的图能补充新信息时才生成新围栏**；勿删（这是「引用文档图片」行为的唯一显式契约）。 The 2026-09-15 compression still stands: every constraint is load-bearing (each paid for with a real rendering bug), so never "clean up" a hint's why-clause or example without checking its AGENTS.md history. Hard rules when touching the array: (1) **keep the pool static per turn** — it now rides as one byte-stable prefix; never inject per-turn content into it (the removed per-turn llms.txt fetch is the same anti-pattern); do not reintroduce keyword/family gating without a new user decision; (2) hint-less degradation is graceful (the client renders fences natively with or without hints), so the fix for a missed format is a better hint, not runtime detection. Deliberately NOT built: per-session hint layering (a fixed specialist pack per session) and per-family gating — both trade behavior for token savings the user rejected. Hermes runs receive the full hints every turn (`instructions`); agent providers get the full `AGENT_RENDER_HINT` on their first turn only (their server-side transcript retains it).

## Provider 接入

### opencode agent provider (`opencode serve` 直连， 2026-09-06)

Second built-in fixed agent provider (`opencode` in `storage.js` DEFAULTS, `isOpencode: true`, card alias "OpenCode Agent") connecting browsa to the [opencode](https://opencode.ai) CLI agent via its **first-party headless HTTP server** — the same architecture class as Hermes (`/v1/runs`): the agent IS the server, every UI is a client. Protocol client: `lib/opencode-client.js`. All wire facts below were verified live against opencode 1.18.29 by running `opencode serve --port 4096` with a mock OpenAI-compatible provider (`dev-preview/opencode-mock.mjs` + `dev-preview/opencode-e2e.mjs` replay the whole verification, streaming turn + permission round trip included); the authoritative contract is the OpenAPI spec the server itself serves at `GET /doc` (162 paths).

- **Port**: bare `opencode serve` picks a RANDOM port (shown in the startup banner) and a NEW one on every restart — browsa accepts any address, so a user may just type the current port into the Base URL, but the saved URL goes stale each restart; `--port 4096` is the set-and-forget recommendation, not a requirement (the card's baseUrl ships EMPTY, same as Hermes — the recommended address lives in the options placeholder; a default pointing at a server that isn't running would look configured while dead). Server auth is opt-in server-side (`OPENCODE_SERVER_PASSWORD`); browsa sends `Authorization: Bearer <apiKey>` only when the card's API key is set.
- **Send**: `POST /api/session/{id}/prompt {prompt:{text}}` returns immediately (`delivery:'steer'`); the turn then streams as events. `buildOpencodeTurn(msg, history)` mirrors the squilla rule — send ONLY the user's turn (+ the trailing run of `PAGE_CONTEXT_PREFIX` attach turns, joined across interleaved text parts, with the "answer from this, don't refetch" directive); the server keeps its own per-session transcript, so full-history resend would fight the agent's context management. **Images ARE forwarded (2026-09-08, reversing the v1 stance after a live probe)**: the prompt body is `{prompt:{text, files?}}` and `files: [{uri}]` accepts `data:` image URLs — verified live against real `opencode serve` 1.18.29: the attachment reaches the provider as a native `image_url` part and the server derives `mime` from the data URI itself. The OpenAPI `/doc` spec is MISLEADING here (its requestBody `$ref` resolves to a bare `PromptInput`; the real body wraps it in a `prompt` key — found via the 400 `Missing key at ["prompt"]`). Caps/shape come from `buildAgentTurn`'s `.images` + `withTurnImages` (see lib/agent-turn.js — the shared fixed-agent-provider layer; opencode-client.js stays opencode-only and its `buildOpencodeTurn` is a thin wrapper over `buildAgentTurn`); `opencodeFileAttachments` re-filters shape-strict because ONE malformed attachment uri poisons the WHOLE turn server-side (`finish:error` `OpenAI Chat media must contain valid base64`, never reaching the provider). Continuation/rewrite legs null the images (the server transcript already holds leg 1). **Render hints (2026-09-13)**: opencode never sees CAPABILITY_HINTS — `withAgentRenderHints` (lib/agent-turn.js) appends a compact fence-vocabulary block (mermaid/echarts/markmap/smiles/pdb + never-invent-PDB-IDs) to the FIRST turn of a session only; the server transcript carries it onward.
- **Event stream gotchas (each one cost real debugging time)**: (1) text deltas (`session.next.text.delta`) flow ONLY on the GLOBAL streams (`GET /api/event`); the per-session stream `GET /api/session/{id}/event` is lifecycle-only — it first REPLAYS the session's durable history (event-sourced, `durable.seq`) then tails live events. (2) The spec lists `session.idle`/`message.updated` but 1.18.29 never emits them — **turn completion is observed by polling `GET /api/session/active`** (returns `{data:{<sesId>:{type:'running'}}}` while busy, `{}` when idle; the session disappears exactly when the turn ends, verified with interrupt too). `opencodeStream` runs the SSE reader and a poll loop concurrently; disappearance only counts after the session was seen busy at least once (the POST reply races the worker marking it active), followed by a 250ms drain before the SSE is cut so buffered tail deltas reach the live bubble.
- **Final content/usage**: `GET /api/session/{id}/message` is ordered **NEWEST-FIRST**, and one turn spans SEVERAL assistant messages (a textless tool-call leg + the text leg) — "last assistant in the array" returns the wrong text (real e2e bug caught live: turn 2 returned turn 1's reply). `fetchFinalMessage` picks max `time.created` and sums `tokens.{input,output}` over assistant legs newer than the newest user message (the turn's own usage; mapped to browsa's `{prompt_tokens, completion_tokens}`).
- **Approvals/clarifications**: `permission.v2.asked` → browsa's APPROVAL card (`tool`=action, `command`=resources joined, choices `once/always/deny`) → `POST …/permission/{reqID}/reply {reply:'once'|'always'|'reject'}` (deny→reject mapping in background.js's APPROVAL_RESPOND). `question.v2.asked` → CLARIFY card; browsa's free-text response rides as `{answers:[[response]]}` (opencode's QuestionInfo has a `custom` answer path). Note: opencode's DEFAULT permission config auto-allows bash — the card only appears when the user's opencode config sets `permission.bash = 'ask'` etc.
- **Cancel**: outer signal abort → fire-and-forget `POST /api/session/{id}/interrupt` (else the agent keeps running headless), then AbortError. The server emits `session.next.step.failed` with `error.message = 'Provider turn interrupted'` — browsa doesn't parse it (client-side abort semantics own the UX). On `session.error` events the stream client throws with the server's message; note `session.error` must also END the poll loop or the client hangs when active never clears.
- **Session identity**: server-assigned `ses_…` id, stored in `chrome.storage.session` as `opencodeSessionId_<provider>` (survives SW restarts mid-conversation), created lazily on the first turn of a browser session, cleared in the history-clear path alongside Hermes session-id resets. Subchat keeps its own per-thread in-memory session map (SW restart = fresh side session, same degradation rule as squilla). Auto-continuation and the timestamp-rewrite second pass work by sending a bare instruction prompt into the SAME server session (its transcript already holds v1) — no history rebuild needed.
- **Known tradeoff**: handleChat's transient-error retry loop (MAX_RETRIES=2) re-invokes `opencodeStream`, which re-submits the prompt — a flaky connection can make the agent process a turn twice (same tradeoff the Hermes runs path already carries).
- **Testing**: `test/opencode-client.test.mjs` (13 cases) drives the real client through a scripted `globalThis.fetch` — SSE via locally-constructed `ReadableStream` Responses, active-poll scripts, endpoint/body assertions. **Two harness lessons**: (1) aborting the fetch signal does NOT terminate reads on a locally-constructed Response body (unlike a real network stream) — the SSE reader must race `reader.read()` against its own abort promise or the client hangs forever in tests; (2) a conditional template literal nested three levels deep inside options.js's card `innerHTML` template made V8 bail with "missing ) after argument list" (while `node --check options.js` passed — it parses .js as CJS-first and silently reports OK) — precompute such fragments into variables; verify with `cp options.js /tmp/x.mjs && node --check /tmp/x.mjs`. `test/options-provider-ping.test.mjs` expectations updated for the second fixed agent card.

### OpenSquilla agent provider (`isSquilla` + `lib/squilla-client.js`)

**OpenSquilla is a fixed agent provider** (`DEFAULTS.providers.squilla`, type:'agent', isSquilla:true, alias:'OpenSquilla', non-deletable like `hermes`; no Model ID, no apiStyle). Its backend is a local desktop agent whose gateway speaks a JSON frame protocol over **one WebSocket per turn** (`ws://127.0.0.1:18791/ws`): `connect.challenge` → client `connect` req (`minProtocol`/`maxProtocol`, optional `auth:{token}`) → dedicated `hello-ok` frame (NOT a `res`) → `sessions.messages.subscribe` → `sessions.send` (`key`, `message`, `clientRequestId`, `_source:{caller_kind:'cli', channel_kind:'cli'}`, optional `attachments`) → `session.event.*` → terminal. Transport lives entirely in `lib/squilla-client.js` (`squillaStream`/`createSquillaSession`/`uploadSquillaFile`/`pingSquilla`/`normalizeSquillaUrl`). **Lineage**: 2026-08-31 integration (9eaaf0a) → removed 2026-09-03 (4eda6c9, upstream origin-guard PR unmerged) → restored 2026-09-23 (upstream merged; v0.5.5 accepts exactly-listed `chrome-extension://` origins on loopback).

One connection per turn is deliberate: the MV3 service worker sleeps between turns, so nothing may outlive a chat turn. The gateway disconnects clients idle for 120s, so `squillaStream` pings `agent.identity.get` every 30s during a turn. Events are filtered by `task_id` (from the send res) so a stale task still streaming in the same session can't pollute the turn.

- **Turn build/dispatch**: the `squilla` kind lives in `turn-request.js` — `prepare()` = get-or-create the gateway session (`createSquillaSession` + persist `storage.setSquillaSessionKey`) → `buildSquillaTurn(msg, langInstruction(all.replyLanguage), sendHistory)` (`lib/message-builder.js`) → the 60k file-channel fallback below; `doStream`'s `kind === 'squilla'` branch calls `squillaStream`. The gateway keeps its own transcript per sessionKey — browsa never re-sends chat history or a system prompt. **Page context is the exception**: the trailing run of page-context turns in local history forwards ONCE (consecutive attaches before a question forward together) with an explicit "content is attached, don't re-fetch the URL" directive. **Interleaved entries must forward ALL text segments** (real bug, 2026-09-01: taking only the first text part shipped "title + figure-1 caption" of a 369k-char page). Figure images ride as base64 `attachments` (data: URLs only; cap 5MB/张、总数 10; http images skipped). Continuation/timestamp-rewrite legs just swap in the bare instruction (`turn.continueWith`/`turn.rewriteWith`) and drop attachments (the agent's transcript already holds them — resending duplicates; same rule as opencode/bridge images).
- **Turns go through `sessions.send`, never `chat.send`** (real bug, 2026-09-01, gateway 0.5.4): `chat.send` ignores `_source` and its input-normalization guard rewrites a web caller's large text into a PREVIEW_ONLY attachment (a ~40-char note reaches the model — symptom "attach 没传到 / agent 自己 fetch URL"). `sessions.send` honors `_source` (`caller_kind:'cli'` passes verbatim). It requires an existing session and rejects client-chosen keys, so the flow is `sessions.create {agentId:'main', kind:'webchat'}` (gateway assigns `agent:main:webchat:<8hex>`) → `sessions.send`; abort stays on `chat.abort {sessionKey}`.
- **Session kind is `webchat`, not `cli` (2026-10-07 跨入口接力 completion)**: the OpenSquilla app's sidebar deliberately HIDES cli-surface chats (webui `sidebarFamilyForSession` drops surface cli/tui/mcp/subagent — "hide non-Web chat surfaces"), so the original `agent:main:cli:*` keys were invisible in the agent UI and browsa conversations could never be picked up there. A webchat key classifies as a normal app chat (live-verified against a source-built 0.5.6 gateway: sessions.list row carries `surface=webchat, sessionKind=chat`, `capabilities.open:true`) and shows under whatever `sessions.rename` named it. **The large-input admission policy reads the SEND-TIME `_source` hints, not the session key** (`admission_input.py` — caller/channel come off each send, defaulting to web only when hints are absent): browsa still sends `_source:{caller_kind:'cli', channel_kind:'cli'}` into webchat sessions, and a 30,086-char inline message passed with `message_len=30086, attachments_count=0` (live gateway log) — the 0.5.4 preview-only trap does NOT re-arm. **The detail thread (subchat) passes `kind:'cli'` explicitly** — throwaway 追问 threads must not clutter the sidebar. Sessions created before this change keep their cli keys (still fully functional from browsa; only invisible in the app). Combined with `renameSquillaSession` (session-naming bullet above) this is the full codex/claude/pi-parity handoff: the conversation appears in the OpenSquilla sidebar as 「browsa：<title>」 and continues there through the app's own turn runner.
- **60k file-channel fallback** (0.35.9): inline context over `SQUILLA_INLINE_CONTEXT_CAP = 60_000` chars dies with `LargeContextCapacityError` at the prompt assembler (the routed model's window can't hold hundreds of KB) — `uploadSquillaFile` (POST `/api/v1/files/upload`, multipart `file`) uploads `page-context.md` and the message becomes "read the attachment first, then answer".
- **Image degradation** (0.35.8, inside `squillaStream`): a turn that carried attachments and failed with ZERO deltas retries once WITHOUT them. The trigger is deliberately "no delta yet", not the error string (terminal events carry no reason — string matching missed cases in the field); the degradation is intentionally silent (user preference — the router frequently picks text-only models).
- **attach-summarizer skips squilla** — the shared agent guard (`provider?.isOpencode || provider?.isBridge || provider?.isSquilla` in `maybeSummarizeAttachment`): the full attachment goes inline, condensing would only degrade the agent's view, and the summarizer's chatStream can't reach a ws:// baseUrl (it used to fire one failed fetch per 12k chunk).
- **subchat has a squilla branch**: detail threads use `squillaStream` with a DEDICATED gateway session per subId (in-memory `subchatSessionKeys` map — same isolation rule as keeping subchat off the Hermes runs path; a SW restart mid-thread just starts a fresh session). Multi-turn threads serialize into one message with `[用户]/[助手]` markers; `withAgentRenderHints` rides the FIRST turn (parity with opencode/bridge — the hint postdates the original integration); capabilityHints are never forwarded (no system-prompt channel).
- **Terminal events**: `session.event.done`, `task.succeeded/failed/cancelled`, or `sessions.changed` with reason `task_terminal/task_failed/task_cancelled` (matching `last_task.task_id`). **Upstream bug (0.5.4, reported)**: after `chat.abort` the turn's async cleanup crashed (ContextVar reset across asyncio Contexts) and NO terminal event is emitted — `squillaStream` therefore treats abort as terminal client-side (the signal listener sends `chat.abort` over the still-open socket — closing the WS alone does NOT stop the server-side task — then throws AbortError). **Abort contract** is the same as chatStream/runsApiStream: signal abort must throw AbortError even with partial text or chat-handler persists a phantom turn. Known cosmetic gap: the gateway's tool-context logs `caller_kind=WEB` for these turns (server-side attribution is separate from the send-source hint; tools run fine).
- **Pasted images are NOT forwarded** (`msg.images` stays browsa-side — the attachment contract covers rendered page figures only). `buildSquillaTurn`'s trailing-page-context walk intentionally parallels `agent-turn.js`'s `buildAgentTurn` but keeps its own image policy — do not merge the walks without revisiting both contracts (noted at the definition).
- **Delivery-directive stripping (2026-10-07, inside `squillaStream`)**: OpenSquilla models embed channel-routing directives (`[[reply_to_current]]` / `[[reply_to: <target>]]`) in the reply text; the gateway strips them only on its app-delivery path (`channel_dispatch._strip_inline_directive_tags`), so the `session.event.text_delta` stream browsa subscribes to carries the RAW model text — a browsa reply opened with a literal `[[reply_to_current]]` line (field report). Upstream handles the same leak CLIENT-side (webui `stripDirectiveTags`; TUI `StreamDirectiveFilter`), and `createSquillaDirectiveFilter` (exported, in squilla-client.js) ports the TUI's streaming semantics exactly: tag + one trailing whitespace/newline disappear, a tag split across deltas is held back (≤96-char plausible prefix) so it never flashes on screen, an unfinished prefix at flush is ordinary text, ordinary bracket text (`arr[[0]]`, `see [1]`) survives byte-for-byte. `full`/onDelta therefore never carry the directive; thinking events bypass the filter (directives live in the answer stream); the filter is re-created per image-retry attempt alongside `full`'s reset. Do NOT "fix" this gateway-side (not our repo) or widen the body match beyond `reply_to_current|reply_to:…` — the tight body is what keeps ordinary `[[…]]` text safe. ## 存储与会话

### History image lifecycle (`lib/handlers/history-compactor.js` + `lib/message-builder.js`)

**Display fidelity is a hard requirement (2026-09-23 user mandate: 气泡里面该有啥就有啥 / 能看到啥就看啥): stored image pixels are NEVER destroyed.** Chat bubbles, the transcript drawer's screenshot cards, and session snapshots keep showing exactly what was sent, forever. Everything that reshapes images for a CONSUMER happens at read/build time (the same request-side philosophy as context aging above) — see **ADR-0013** (this section replaced the earlier destructive "History image compaction" design after a real user report: pasted images vanished from their bubble once history re-rendered).

- **Model side (2026-10-14 KV-cache ruling — supersedes the request-side label compaction)**: `handleChat` still stamps `IMAGE_SEEN_FLAG` (`imagesSeen`) on image-bearing entries at the same WHEN as before (post-answer, folded into the append's locked mutate; a restored snapshot stamps at its first answered turn) — but the flag is now LEGACY BOOKKEEPING only: `prepareHistoryForModel` strips it from request bodies (older stored histories and saved-session snapshots carry it; it must never leak into a request) and does NOTHING else. History — figure pixels included — rides to the model verbatim on every turn; later turns keep seeing figure pixels (the old "labels only" tradeoff is REVERSED), and provider prefix caches stay hit across turns. `compactEntryImageParts`/`parseFigureLabels` survive solely as `boundUnseenImageBytes`'s undecodable-payload fallback (storage-side display). ADR-0005 unchanged.
- **Agent providers need zero change**: `buildAgentTurn` only collects the trailing page-context run (never answered → never flagged), so its image forwarding is naturally identical to the old behavior.
- **Storage side (panel-open hygiene)**: `boundUnseenImageBytes` caps parked pixels at `UNSEEN_IMAGE_BYTES_BUDGET` (8MB) by **downscaling** the oldest image-bearing entries' parts to display thumbnails (`downscaleDataUrl` — service-worker `createImageBitmap` + `OffscreenCanvas`, `THUMB_MAX_EDGE` 480px, opaque-white JPEG) — never to labels: an entry that loses its pixels loses its bubble picture. The newest image-bearing entry is always spared (the attach the user is about to ask about keeps full pixels for the model's first look). Only an undecodable payload falls back to label placeholders. The whole pass is ONE locked async read-modify-write (mutateHistory awaits the mutator); the earlier two-phase "plan victims by URL, rewrite by URL" design was tried and REJECTED — entries sharing one data URL over-matched and non-victims got rewritten (victim choice + rewrite must be atomic against concurrent appends/deletes).
- **Testing**: `test/history-compactor.test.mjs` covers the pure policy (`parseFigureLabels` / `compactEntryImageParts` / `prepareHistoryForModel`, incl. the identity-passthrough + no-flag-leak pins), `markImagesSeenInHistory` (stamp once, pixels untouched, idempotent), `boundUnseenImageBytes` (thumbnail semantics via an injected `downscale`, label fallback on undecodable payloads, newest spared, idempotent), and builder integration (`buildMessages` / `buildAnthropicMessages` / `buildRunsConversationHistory` — seen→labels, unseen→pixels, flag never on the wire). ### Background streams across session switches (2026-09-24)

Switching conversations mid-turn **no longer cancels the reply** (user report: "AI 还在 thinking，一切换就全没了" — a minutes-long reasoning run evaporated on a stray click). The turn keeps running in the service worker and its output lands in the session it STARTED in.

- **Routing rule (the whole design in one line)**: a turn entry is written to the LIVE history only while the panel is watching its stream (`streamState.bg === false`); once the stream is backgrounded it writes to the ORIGIN session's snapshot (`storage.appendToSessionHistory`). `chat-handler.persistTurnEntry(tabId, entry)` is the single writer — `bg` is set/cleared only by explicit messages (REASSIGN after a switch-away auto-save / STREAM_PEEK attach on a switch back), which kills the loadSession-vs-DONE race window (a mis-route can only go to the safe snapshot side).
- **Plumbing**: `initStreamState(tabId, { originSessionId })` stamps the turn's owning session (the sidepanel puts `sessionId` on the CHAT message); `REASSIGN_STREAM_SESSION` backgrounds the stream and re-stamps the origin to the switch-away auto-save's session id (SAVE_SESSION returns the session); `STREAM_PEEK` with `sessionId` re-attaches only when the session IS the origin (else the reply of ANOTHER conversation must never render here — `peek.bg` gates `resumeInFlightStream`).
- **Stop-watching ≠ cancel**: `cancelStream({ detach: true })` (exported as `stopWatchingStream`) does the local teardown (port detach, bubble finalize) WITHOUT `STREAM_ABORT` — the server-side turn continues. Plain `cancelStream()` (Esc / ■) still aborts, and `clearChatHistory` aborts with `salvage: false` (explicit destruction). `pushChunk` drops CHUNK/DONE/ERROR for bg streams (the panel is showing another conversation) but still pushes APPROVAL/CLARIFY — a blocked tool call must not hang the turn.
- **收尸 (interrupted-turn salvage, folded in here)**: an aborted turn with streamed text is persisted as `{ interrupted: true }` into the origin (user Esc / idle timeout / network drop — thinking must not evaporate); `abort('drop')` skips it. This replaced the old "abort = never write history" contract; the AbortError-throw contract on the CLIENTS is unchanged (a resolved-with-partial would still look like a completed turn).
- **UI**: the sessions drawer marks in-flight turns with a `.session-active-dot` (GET_SESSIONS gains `active` from live streams' origins); switching away toasts `streamMovedToBackground`; switching back auto-reattaches rendering. Known limit: `markImagesSeenInHistory` still walks only the live history, so a backgrounded turn's images get flagged one turn late (sends pixels once more — cost only, safe).
- **Tests**: `test/lib-persist-turn-routing.test.mjs` (live vs snapshot vs missing-session fallback, pushChunk bg gating, interrupted shape — `appendToSessionHistory` exercised via the bg route), `test/lib-sessions-ui.test.mjs` (loadSession sends REASSIGN + stop-watching and NEVER STREAM_ABORT).

### Auto-summarize long attachments (`lib/handlers/attach-summarizer.js`)

Ported from auditing BiliNote's chunk-summarize-merge pipeline. A 4-5 hour video's transcript (one `[mm:ss] text` line per caption, per `youtube-content-script.js`/`bilibili-content-script.js`) runs 60-80K+ characters. The real problem this solves: `buildMessages` (`lib/message-builder.js`) resends the **entire history** on every single turn — an oversized attachment isn't a one-time cost, it's resent in full on every message for the rest of the session, and can silently exceed a smaller-context provider's window (browsa's own `maxTextChars` cap defaults to 1,000,000 chars, far above what many self-hosted/local providers can handle).

- **No UI changes needed.** The raw attach text is never rendered in the chat bubble (the UI only shows a small "已附加" chip, driven by `PAGE_CONTEXT_PREFIX` detection, not by rendering `content`) — so replacing the stored entry's `content` after the fact is a pure storage-side enhancement. This is why the whole pipeline can run **fire-and-forget, after** `ATTACH_PAGE` has already responded — no "compressing…" progress UI, no port/stream lifecycle to get wrong.
- **Flow**: `background.js`'s `ATTACH_PAGE` case computes `willSummarize = all.autoSummarizeAttachments !== false && shouldSummarize(ctx.text, all.summarizeThresholdChars)` *before* `appendToHistory`; if true, stamps `historyEntry.attachId = crypto.randomUUID()` (same "extra field on the entry" pattern as `videoSrc`) so the entry can be found again later. After `appendToHistory` and right before the `return`, calls `maybeSummarizeAttachment({ attachId, ctx, provider })` **without awaiting it** — `ATTACH_PAGE`'s response latency is completely unaffected.
- **`maybeSummarizeAttachment`** (`lib/handlers/attach-summarizer.js`) does the real work: `summarizeLongText` splits `ctx.text` via `splitIntoChunks` (greedy, line-respecting — never splits a transcript line in half), runs one `chatStream()` call **per chunk in parallel** (`Promise.all` — chunks are independent, `chatStream` has no shared module-level state), then one final merge `chatStream()` call combining the chunk summaries in order. Each call passes `onDelta: () => {}` (never surfaced to any UI — this isn't tied to any chat turn's port/streamState) and `signal: AbortSignal.timeout(90_000)` (bounds worst case; `AbortSignal.timeout` is already an established pattern here, see `chat-handler.js`'s `fetchLlmsTxt`). Then re-reads `storage.getHistory()` fresh, finds the entry by `attachId`, and replaces just that entry's `content` (rebuilt via `buildPageContextText({...ctx, text: summarized})`, same header format) plus stamps `summarized: true`.
- **Video-mode timestamp preservation is the one place this is genuinely easy to get wrong**: the chunk-summary and merge prompts for `mode === 'youtube' || 'bilibili'` explicitly instruct the model to keep every kept point's original `[mm:ss]` marker exactly (earliest timestamp when merging lines) — never invent/renumber/drop timestamps. Without this constraint, condensing a timestamped transcript would silently break `linkifyTimestamps`/`SEEK_VIDEO`'s clickable-jump feature (wrong or missing anchors). Non-video attachments get a generic "preserve key facts/names/numbers/quotes, drop repetition" prompt instead.
- **Fails open, never corrupts**: `maybeSummarizeAttachment` catches everything (provider not configured → `console.warn` + no-op; network error/timeout; empty result) and simply leaves the original raw entry untouched on any failure — identical to today's pre-existing behavior, never a partial/garbled write. If the entry was removed by the time summarization finishes (user hit 撤销, deleted it via multiselect, or it fell out via `MAX_HISTORY`/`MAX_TOTAL_CHARS` trimming), `history.findIndex` returns `-1` and it's a silent no-op — not an error.
- **Config**: `autoSummarizeAttachments` (default `true`) and `summarizeThresholdChars` (default `0` = use the built-in 100,000-char fallback, same "0 means use default" convention as `maxTextChars`/`textCap`) live in `lib/storage.js` DEFAULTS. There is **no options-page UI for these** — the "Content limits" card was removed (the composer's context-mode selector already covers the user-facing side), so they are effectively hardcoded defaults: always auto-summarize above 100K, cap at 1M (`maxTextChars: 0` → 1M fallback in `extractActiveTab`). The storage keys are kept so tests (which set low thresholds / disable the feature directly in storage) keep working. The threshold was deliberately NOT lowered below 100K when a real overflow incident landed (2026-09-16: an 18-page arXiv PDF, 67.8K chars ≈ 35K tokens, + 9 figures + Hermes's ~23K tokens of tool definitions blew a 64K-class window) — a lower default would silently condense big-window users' verbatim attachments; the send-time self-rescue below owns that failure instead.
- **Context-overflow self-rescue (handleChat's retry loop, 2026-09-16)**: when a send fails with a context-overflow error (`isContextOverflowError` matches the real wordings: Hermes's "conversation has grown too long … couldn't shrink it enough", OpenAI's "maximum context length", Anthropic's "prompt is too long", `context_length_exceeded`, 413s, 输入过长/上下文超过限制), the loop — once per turn — stubs EVERY oversized attach in `sendHistory` via `stubOversizedAttachments` (`lib/message-builder.js`; newest attach included, unlike aging, and multimodal figure blocks DROPPED — they can be ~15K tokens), rebuilds the request shapes (runsConvHistory / messages / responsesInput / anthropicMessages), pushes a TOOL_PROGRESS notice (「附件超出模型上下文窗口，已临时裁剪大附件并自动重试…」), and retries immediately via `attempt--` + continue (does not consume the transient-retry ladder; the rescue flag bounds it to one shot). Storage is rewritten ONLY after the retried turn succeeds — attachId-keyed `storage.mutateHistory`, same atomic pattern as `maybeSummarizeAttachment` — so a still-failing turn never destroys the raw attachment (the user can still retry on a bigger-window model). `summarized: false` entries keep their raw text for re-attach; the stub keeps the `PAGE_CONTEXT_PREFIX` head so the sidepanel's chip-instead-of-bubble rendering is unchanged. opencode/bridge are EXCLUDED (their transcripts live server-side; a smaller resent prompt cannot shrink what the agent already stored — same rationale as their summarizer skip). The persist-after-success design means the FIRST overflowed turn's raw text stays in storage until a rescued turn succeeds; if the rescue cannot help (stubbing still overflows), the original error propagates and the user is told to re-attach / switch models as before. This closes the dead-end where every retry re-sent the identical oversized history and neither Hermes's shrink could intervene (context aging was removed entirely by the 2026-10-14 KV-cache ruling — the rescue is now the ONLY in-request stubbing).
- **`ATTACH_PDF_CONFIRM` (`background.js`) gets the exact same `willSummarize`/`attachId`/`maybeSummarizeAttachment` wiring as `ATTACH_PAGE`** (added after a real gap was found: PDF attachments used to bypass this feature entirely — no threshold check, no attachId stamp — so a 50-100 page PDF's extracted text, comfortably under `pdf-extractor.js`'s own `DEFAULT_MAX_CHARS` = 500K lossy-truncation ceiling but well over the 100K summarize threshold, was stored in full and resent on every turn forever, unlike an equally-sized webpage attachment). The two length caps serve different purposes and neither substitutes for the other: `DEFAULT_MAX_CHARS` is a hard, lossy truncation safety valve against pathological sizes; `summarizeThresholdChars` triggers an LLM-based compression pass that preserves key facts. `pdf` mode uses the generic (non-video) summarize/merge prompts — PDFs have no `[mm:ss]` timestamps to preserve.

## 附加与抽取管线

### Extraction quality improvements (no new UI)

Three backend-only improvements ported from the Python scraping library Scrapling, applied transparently to the existing pipeline (see also the firecrawl-ported improvements further below):

- **Prompt-injection defensive sanitization**: `extractInPageWorld` strips `<template>` elements and HTML comments from the Readability clone before parsing — a page can hide instructions meant for an LLM reader in markup a human never sees, and this removes them before they reach the model. It also marks CSS-hidden elements (`display:none`/`visibility:hidden`/`opacity:0`/`font-size:0`/zero-dimension boxes) on the **live** document before cloning — `getComputedStyle` needs rendering info the detached clone doesn't have — then strips them from the clone via the marker attribute, immediately un-marking the live DOM afterward so the page itself is never left mutated. `NOISE_SELECTORS`'s `[hidden]`/`[aria-hidden="true"]` only catch attribute-based hiding; this closes the stylesheet-driven blind spot (same threat model — a page can hide boilerplate or an actual injection payload from a human reader while still feeding it to the LLM). Only elements carrying non-empty `textContent` are checked, to bound cost and avoid false positives on empty containers awaiting JS hydration. All of `extractInPageWorld`/`extractDomTreeInPageWorld`/`extractFullInPageWorld` also strip zero-width chars (U+200B/200C/200D/2060/FEFF), control characters, and (ported from auditing browser-use's `sanitize_surrogates`) UNPAIRED UTF-16 surrogate code units (U+D800-DFFF) from their final text output — real-world pages sometimes leak broken emoji/symbol encodings as lone surrogate halves, which can break JSON encoding of the request body or get rejected outright by a provider's API. The regex (`/[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]/g`) must be pair-aware — a naive blanket `[\uD800-\uDFFF]` strip would also destroy legitimate emoji/astral characters, which are themselves valid high+low surrogate pairs.
- **Repeated-structure item markers** (`extractDomTreeInPageWorld`): when a container has ≥3 structurally-similar children (same tag + primary class token — e.g. 20 `.product-card` divs, or a `<ul>/<li>` list), walk() inserts `— Item N —` boundary markers before each item, so the LLM can see where one item ends and the next begins rather than receiving a flat interleaved wall of title/price/link fields with no grouping. Only triggers when the similar group makes up ≥60% of the container's visible children, to avoid spurious markers on navigation menus or mixed-content layouts. Concept: `fingerprint(el)` (tag + first class) + `findRepeatedGroup(children)` (Map-based majority grouping) inlined into the self-contained MAIN-world function. Automatically active in auto/dom modes, no user configuration.
- **Site-chrome stripping** (`extractDomTreeInPageWorld`'s nested `isChromeNoise(el)`, applied at walk() entry AND excluded from the `visibleChildren` repeated-group filter): DOM-tree mode used to dump the ENTIRE page — top nav, sidebars, "On this page" TOC, footer, search widget — because it had no noise handling at all (reader mode strips exactly these via `NOISE_SELECTORS`, so the two modes' noise handling is now consistent). Found via a real user report: attaching `pi.dev/docs/latest/settings` via 📎 came back as a 36K-char wall of menu links (the whole site nav + left rail + right TOC + footer, effectively twice — desktop + mobile variants) instead of the article; after the fix it's ~25K chars starting directly at the article body with every chrome section gone. `isChromeNoise` strips (1) `nav`/`header`/`footer`/`aside` tags, (2) `role="navigation"`/`"banner"`/`"contentinfo"`/`"complementary"`/`"search"`, (3) `aria-hidden="true"` (the `hidden` attribute is already covered by `isHidden`), and (4) a `<details>` element whose subtree contains any of the above — the collapsible mobile-nav/TOC disclosures docs sites render as `<details class="docs-mobile-*">` siblings OUTSIDE the `<aside>` rails (pi.dev does exactly this) would otherwise leak bare `Navigation`/`Documentation`/`On this page` labels + the search input even though the `<nav>` they wrap is stripped; a legit FAQ accordion `<details><summary>Q</summary><p>A</p></details>` has no chrome descendant and is untouched. One `querySelector` per `<details>` (details are rare, subtrees small) — bounded cost. `header` is stripped unconditionally to match reader mode (this drops a page's `<h1>` if it lives inside a `<header>`, exactly as reader mode already does — consistency over title preservation; the article body is what matters). The one residual not chased: `<header>`-less pages where the only heading is inside a stripped header are accepted as reader mode's established behavior.
- **`lib/dom-similarity.js`** — pure, Node-testable module: `stringRatio` (Dice-coefficient bigram similarity), `scoreDescriptors` (weighted element descriptor similarity), `cleanText` (zero-width/control char stripping). No longer used by production page-extraction code directly — `_relocateXhsAnchorsInPageWorld` (below) inlines its own copy per the MAIN-world constraint. Kept as the tested reference implementation; if either copy is changed, sync the other.
- **XHS adaptive relocation** (`tryXhsAnchorRelocation`/`_captureXhsAnchorFingerprintsInPageWorld`/`_relocateXhsAnchorsInPageWorld` in `page-extractor.js`): scoped narrowly to XHS's `#detail-title`/`#detail-desc` DOM-anchor fallback path. On every successful DOM-path extraction, saves the anchors' structural fingerprint to `chrome.storage.local`; on a future selector miss (site redesign), attempts structural relocation before falling through to Readability. Not applied to the other 9 sites (they rely on XHR interception). Fully invisible to the user — no UI, no new message types.
- **Same-origin iframe / open shadow-DOM extraction** (idea ported from auditing Alibaba's `page-agent` extension): all three MAIN-world extraction paths used to treat `<iframe>` as pure noise (`NOISE_SELECTORS`/`SKIP`) and never traversed shadow DOM, silently dropping any page content embedded that way. One level of traversal only (no recursion into nested iframes/shadow roots), gated on non-trivial text (>40 chars) and capped at 20 embeds per extraction, to bound cost on pathological pages. Cross-origin iframe access is wrapped in `try/catch` (throws or returns an inaccessible document depending on engine — same-origin policy, expected and unavoidable); closed shadow roots are unreachable by design (`el.shadowRoot` returns `null`). Per-function implementation: `extractDomTreeInPageWorld`'s `walk()` recurses into `el.contentDocument.body` for same-origin iframes and `el.shadowRoot.children` for open shadow hosts (safe unconditionally — `el.textContent` never includes shadow-tree content, so no double-counting). `extractFullInPageWorld` appends captured shadow/iframe `textContent` to its raw text dump. `extractInPageWorld` (Readability path, the default) captures embeds on the **live** document before cloning (same `mark → clone → unmark` pattern as the CSS-hidden pass above, since `cloneNode(true)` doesn't clone shadow trees and can't reach into a live iframe's `contentDocument`), then injects the captured HTML into the clone **before** the `NOISE_SELECTORS` strip — critically, iframe hosts are `replaceWith`'d (not just have content appended into them) since the `<iframe>` tag itself is in `NOISE_SELECTORS` and would otherwise be removed wholesale along with any injected content inside it; shadow-DOM hosts survive that strip so their content is just appended as a child. This ordering means captured content flows through the same noise/template/comment stripping as native page content, preserving the file's prompt-injection defense posture.

Four more improvements ported from auditing firecrawl (a heavy-backend scraping API service) — only the pure/local pieces of its content-cleaning logic apply; its Playwright/queue/remote-LLM infrastructure has no equivalent in a no-backend extension:

- **Turndown GFM plugin** (`turndown-plugin-gfm`, vendored as `lib/vendor/TurndownPluginGfm.iife.js`): plain Turndown collapses `<table>`/`<del>`/task-list checkboxes into unstructured text. `ensureReadabilityInjected` now also injects this plugin (best-effort — a `getVendorSrc(...).catch(() => null)` means a fetch failure here never blocks the *required* Readability/Turndown injection), and `extractInPageWorld` calls `td.use(TurndownPluginGfm.gfm)` only when it's actually present (`typeof TurndownPluginGfm !== 'undefined' && TurndownPluginGfm.gfm`), so extraction still works — just without GFM tables — if injection failed for any reason. **A real regression found while rebuilding `Turndown.iife.js`** to add this: turndown 7.2.4's CJS entry does `module.exports = TurndownService` directly (the constructor itself), not the `{TurndownService: ...}`/`{default: ...}` wrapper shape the old bundle apparently had — the existing `tGlobal.TurndownService || tGlobal.default` resolution silently produced `undefined`. Fixed by adding a final `|| tGlobal` fallback. **Rebuilding this vendor requires `npm install turndown turndown-plugin-gfm --no-save` inside `build/_deps/` first** — `build/_deps/node_modules` is gitignored/ephemeral, and a bare `npm run build` will otherwise skip both (source not found) and leave the committed bundles untouched; installing there is not additive — npm prunes whatever `build/_deps` packages aren't in that install's own dependency list as "extraneous" (same gotcha hit earlier with markmap-lib), so any *other* `_deps`-sourced vendor (marked, DOMPurify) needs reinstalling too if you need to rebuild it later.
- **`postProcessMarkdown(markdown)`** — a markdown-level cleanup pass run after `td.turndown(...)` inside `extractInPageWorld`: strips inline base64 `<img>` data URIs down to a `(<image-removed>)` placeholder (pure token waste — this is plain text sent to the model, not a vision attachment, so the model never "sees" the pixels either way), strips "Skip to Content" a11y anchors (boilerplate on most CMS/framework themes), escapes newlines inside multi-line link text, and (ported from auditing `browser-use`'s `_preprocess_markdown_content`) strips SPA-embedded JSON state/config blobs — LinkedIn/Facebook-style component-driven sites leave large `{"key":"value",...}` blobs sitting in otherwise-readable DOM text, which Readability doesn't recognize as noise since it's real text content, not markup. Three size-gated regex passes (JSON inside a code span, `{"$type":...}` blobs, nested `{"key":{...}}` objects — each requires ≥100 chars so small legitimate inline JSON examples in real article prose survive) plus a per-line `JSON.parse` sanity check before dropping any remaining long line that merely starts with `{`/`[` (a prefix check alone isn't enough since Markdown links/images also start with `[`). **A real test-infra gotcha hit while adding this**: `test/page-extractor.test.mjs`'s `loadSiblingFn` extracts a function's source via naive char-by-char `{`/`}` depth counting, with zero awareness of regex literals, string literals, or comments — a regex like `[^}]{100,}` or a comment containing a lone `'{'` introduces an unmatched brace count that throws `"unbalanced braces"` (or silently truncates the extracted source) even though the actual JS is perfectly valid. Fixed by writing the JSON-blob regexes' structural braces as `\x7B`/`\x7D` hex escapes instead of literal `{`/`}` (only the self-balanced `{100,}`-style quantifiers stay literal), using `charCodeAt(0) === 0x7B/0x5B` instead of `[0] === '{'`/`'['` string comparisons, and avoiding lone brace characters in the surrounding comments — the general lesson: any new regex/string added to a MAIN-world-injected nested function must keep the *raw source text's* brace count balanced, not just be valid JavaScript. **Declared as a function nested inside `extractInPageWorld`, not a module-level sibling** — see the `countImages` note below for why that distinction matters for MAIN-world injection.
- **`NOISE_SELECTORS` additions + `img[srcset]` highest-resolution picking**: two small `extractInPageWorld` tweaks. `NOISE_SELECTORS` gained `.lang-selector`/`.language`/`#language-selector` and `.breadcrumbs`/`#breadcrumbs`. Separately, before the noise strip, `docClone.querySelectorAll('img[srcset]')` picks the highest-resolution candidate (parses each `url descriptor` pair, keeps the max parsed-float score) and rewrites `src` to it — lazy-loaded pages often ship a low-res placeholder in `src` with the real image only reachable via `srcset`, and Turndown converts `<img>` using `src`. `w`/`x` descriptors are never mixed within one `srcset` per spec, so comparing raw floats within one image's own candidate list is safe even though the two descriptor kinds aren't cross-comparable in general.
- **`lib/markdown-chunker.js`** — pure, Node-testable utility module (no chrome/DOM deps) with two exports: `findSafeTruncationPoint(text, cap)` and `splitIntoMarkdownChunks(text, chunkSizeChars)`. Ported from auditing browser-use's `chunk_markdown_by_structure`. `findSafeTruncationPoint` replaces the raw `.slice(0, cap)` calls in `pdf-extractor.js` (two sites: wasm path and pdf.js path) — it scans lines forward tracking fence parity and table-row state, returning the rightmost `\n` position ≤ `cap` that is not inside an open fence block and not on a `|` table row line, falling back to `cap` when no such position exists (degrades gracefully for plain text). `splitIntoMarkdownChunks` replaces the call to `splitIntoChunks` in `attach-summarizer.js`'s `summarizeLongText` — it uses the same line-by-line greedy packing as the original, but pre-collects fenced code blocks (``` or ~~~ delimited) and table runs (consecutive `|` lines) into atomic units that are never split across chunks. Oversized atomic units become their own chunk rather than being dropped (same behavior as `splitIntoChunks` for single overlong lines). When a table overflows into a new chunk, its header+separator rows are prepended to the next chunk so the LLM can read the column names. **Three inline helpers in `page-extractor.js`** (not imported from `markdown-chunker.js` — MAIN-world `chrome.scripting.executeScript` constraint): `findSafeCutPoint` nested in `extractInPageWorld` (full fence+table tracking, same algorithm as the module version, written with `\x60`/`\x7B`/`\x7D` hex escapes and brace-balanced for `loadSiblingFn`), `findDomTreeCutPoint` nested in `extractDomTreeInPageWorld` (scans backward for `— Item ` or `#` heading boundary, falls back to last `\n`), and a short inline `\n\n`/`\n` boundary finder in `extractFullInPageWorld`. `old splitIntoChunks` export in `attach-summarizer.js` is kept (existing unit tests reference it directly).
- **Local re-attach change detection** (`lib/handlers/attach-change-tracker.js`): `checkAndRecordAttachChange(key, text)` hashes (FNV-1a, no crypto needed) the extracted text and compares it against the last snapshot stored under `key` in `chrome.storage.local` (key = `${mode}::${url}`, capped at 50 entries, oldest evicted first — deliberately NOT keyed by URL alone, since reader/dom/full modes naturally yield different text for the same page and would otherwise produce false "changed" signals). Wired into `background.js`'s `ATTACH_PAGE` case right before history is stored, skipped for `selected`/`pdf-url`/`screenshot` modes (a text selection differs every time by design; PDF/screenshot text is a fixed placeholder, not real content) and for near-empty text (<50 chars). When changed, `ctx.changedSinceLastAttach = {previousAttachedAt, previousLength}` flows into `buildPageContextText`, which appends a `Note: this page's content has changed since it was last attached (...)` line to the header — **model-facing only, no new UI chip/badge**, consistent with this section's "no new UI" theme. Unlike firecrawl's `change-tracking-diff.ts` (which stores the full previous markdown and computes a real unified diff), browsa only needs a cheap "did this change at all" boolean, so a hash+length+timestamp per key is sufficient and avoids doubling `chrome.storage.local` usage for every attached page.

**`countImages` — a real, separate production bug found and fixed while adding the above** (unrelated to the firecrawl port itself, but directly adjacent code): it used to be a module-level sibling function that `extractInPageWorld` called directly. `chrome.scripting.executeScript`'s `func` injection only serializes the ONE function it's given (`Function.prototype.toString()` of just that function, re-evaluated in the page's own realm) — a call to a sibling top-level function throws `ReferenceError` in real Chrome the moment Readability actually succeeds. This only ever appeared to work in this file's own tests because the test harness (`runExtractInPageWorldOnLiveDoc` in `test/page-extractor.test.mjs`) manually concatenated both function bodies into one `vm` context — something the real `chrome.scripting.executeScript` call never does. Fixed by nesting `countImages` inside `extractInPageWorld` (same treatment as the new `postProcessMarkdown`), and the test harness was simplified to stop separately concatenating it. **General rule reinforced by this bug**: any helper a MAIN-world-injected function depends on must be declared *inside* that function's own body (or duplicated inline, as the XHS/dom-similarity functions already do) — never as a module-level sibling, no matter how obviously "shared" it looks in the source file.

Two more firecrawl-inspired features, added in a later pass, each with a genuine architectural finding baked into the design:

- **PDF client-side text extraction** (`pdfjs-dist`, vendored as `lib/vendor/pdf.bundle.js` + `lib/vendor/pdf.worker.bundle.js` — two independent `VENDORS` entries in `build/build.mjs`, since pdf.js spawns its own Worker at runtime by URL string, not a static `import` esbuild can inline into one file). **Key finding**: pdf.js's `getDocument()` needs a real `window` (its internal worker-init code touches `window.location`) — it cannot run in the bare service worker (`background.js` has no `window`) or in a plain dedicated Worker (workers have `self`, not `window`). `sidepanel.js` already has a `window` and is already open whenever 📎 can be clicked, and this codebase already has an exact precedent for spinning up a same-origin Worker from an extension page (`lib/sidepanel/katex-worker-client.js`'s `new Worker(chrome.runtime.getURL(...), {type:'module'})`) — so `lib/sidepanel/pdf-extractor.js`'s `extractPdfText()` runs there, needing **zero new permissions** (existing CSP already has `worker-src 'self'`) and **no `chrome.offscreen`**.
  - **Flow** (fail-open at every stage — every failure mode collapses back to exactly the pre-existing placeholder behavior, never a new stuck state): `tryPdfExtraction` (`lib/page-extractor.js`) tries `_fetchPdfBytesInPageWorld` via `chrome.scripting.executeScript({world:'MAIN'})` — **must run in-tab, not from the service worker**, so the fetch carries the page's own cookies (same reasoning as `fetchImageBase64` for XHS images; a service-worker-side fetch of an arbitrary site is cross-origin and would be CORS-blocked for anything login-gated). Success (and under `MAX_PDF_BYTES` = 30MB) → returns `{mode:'pdf-pending', pdfBase64}` **without storing to history yet** (mirrors the existing screenshot-mode early-return in `background.js`'s `ATTACH_PAGE` case exactly). Any failure (fetch error, oversized, thrown exception) → falls through to the pre-existing placeholder-text result, unchanged code path.
  - `sidepanel.js`'s `onAttachPage()` sees `ctx.mode === 'pdf-pending'`, calls `extractPdfContent()` (see below — the wasm-primary/pdf.js-fallback orchestrator, not `extractPdfText()` directly) raced against a 45s timeout; on success sends the new `ATTACH_PDF_CONFIRM` message; on total failure/timeout (corrupt/encrypted/scanned-image-only PDF) falls back to building the SAME placeholder text itself and sending it via the same message — `background.js`'s `ATTACH_PDF_CONFIRM` case (mirrors `ATTACH_SCREENSHOT_CONFIRM`) never needs to know a failure happened, it just stores whatever text it's given via `buildPageContextText`.
  - **`pdf-inspector-wasm` layered on top (later pass)**: `lib/sidepanel/pdf-extractor.js`'s `extractPdfContent()` is now the actual entry point `onAttachPage()` calls — it tries `@firecrawl/pdf-inspector-wasm` (Firecrawl's Rust PDF-to-Markdown engine, compiled to WASM, published on the public npm registry — verified via `npm view`/`npm pack`, not something we wrote) FIRST, falling back to the pdf.js text-join above (`extractPdfText()`, kept completely unchanged as the fallback) only when the wasm path is unavailable or its result fails a usability check. **Why wasm over porting the Rust logic to JS**: researching `/mnt/data/work/pdf-inspector` (a separate, sibling Firecrawl repo from the main scraping API) found that its highest-value features — bordered/ruled-line table detection, image-anchored reading order, geometric underline detection, struct-tree tables — all require PDF vector-graphics/image operators that pdf.js's `getTextContent()` doesn't expose; porting them to JS would mean re-implementing a slice of PDF content-stream parsing. The repo already ships a complete WASM binding (`pdf-inspector/wasm/`) running the *entire* Rust engine (layout/table/heading/reading-order reconstruction) directly on raw PDF bytes via `processPdf(bytes, options) -> {markdown, pdfType, confidence, pagesNeedingOcr, layout, ...}` — every feature for free, zero new PDF-parsing code.
    - **Vendoring**: `pdf_inspector_wasm_bg.wasm` (4.84MB) + `pdf_inspector_wasm.js` (wasm-bindgen `--target web` ESM glue, verified to reference only `globalThis`, never `window`/`document` — safe inside a Worker) are copied as-is into `lib/vendor/` by a new `RAW_COPIES` step in `build/build.mjs`, separate from the `VENDORS`/esbuild loop — esbuild can't bundle a `.wasm` binary, and the glue is already a clean dependency-free ESM file that doesn't need bundling.
    - **CSP**: `manifest.json`'s `script-src` gained `'wasm-unsafe-eval'` (Chrome/Edge 103+, within the 114+ baseline) — required for `WebAssembly.instantiate` under MV3's default-restrictive CSP.
    - **Worker pattern**: `processPdf()` is synchronous/CPU-bound (its own README recommends a Worker for large documents) — `lib/sidepanel/pdf-inspector.worker.js` + `lib/sidepanel/pdf-inspector-worker-client.js` mirror `katex.worker.js`/`katex-worker-client.js`'s exact shape (`type:'module'` Worker, sticky `workerFailed` flag, timeout-resolves-`null` so the caller falls through rather than hanging) — one PDF per call, no batching needed (unlike KaTeX's per-message formula batches).
    - **Quality gate** (`isUsableWasmResult` in `pdf-extractor.js`): a wasm result is only accepted if `pdfType !== 'Scanned'` and `markdown` is non-empty after trimming. **Tuned empirically, not by assumption**: an earlier version also rejected results where `pagesNeedingOcr` covered every page, but a real single-page test fixture with genuinely-extracted, genuinely-correct text (`"Hello World"`) still came back with `pagesNeedingOcr: [1]` — the engine's OCR-need heuristic is a conservative low-confidence signal, not a reliable "extraction actually failed" signal, so the gate deliberately does not key off it. This is the concrete fix for the earlier open question "what if PDF extraction silently returns wrong/lost content" — `pdfType`/`confidence` are signals plain pdf.js text-join has no equivalent of.
    - **Testing**: unlike pdf.js (needs `DOMMatrix`/a real Worker, structural-tests-only), plain `WebAssembly.instantiate` runs directly in Node — `test/lib-pdf-inspector-wasm.test.mjs` does **real execution tests** (`initSync({module: bytes})` against the actual vendored `.wasm`, tiny hand-built PDF fixtures, asserting on real returned `markdown`/`pdfType`) rather than just checking the module's shape. `test/lib-pdf-extractor-content.test.mjs`/`test/lib-pdf-extractor-fallback.test.mjs` are split into **two separate files** (not two `test()` cases in one file) specifically because `pdf-extractor.js`'s internal `import('./pdf-inspector-worker-client.js')` is not cache-busted, so the worker-client's module-level `worker` singleton persists across every test case within one process — only a separate file (node's test runner isolates each file into its own process) gets a truly fresh singleton for the "wasm result is unusable, must fall through" scenario.
  - `_fetchPdfBytesInPageWorld` is a module-level MAIN-world function with two nested helpers (`toRawPdfUrl`/`fetchAsBase64`) — still safe under the `countImages` lesson (no sibling module-scope calls; only browser built-ins `fetch`/`Blob`/`btoa`/`URL`). Two refinements over a plain `fetch(location.href)`: (1) **GitHub `/blob/` rewrite** — `github.com/{owner}/{repo}/blob/{ref}/{path}` serves the GitHub web UI (`text/html`), not the file bytes, so fetching it returns HTML, fails PDF parsing, and falls back to the URL-only placeholder (the exact reason a GitHub-hosted `book.pdf` attached as `[PDF file - agent should fetch and read directly]` wasn't parsed). `toRawPdfUrl` rewrites it to `raw.githubusercontent.com` (serves the bytes, sends `Access-Control-Allow-Origin: *`); that cross-origin fetch MUST use `credentials:'omit'` — raw sends no `Access-Control-Allow-Credentials`, so `'include'` is browser-blocked (and the public raw endpoint needs no auth). Same-site fetches still use `'include'` for login cookies. (2) **HTML viewer detection** — if the response `Content-Type` is `text/html`, return an error instead of base64-encoding HTML for the parser (a real PDF served as `application/pdf`/`application/octet-stream`/`text/plain` still passes; only `text/html` is rejected). The 4 pre-existing vm-sandbox tests mock `fetch` with no `headers` field and no `URL` global, so the content-type read is guarded `(resp.headers && resp.headers.get(...)) || ''` (degrades to "not HTML, proceed") and `toRawPdfUrl`'s `try/catch` silently skips the rewrite when `URL` is absent — the two new tests pass `URL: globalThis.URL` and a `headers.get` mock to exercise both new paths. `MAX_PDF_BYTES` is 30 MiB (raised from 20) to admit ~20 MiB real-world PDFs like the GitHub book that prompted this; the tradeoff — base64 inflates 30 MiB to ~40 MB through `chrome.runtime` messaging, and wasm/pdf.js parsing is slower — is why the wasm worker `TIMEOUT_MS` went 45s->90s and `onAttachPage`'s race timeout 45s->150s (raised again from 120s to give the figure pass - scanning up to 200 pages + rendering up to 30 figures - room after wasm text extraction) (a timed-out wasm call still leaves room for the pdf.js fallback within the outer budget).
  - **PDF figure preservation (vision-capable providers)** — 光学：wasm markdown 与 `getTextContent()` 都是纯文本，栅格图/矢量图会被静默丢掉。`extractPdfContent()` 走 opt-in `opts.extractFigures`（面板 PDF 分支传入）：`extractPdfFigures()` 检测含图页、**裁剪真实图区**（非整页渲染）、配对 caption，产出 `result.figureImages` `[{url, caption, page}]`。裁决（叙事与两个调试故事见 wiki Architecture「PDF figure extraction」）：
    - **检测**：`classifyPageOps`（纯函数）每页一次 `getOperatorList()`（检测期不渲染）计数图像/矢量/文字 op；含图判定 = 有图像 op，或 `vecOps>=40 && textOps<40`（图表签名）；唯一漏网是高文字矢量页——仅对这类歧义页用 `getTextContent()` 查 `Figure N` caption 定夺（不加扫每页成本；无 caption 的高文字矢量页——表格/伪代码框——因此被正确排除，否则会挤掉真图）。
    - **选图按文档序（页升序），不按密度**——早期 signal-desc 设计的真 bug：矢量图（signal 50-200）压过栅格图（3-6），紧预算下栅格图全灭。预算裁谁由预算决定（ predictable 地砍后章）。`FIGURE_MAX_IMAGES=30`（每张每轮 ~1K token 重发）、扫 200 页、每页 ≤2 张；`Array.sort` Chrome 114+ 稳定，同页图保持页内阅读序，选择序=输出序。
    - **CTM 一律后乘**（canvas 约定 `CTM' = CTM × args`，非 PDF 教科书前乘）——前乘把 scale 复合进 translate，bbox 全部飞出页 ~25 倍，每张图退化整页兜底；「重复相同缩略图 / Figure 1.1 没检出 / 图变整页」三个表象同根。`transform = multiplyMatrix(stack[last], args)`。bbox 在 default user space（与 `getTextContent()` 条目同空间——caption 可直接配对，无需视口换算）。`dedupeBoxesByName`（objId）在 merge 和页配额**之前**；末尾再过一道字节级去重（同像素不同 objId）。
    - **caption 配对用点到矩形最近边距离**（非中心距——caption 左对齐页边/图左缘，中心距曾把 book.pdf p15 的 Figure 1.1 误拒），`maxDist`=15% 页高，正则 `^(figure|fig\.?|table|图|表)\s*\d+`。渲染每页一次 1000px；<2% 页面积跳过、≥60% 或裁剪退化（<20px）转整页兜底；JPEG 长边压到 `FIGURE_MAX_LONG_EDGE=1568`（每轮重发，分辨率成本跨会话复利）；每次调用换新字节缓冲（pdf.js 会 detach）。
    - **存储形状与截图确认完全同构**：非空时 `## Figures` 小节按序列 caption 进 `finalText`，`content` 变多模态数组且 `image_url` 块顺序=图节顺序（保 caption↔图配对）；空/缺图保持纯字符串形状。Hermes 路径经 `buildRunsConversationHistory` 转 `input_image`；非视觉模型无视之。**摘要兼容**：`maybeSummarizeAttachment` 重写保留既有 `image_url` 块（`[{text 压缩体}, ...原图块]`）。**2026-10-21 最终裁决：PDF 与博客同构**——PDF 图照常提取、附带，并用 `[图N]` 引用；自动裁剪出错是**检测质量问题，正向修**（提高 bbox/caption 配准），不要靠删掉引用契约绕过。`parseFigureLabels` 额外兼容过渡期的 `## Attached PDF figures` 无编号格式（短暂窗口内产生的历史条目仍能压缩）；`figuresBeforeEntry`/`decorateFigureRefs` 不区分 PDF，与博客走同一套。
    - **已知边界（刻意的中道路线）**：wasm markdown 无页边界（探针实证）、逐页重解析 ~10× 不可扩展——caption 锚定保住 wasm 质量 + 免页边界的图文对应；无编号 caption 退化为页码锚；单栏 y 序。
    - Tests: `test/lib-pdf-extractor-figures.test.mjs`（纯函数矩阵 + `_extractFigures` 注入缝）+ `attach-pdf-confirm`（存储形状/摘要存活）。⚠ `FIGURE_TIMEOUT_MS` 的 90s 定时器必须在 `finally` 清（否则挂死 Node 测试跑者）。
  - **PDF 治理批（2026-10-23 opendataloader 移植，勿回退）**：扫描兜底页图≤12 随附（note 保 `[PDF file` 前缀）；页眉页脚两票去重；run 去重+<1pt 过滤；U+FFFD≥0.3 旗标；wasm 测试一文件一场景；详见 docs/opendataloader-pdf-borrow-study.md。
  - Explicitly out of scope for the first pass: no `attach-change-tracker` wiring for PDF text yet (keyed generically off `ctx.text`/`ctx.mode` and could be added later without re-touching this flow); no OCR support.
- **Office 文档附加（docling.rs-wasm）** — 裁决：`OFFICE_EXTS` **刻意排除**旧版 `.doc/.xls/.ppt`（wasm 构建不支持）与纯文本网页格式（通用管线已能读）。转换在 sidepanel 的 `type:'module'` Worker 里做，wasm URL 由主线程传入（**Worker 全局没有 `chrome.*`**——pdf worker 踩过的真 bug）。**刻意不在面板 init 预热**：编译 13.4MB wasm 要占数十 MB RSS 一整个面板生命周期。vendor glue 是 wasm-bindgen `/web` 产物，**esbuild 绝不能碰**，RAW_COPY。已知 v1 限制：pptx 幻灯片号漏成游离列表项、xlsx 无表名标签、图片只留 `<!-- image -->` 占位。

- **DOM relevance-based item reordering** (`extractDomTreeInPageWorld`'s repeated-group branch, `lib/page-extractor.js`): the existing hard `htmlCap` truncation cuts content strictly by DOM position — if a page has many repeated items (product cards, search results) and the total exceeds the cap, whichever items are later in the DOM are silently dropped regardless of relevance. `query` (whatever's currently typed in the input box, opportunistically read at the moment 📎 is clicked — **browsa's UX is strictly "attach first, type question later"**, confirmed via code trace, so there is no dedicated moment where "the question" and "the attach action" coexist; this reuses whatever's already there rather than changing that UX) is threaded through `sidepanel.js`'s `ATTACH_PAGE` message → `background.js` → `extractActiveTab` → `runGenericExtraction` → `extractDomTreeInPageWorld({htmlCap, query})`. When `query` is empty (the common/intended flow), this is a **provable no-op** — the reorder's stable sort with all-equal (zero) scores keeps the original DOM order byte-identical.
  - **`bm25ScoreItems(texts, queryText)` + `tagPriorityWeight(el)`** (nested inside `extractDomTreeInPageWorld`, never module-level siblings, per the `countImages` lesson) — replaced the original `scoreTextByQuery` character-bigram Dice-coefficient cosine (ported from auditing crawl4ai's `BM25ContentFilter` instead): proper Okapi BM25 (k1=1.5, b=0.75) with term-frequency + document-length normalization + inverse-document-frequency, scored over the CURRENT repeated-group's items as the corpus (N = group size). Uses `tokenizeBigrams` (character bigrams, **not** firecrawl's/crawl4ai's whitespace-tokenized+stemmed words) as BM25's "terms" — deliberately adapted for browsa's primarily-Chinese UI, since CJK text has no whitespace word boundaries and bigrams sidestep the need for a stemmer entirely. `tagPriorityWeight` multiplies the BM25 score by a gentle factor (h1=1.5, h2=1.35, h3=1.2, h4-h6=1.1, none=1.0) when an item's `querySelector('h1,h2,h3,h4,h5,h6')` finds a heading — much gentler than crawl4ai's page-wide h1×5, since repeated-group items are all the same type of thing (e.g. product cards), not a mixed document tree. The `if (query)` gate and `{child, itemNum}` true-DOM-order labeling below are unchanged.
  - **Reordering preserves two invariants tested explicitly**: (1) each item's printed `— Item N —` label always reflects its TRUE DOM-order position, never its position in a reordered output slot (so "what's item 5" always means the same thing to the user, regardless of relevance reordering) — achieved by capturing `{child, itemNum}` pairs before sorting, and only permuting which item's *content* fills each fixed slot; (2) non-group "outlier" siblings interspersed among group items (e.g. a "Load more" button) keep their exact original position — the `el.children` walk loop structure is unchanged, only the group-item content assigned to group slots is reordered.
  - Only `dom`/`auto`-falling-into-dom-tree modes are affected; `reader`/`full` mode truncation (a dumb `.slice(0, htmlCap)`) is unchanged — out of scope, they have no "repeated items" concept to reorder.
- **Link-to-citation numbering** (`postProcessMarkdown`'s final step, `lib/page-extractor.js`, ported from auditing crawl4ai's `convert_links_to_citations`): on link-dense pages, `[text](https://long-url...)` repeating the full URL inline wastes tokens for no benefit to the model. When a page has **≥6 unique `http(s)` link URLs**, every occurrence of `[text](url)` is rewritten to `text⟨N⟩` (Unicode angle brackets — not `<N>`, which a markdown/HTML renderer could interpret as a tag, and not `[N]`, which reads as another markdown link) and a `## References` list mapping number→URL is appended. Below the 6-link threshold the markdown is left untouched — the marker+footer overhead isn't worth it for a couple of citation links. A negative lookbehind (`(?<!!)`) excludes image syntax `![alt](url)`. Confirmed safe from a UI-rendering standpoint: `PAGE_CONTEXT_PREFIX`-tagged attach text is explicitly skipped by `sidepanel.js`'s `renderHistory` before it ever reaches the markdown renderer — this transform only affects what the model (and `sessions-ui.js`'s plain-text export placeholder) sees, never chat-UI-rendered HTML.
- **虚拟列表的滚动与恢复（preExtractCleanup Step 3 扩展）** — 裁决：windowed feed 会替换屏外 DOM，滚动时记录 `{key → html}` 并在滚动结束后恢复被替换的项；**这确实在改用户活页面的 DOM，属刻意接受的低风险变体**（与 `preExtractCleanup` 本就无条件执行的同类变更同级）。仅在检测到 feed 候选时才做。
  → 完整机制/事故叙事：wiki **Architecture-zh「虚拟列表滚动与恢复」**
- **Pre-extraction page cleanup** (`preExtractCleanup` in `lib/page-extractor.js`，概念审自 firecrawl 的页内 actions 系统——其实现全在远端 Playwright 服务，从零重写)：主抽取前注入的 async MAIN-world 函数，**3.5 秒硬预算**四步。(1) 关 cookie 横幅——**容器门控 + 危险词否决**双门（只点 `NOISE_SELECTORS` cookie 容器内的元素；购买/删除/确认/支付类文案一律跳过——两门合起来才防误点破坏性按钮）。(2) 展开「阅读全文」——点 `[aria-expanded="false"]`/`[class*="read-more"]`，排除 chrome 区（与 `detectIncompleteness`/`interactiveSnapshot` 同一套 nav/header/footer 排除），`MAX_EXPAND=8` + 两连空转（零增量）即止；**`safeClick` 拒绝一切可导航的 `<a href>`（非 `#`/`javascript:`）**——两步共用的唯一卡点（hfviewer 事故：品牌链 `<a id="brand" aria-expanded="false" href="/">` 站在 chrome 区外、无危险词，被点后整 tab 跳走附加失败）。**labuladong 事故加固了全部三门**（78 个候选里唯一带字的 chrome 区外按钮是侧栏「清除阅读历史」，弹出的确认框被 Readability 当正文打分）：`inChrome` 对齐 `isChromeNoise`（补 `aside`/`[role=complementary|search]`）；`DANGER_WORDS` 增破坏性动词（中文整词 + 英文带词边界）；每次展开点击后 `dismissOpenDialogs()`（优先显式取消按钮→编程关闭+合成 Escape），**弹过框即停**本轮、`return` 前再扫一次，`expandedCount` 回滚。零增量兜底抓不到弹框（React 预渲染 dialog 文本，textContent 不变）。已知边界留档：内层滚动容器懒渲染的正文抓不全（飞书快路径同类问题；内层滚动器扫描是 future work，不静默重试）。(3) 滚底等懒加载（最多 `MAX_ROUNDS=3`）——**信号门控**（2026-09-14 用户报告「看页面自己动很瘆人」）：仅在检出懒加载/虚拟化信号时才滚，静态文章一像素不动；需要滚时文档短暂 `opacity:0` 抑制绘制——**必须用 opacity 不用 visibility**（visibility 可继承，会改全页每个元素的计算样式：labuladong 上旧抑制法把文章子树卡在 `visibility:hidden`，用户页面白屏 + 抽取器的 hidden-mark 也瞎了），`finally` 恢复 + 8 秒 page-world setTimeout 保险，`scrollY` 必还原。(4) 虚拟化信息流还原见专条。**无条件运行、无设置项**（`autoCleanBeforeExtract` 开关曾短暂存在，用户明令删掉硬编码默认）；只在 `runGenericExtraction` 内跑（站点快路径/PDF/截图/选区在 `extractActiveTab` 提前返回，不经此处）。⚠ `loadSiblingFn` 的函数提取正则必须容 `async function` 声明（漏了会让带 await 的注入体在测试期 SyntaxError）。叙事与两个事故全貌：wiki Architecture「Pre-extraction cleanup incidents」。
- **Full-mode dump hygiene** (`extractFullInPageWorld`, 2026-09-16): the last-resort `body.textContent` dump now strips `script`/`style`/`noscript`/`template` from a detached body clone before reading. It deliberately still reads `textContent` rather than `innerText` — 小红书-style CSS-hidden prose must survive — but dead markup text must not: labuladong.online inlines its Next.js RSC flight payload as a ~50KB `<script>` at the top of `<body>`, so the degraded attach returned 124K chars that were half serialized flight JSON. The live DOM is never touched; any clone failure falls back to the unstripped dump.
- **A frame destroyed mid-read is not an attach failure (2026-09-16)**: `runGenericExtraction`'s injection wrapper now catches chrome.scripting's frame-gone rejection. The same user report that exposed the anchor misclick above ALSO exposed this second, independent hole: the raw browser string reached the UI as 「⚠ Failed to read page DOM: Frame with ID 0 was removed.」 for a tab that was perfectly fine, and the whole attach died. Two branches, because the two situations need opposite responses: **same URL** ⇒ the page reloaded itself in place, so wait 300ms (the new document must commit before it can be injected into, else the retry throws again) and inject once more — live-verified against real Chrome that an executeScript 300ms after the frame died succeeds; **URL moved** ⇒ the page the user asked to read is gone, so throw a typed `page-navigated` error rather than silently attaching whatever replaced it. The typed error's message stays English (logs/other consumers) and `background.js`'s ATTACH_PAGE catch forwards `e.code`; `lib/sidepanel/attach-orchestrator.js`'s `ATTACH_ERROR_KEYS` maps that code to `[locale key, English source]` because the panel is where the UI language is known (`pageNavigatedDuringRead` added to both `_locales`). Tests: `test/lib-page-extract-frame-gone.test.mjs` (retry-on-same-URL; typed code + no retry when the URL moved).
- **GitHub `/blob/` 原始文件快速路径** — 裁决：`/blob/` 是 JS 视图页不是文件内容，`tryGithubExtraction` 把 URL 重写到 `raw.githubusercontent.com` 直取原文（**必须 `credentials:'omit'`**——raw 不发 `Allow-Credentials`，`include` 会被浏览器拦）。`www.github.com` 与带斜杠的 ref 都要认；非 github/非 blob 一律返回 null 且**不发 fetch**。任何失败（404/图片/pdf/空字节/网络/空内容）都 fail-open 回通用管线。PDF 不到这里——`tryPdfExtraction` 先跑且自带 raw 重写。
  → 完整机制/事故叙事：wiki **Architecture-zh「GitHub /blob/ 原始文件快速路径」**

### Deep extraction (auto-expand & paginate, `lib/agentic-extract.js`, quiet-attach rework 2026-09-14)

After the generic extraction cascade, `detectIncompleteness()` (MAIN-world probe) reports `deepExtractSignals` on the result — a `rel=next`/pagination-container URL (`nextPageHref`), a same-DOM load-more control (`loadMore`), or collapsed expanders that survived `preExtractCleanup` (`expandersLeft`; all with chrome-region exclusions). `background.js`'s `ATTACH_PAGE` case feeds these to `maybeDeepExtract()` for reader/dom/full/auto modes when `deepExtractEnabled !== false` (options toggle, default on). Two escalation mechanisms under one budget (`TOTAL_BUDGET_MS = 75s`, hard caps `MAX_STEPS = 8` brain clicks / `MAX_PAGES = 4` pages, abortable through the chat-stream plumbing), every failure path returns null so the baseline result is never lost (deep extraction is an enhancement, never a dependency):

- **URL pagination — deterministic background walker** (`walkNextPages`): opens `nextPageHref` in a `chrome.tabs.create({active:false})` tab per page (`waitTabComplete` → `preExtractCleanup` → `extractFullInPageWorld` → that page's own next link), up to `MAX_PAGES - 1`; each walker tab is closed on every exit path. Pages are appended under `[Page N]` markers by `assembleDeepText`, skipping a page whose opening ~300 normalized chars repeat already-known content.
- **Interactive expansion — LLM-in-the-loop on a BACKGROUND COPY**: `driveInTabInteractions` used to snapshot+click the USER's tab; a user report ("attach 时看着页面自己点击，体验奇怪") moved it to a fresh `chrome.tabs.create({active:false})` copy of `ctx.meta.url` — same URL, same cookies, user's tab never touched. The copy is opened only when `loadMore || expandersLeft > 0` (URL-only signals go straight to the walker), then `waitTabComplete` → 800ms SPA-settle → `preExtractCleanup`. `interactiveSnapshot` numbers ≤150 non-navigating controls (anchors with a real href are excluded outright — the brain can never even point at anything that navigates; chrome regions excluded), the active provider answers ONE one-shot completion with a single JSON action (`parseAction` fails closed to `done` on any malformed reply), `clickIndexed` re-finds the control by `data-browsa-ix`, applies the danger-word veto, clicks, and settle-polls a body-text sentinel (100ms × 2s; crawl4ai's content-freshness check). The copy's re-extraction (same extractor kind as the baseline via `extractorFor(redoMode)`) is adopted only when it beats the baseline by `MIN_GAIN_CHARS = 200` — a degraded hidden-tab copy can never make the result worse. The copy is closed on every exit path; the brain shares the chat-stream keepalive/abort registration (`chatControllers` + `STREAM_KEEPALIVE_ALARM`, only when no chat stream owns the tab). Brain dispatch is apiStyle-aware (`chatStream`/`responsesStream`/`anthropicStream`/`runsApiStream` for agent providers), `temperature: 0`, 300 tokens — a plain one-shot, no agent/tool protocol.

Progress texts ride `pushDeepProgress` to the side panel (`deepExtractStart`/`deepExtractStep`/`deepExtractPage` locales). Tests: `test/agentic-extract.test.mjs` (pure helpers + orchestrator against mocked chrome/fetch — asserts every `executeScript` targets the background copy, never the user's tab; copy open/close on success AND failure; fail-open paths), `test/lib-deep-extract-pagefuncs.test.mjs` (the MAIN-world probes), and the Step-2/Step-3 quiet-attach contracts (no-scroll-on-static, visibility suppression window, chrome-exclusion) in `test/lib-pre-extract-cleanup.test.mjs`.

### Page inline images (reader/auto/jina 配图 [图N] 内联, `lib/page-images.js`, 2026-08-29)

Reader-mode Markdown already carries article images **in position** — Turndown emits `![alt](url)` (with page-extractor's srcset→best-src upgrade), and even Jina output does. `inlinePageImages` (called in `ATTACH_PAGE` for `['reader','auto','jina']`, after `withSiteInstructions`) downloads those images in the service worker, compresses each to a ≤768px JPEG dataURL (`createImageBitmap` + `OffscreenCanvas` — both available in MV3 SW; white-fill first or transparent PNGs turn black under JPEG), and rewrites each kept image **in place** to a `[图N] alt` anchor line. The entry then stores `interleaveImageParts(contextText, figures)` — the exact same [图N] protocol as video keyframes (`ATTACH_ASR_CONFIRM`), so output-side `decorateFigureRefs` renders model citations of page figures with zero extra wiring.

- **Cap/filter**: max 8 figures (resend-every-turn token ceiling), 16 candidates scanned; per-image ≥200×120 (icons/avatars/dividers drop by decoded size), 8s fetch timeout, 8MB download cap, non-`image/*` content types rejected. Same URL anchors only its first occurrence; numbering follows document order with no gaps — `figures[N-1]` must correspond to `[图N]`.
- **Fail-open everywhere**: any download/decode failure keeps that image's `![alt](url)` verbatim (the model still sees the URL); no decode environment (non-SW) or zero successes returns the text unchanged and the entry stays a plain-string content — the pre-existing shape. SVG fails decode in Chrome and self-filters.
- **Scope**: `dom`/`full` modes are tree-format text (no Markdown image syntax) and `selected` is a partial excerpt — all excluded. XHS keeps its own `imageBase64List` vision path. Lazy-loaded below-fold images whose `src` is a tiny placeholder drop via the size filter (acceptable V1 loss).
- **Interplay**: history image compaction labels these `[image N]` (same numbering as the [图N] anchors, non-PDF branch); auto-summarize preserves the `image_url` blocks like every other multimodal entry. Tests: `test/lib-page-images.test.mjs` (pure, stubbed decoder) + `test/attach-page-images.test.mjs` (wiring via the jina branch — no DOM mocking needed).

### Paper reading pipeline (page markers, outline, arXiv metadata, reading-aid card, 2026-08-31)

Research-paper PDFs get a dedicated quality pass across four layers, all best-effort/fail-open — a miss at any layer leaves the pre-existing attach behavior untouched.

- **`[Page N]` markers in both extraction paths** (`lib/sidepanel/pdf-extractor.js`): the wasm engine is called with `includePageMarkers: true` and its `<!-- Page N -->` comments are normalized to visible `[Page N]` lines (`normalizePageMarkers`, pure + tested — dedupes a page boundary the engine emits twice); the pdf.js fallback stamps the same marker per page. Page-boundary-less text was the root cause of two model-facing gaps: no page-precise citations and only weak "Figure on page N" figure anchoring. The markers also give the auto-summarizer something to preserve (see paper-mode prompts below).
- **Layout-aware fallback text** (`reconstructPageText`, pure + tested): the old `items.map(str).join(' ')` emitted content-stream order, which scrambles every two-column paper into interleaved column fragments. It now clusters runs into lines by baseline y (tolerance 0.3× font size), splits a line into column bands on gaps > 12% of page width, and emits each band top-to-bottom (left band first). Single-column pages are unchanged in spirit; whitespace-only runs drop.
- **Bookmarks → `## Contents`** (`flattenOutline`/`formatOutlineMarkdown` + `extractPdfOutline`, tested): `doc.getOutline()` was never read. Outline items' `dest` (array `[pageRef, /XYZ,…]` or named string) resolves to 1-indexed pages matching the `[Page N]` markers; unresolvable dests keep the title with `page: null`. Prepended to the body only when ≥ 3 entries exist (a lone "Cover" node is not a TOC). Concurrency: wasm text, outline, and figures are three INDEPENDENT passes (each opens its own pdf.js doc / worker call from a fresh byte copy) and run CONCURRENTLY via `raceWithTimeout` (outline 15s, figures 90s, timer always cleared — a lingering setTimeout stalls Node's test runner); wall-clock = slowest single pass, not the sum (an earlier version serialized outline after wasm and figures after that, visibly slowing every attach — timings logged as `browsa[pdf]: extract done in Nms` + `attach pipeline (extract+arxiv) took Nms`).
- **arXiv metadata header** (`lib/arxiv.js`, tested): `arxivIdFromUrl` handles `/abs/`, `/pdf/` (± `.pdf`, ± `vN`), `/html/`, old-style `cs/0301012` IDs across `arxiv.org`/`export.arxiv.org`. `fetchArxivMeta` calls the Atom API (`export.arxiv.org/api/query?id_list=…`, 6s timeout) and parses via DOMParser with a regex fallback (DOMParser is absent in Node tests and the regex path must match the DOM result). `formatArxivMeta` renders the header block; the sidepanel fires it **in parallel with extraction**, and `ATTACH_PDF_CONFIRM` prepends it to the context header (never into the body text). Non-arXiv/network failure → `null` → no block. The attach system message shows `，arXiv:<id>` as visible confirmation (the 检查 dialog displays the FULL `contextText` returned by `ATTACH_PDF_CONFIRM` — header + body + Figures — not the pre-header pdfText the sidepanel holds).
- **Paper reading-aid card — REMOVED (2026-08-31, user decision)**: an earlier iteration ran a one-shot structured analysis (concept chips / TLDR / digest) via `chatStream` against the active provider after paper-shaped attaches. Dropped for two compounding reasons: the user's active provider is Hermes, whose `runsApiStream` wire protocol the card did not speak (it silently skipped on non-chat providers — invisible failure), and the value add over the already-attached full text was marginal against the protocol-branching cost. Lesson recorded: **any sidepanel feature that makes its own LLM call must either support all four API styles (chat / runs / responses / anthropic) or fail VISIBLY, not silently.** The protocol-agnostic layers above (markers, outline, arXiv header, paper-mode summarizer prompts) remain.
- **Paper-mode auto-summarize prompts** (`attach-summarizer.js`): `summarizeLongText` now accepts the full `ctx` (bare mode strings still work — video behavior byte-identical); when `ctx.meta.paper`, the chunk prompt preserves section headings + `[Page N]` markers + concrete numbers and drops citation lists, and the merge prompt organizes by the paper's own headings. The stored `pdfCtx.meta.paper` flag rides the same `maybeSummarizeAttachment` path as before.
- **Testing**: pure functions live in `lib/arxiv.js` and pdf-extractor's exported helpers — covered by `test/lib-arxiv.test.mjs` (10 cases) and `test/lib-pdf-structure.test.mjs` (7 cases). The DOM/streaming paths follow the established "manual browser sanity check" convention.

### Video note timestamps (`[mm:ss]` in-place seek + auto-rewrite)

Video notes (youtube/bilibili page context attached via 📎, then "总结…") get clickable `[mm:ss]` timestamps that seek the video page's `<video>` in place, plus an automatic rewrite so the notes actually contain them.

- **`videoSrc` is the single source of truth.** `ATTACH_PAGE` (`background.js`) stamps `historyEntry.videoSrc = { platform: ctx.mode, url: ctx.meta?.url || '', tabId }` on the page-context user turn when `ctx.mode === 'youtube' || 'bilibili'`. `handleChat` (`lib/handlers/chat-handler.js`) scans history newest-first for the most recent entry with `videoSrc`; that drives both the prompt hint and the stamp on the stored assistant turn + DONE chunk. `onSend` does NOT auto-attach page context - the user must click 📎 first, or no `videoSrc` is present and none of this fires.
- **`videoNoteHint`** (the `VIDEO_NOTE_HINT` constant in `background.js`, baked into the youtube/bilibili page-context text at attach time via `withVideoNote` — see ATTACH_PAGE/ATTACH_ASR_CONFIRM) asks the model to organize notes into sections and append each section's start time at the end of its heading as `[mm:ss]` (or `[h:mm:ss]` over an hour), keeping the exact bracket form so it can be linked. It was once appended to `effectiveSystemPrompt` only when `videoSrc` was set — a conditional dynamic prefix that split the KV/prompt cache key between "video session" and "normal session". It now rides in the trajectory (stored attach text) like llms.txt, so `effectiveSystemPrompt` stays byte-stable: it is `[systemPrompt, langExtra, capabilityHints, choiceRequestHint]` and nothing else.
- **`linkifyTimestamps(el)`** (`lib/sidepanel/render.js`, exported) wraps bracketed timestamps - `[mm:ss]`, `[h:mm:ss]`, and BiliNote's `*Content-[mm:ss]` prefix (stripped in display) - in `<span class="browsa-ts" data-s="<seconds>" role="button" tabindex="0">`. It deliberately matches ONLY bracketed forms (regex `/(?:\*Content-)?\[(?:(\d+):)?(\d{1,2}):(\d{2})\]/g`), not bare `mm:ss`, to avoid false positives on version numbers/ratios. It uses a `TreeWalker` over text nodes and skips `SCRIPT`/`STYLE`/`<a>` parents; the wrapper is a `<span>`, not an `<a>`, so `decorateLinks`'s `target=_blank` doesn't fire on it. Runs inside `makeStreamRenderer`'s `isDone` path (after `decorateLinks`) and in `renderHistory`.
- **`dataset.videoSrc`** is stamped on the assistant bubble so a click knows which tab/URL to seek: the live path gets it from the DONE chunk's `videoSrc` field; `renderHistory` gets it from the stored `m.videoSrc`. `onTimestampClick(ts)` reads `ts.dataset.s` + `JSON.parse(ts.closest('.msg')?.dataset.videoSrc)`, sends `SEEK_VIDEO` (tabId + seconds), and on `!res.ok` falls back to `chrome.tabs.create({ url: appendTimeParam(vs.url, seconds) })` (`?t=`/`&t=`) so a closed video tab still jumps to the moment.
- **`SEEK_VIDEO`** (`background.js`) uses `chrome.scripting.executeScript({ world: 'MAIN' })` because YouTube's `#movie_player.seekTo(s, true)` is a page-attached custom method unreachable from the ISOLATED-world DOM wrapper (same reason active-fetch uses `world:'MAIN'`). B站 has no equivalent API, so it sets `video.currentTime = s` and dispatches `seeking`/`timeupdate` so the custom progress bar / danmaku sync. Wrapped in try/catch returning `{ok:false}` on any error (tab closed, no `<video>`).
- **Auto timestamp rewrite** (`handleChat`, after the stream loop, inside the main `try` before CHOICE_REQUEST extraction): if the model's first reply (v1) lacks `[mm:ss]`, the background silently asks it ONCE to reformat with them. The gate is conservative because `videoNoteHint` fires on *any* video-page reply - so the rewrite requires ALL of: `videoSrc` set, `!/\[(?:\d+:)?\d{1,2}:\d{2}\]/.test(fullReply)` (same shape `linkifyTimestamps` matches), the user's message matches a notes/summary keyword regex (`总结|笔记|纪要|要点|大纲|概要|梳理|summary|summarize|notes?|outline|takeaways?|key points`), and `fullReply.length > 50`. A specific question like "这个视频作者是谁？" is therefore NOT reformatted. The rewrite reuses `doStream({ silent: true })` - `doStream` takes an `opts` arg whose `silent` variant accumulates deltas into `streamState` and keeps the idle timer alive but does NOT push `CHUNK` to the UI. The rewritten v2 is delivered as the DONE chunk's `full`, which the side panel's DONE handler re-renders the whole bubble from (`renderStream(finalText, true)` does `el.innerHTML = await renderSafe(delta)`) - so v2 seamlessly replaces v1 with no bubble-wipe machinery. A `TS_STATUS` chunk shows a transient `⏱ 正在补充时间戳…` indicator above the bubble via `showToolProgress` (NOT pushed to `toolEvents`, so DONE's `renderToolHistory` won't render it; cleared by DONE's existing `clearToolProgress`). On abort (user Esc) or any error during the rewrite, v1 is kept and still stored + DONE'd - the user never loses the notes they saw stream in (`pushChunk`'s `safePost` makes the DONE a no-op if `cancelStream` already disconnected the port; v1 is still persisted to history). Only ONE rewrite attempt - no recursion if v2 also lacks timestamps. The CHOICE_REQUEST extraction + `appendToHistory` + `DONE` run AFTER the rewrite on the final `fullReply` (v2 or v1); the literal `await storage.appendToHistory({ role: 'assistant', content: fullReply, ...(videoSrc ? { videoSrc } : {}) });` line is preserved so static-analysis tests still match.

### ego-lite audit borrowings (citrolabs/ego-lite, 2026-09-09)

ego-lite is a Chromium fork where humans and agents co-use one browser (closed-source app; its repo ships only the open `ego-browser` CDP harness + agent skill). Different product class — Task Spaces ownership, kernel-level snapshot, CDP transport are NOT portable to a no-backend MV3 extension, and its visible signature features (Spaces, "experience accumulation") fall under the standing youtube-digest rule (techniques yes, signature features no). What was borrowed, techniques only:

- **Agent-executable setup prompt** (from its `references/install.md` pattern — instructions written for an agent to follow, not a human): the Agent Bridge card in `options.js` has a 「复制配置提示词」 button (`bridgeAgentSetupPrompt`, `_locales` en+zh) that copies a complete prompt the user pastes into their CLI agent, which then performs install → agents.json → serve → health-check itself and reports back only the bridge URL. Same block lives in `docs/guide/providers.html` (zh+en) and both READMEs link it. The prompt deliberately defers adapter-entry specifics to the bridge package's own `agents.example.json`/README so it can't drift. Ego's hard-stop discipline carried over too: the prompt ends with "if a step fails, stop and show the exact error — do not retry in a loop".
- **Per-site knowledge file**: `lib/content-scripts/SITES.md` — triage flow for "a site stops populating its cache", cross-site invariants (each paid for with a real bug: never touch signed URL params, GraphQL hash rotation, MAIN-world constraints, `var`-not-`const` for re-injected scripts), and one fixed-schema entry per site (hosts / intercept points / push message → cache field / product / fragilities / tests), shaped after ego's learnings packs. Update a site's entry in the same commit as any change to its script.

Audited and deliberately NOT adopted: ego's `scrollToBottomUntil(condition)` predicate scroll for extraction — `preExtractCleanup` already terminates on `newHeight <= lastHeight` (page stopped growing), which is the right predicate for "extract everything", and the deep-extract pass had already rejected adding content-condition termination as decoration. `CAPABILITY_HINTS` already satisfy its SKILL.md documentation discipline (anti-patterns named explicitly, every caveat carries its reason), so no churn there either. Direction-level finding: ego validates "agent acts on pages" (click/fill/type/upload are its core helpers) — but after a 2026-09-09/10 scenario review the user shelved the write/act direction entirely: the copy-paste baseline (write in the side panel, paste by hand) already covers single-blob writing, the surviving scenarios (multi-field forms / batch entry / page-feedback loops) are episodic or niche, and the call was 「做好太复杂了 — 就基于当前 browsa 的功能做好」. Do not re-propose generic page-write features; a future restart needs a concrete, real-usage form/batch flow copy-paste genuinely can't handle. (Its lightweight implementation blueprint — external-agent-as-brain via a structured chat-tail protocol, reusing the deep-extract safety skeleton and approval cards — is archived in the project roadmap notes for that day.)

- **检测以 `noTranscript` 结构旗标为准**（synthesizeBilibili/YouTube 都打），不是文本 marker——auto 的 Jina 回退会替换短合成文本、丢 marker（真 bug）。Tests: `attach-asr`。
- **`buildAsrPendingCtx` 平台分派**：B 站重注入 content-script 读 `__browsaGetBilibiliStreams()`；YouTube 走 `__browsaFetchFreshYouTubeStreams`（ANDROID /player 新鲜 pot URL，闭包变量禁止——注入函数必须从 `window.location` 自解析 videoId，2026-08-25 真 bug）。选流：最低码率音频 + **时长 <90% 拒收**（截断流真 bug）+ AAC-LC 优先于 HE-AAC。无音频流 → null → 普通附加。Tests: `attach-asr-closure`、`youtube-streams`。
- **转码是根因修复不是优化**：B 站 m4s 是 fMP4，方舟按内容判成视频→`failed`；必须转 16kHz 单声道 PCM WAV（`resampleToMono` 纯函数可测）。`audioUploadFormat:'original'`（2026-10-07「上传太慢」）只跳编码+上传、**不跳解码**——核对时长就是解码本身。Tests: `lib-attach-asr`。

- **方舟文件缓存**：`browsaArkFileCache` 键 `baseUrl|key指纹|assetId`（`|provider:model` 作用域化——oss:// 文件绑上传时的 model 且 48h 死）；缓存按文件合并写（复用 id 不刷新过期）。Tests: `lib-attach-asr`。
- **千问适配器（2026-10-06/07）**：长音频唯一路 = getPolicy → OSS multipart（字段序固定、`file` 最后）→ `oss://` + `X-DashScope-OssResourceResolve`；音频/视频 part 只进 user message；omni 转写路径发 `reasoning_effort:'none'`（只发 `/^qwen3\.[85]-omni/`）。**默认值两次翻转的遗留守卫**：`attach-asr-pending.js` 在 ASR_DEFAULTS 合并前按残迹推断 provider，`asrAdapterFor(未知)` 回退 ark——回退≠默认，ark 时代用户不被悄悄指向 dashscope。filetrans 族走异步任务 API（`X-DashScope-Async`→轮询），映射 `[mm:ss] [说话人N] text` 是确定性的。Tests: `lib-asr-qwen`、`lib-attach-asr`。
