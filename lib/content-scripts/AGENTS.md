# lib/content-scripts/AGENTS.md — MAIN world 站点脚本与站点快路径

> 作用域：`lib/content-scripts/*`（站点拦截器 + 划词条 + site-relay + SITES.md）及 `lib/site-fallbacks.js`、`lib/site-synthesizers.js` 的站点规则面。
> 根级全局约束见仓库根 `AGENTS.md`；每站运维知识见 `SITES.md`（同目录）。

### Content scripts

Site-specific interceptors (`lib/content-scripts/*-content-script.js`) run in **MAIN world** at `document_start` and wrap `window.fetch` / `XMLHttpRequest` to capture SPA API responses. They send messages to the background, which stores results in `SITE_CACHES` (a registry object in `lib/handlers/site-cache-store.js`（2026-09-23 C7 自 background.js 外迁） — one `Map` per site, keyed by `tabId`). Adding a new site only requires a single entry in `SITE_CACHES`; restore, lookup, and cleanup iterate it automatically. XHS is the one exception — it uses a separate `xhsXhrCache` Map with its own push logic instead of a `SITE_CACHES` entry. `lib/content-scripts/selection-toolbar.js` runs in ISOLATED world at `document_idle` on all `https://` pages.

跨站 helper 收编在 `site-common.js`（relayToHost/htmlToArticleText/图片抓取），经 window 全局或 Node require 桥接；xhs `func:` 副本除外，由 site-twin-lockstep 钉住。

MAIN-world content scripts can't use ES module imports, so URL matchers there must resolve relative paths against the page: use `new URL(url, location.origin)`, not `new URL(url)` — a bare relative fetch/XHR path (e.g. `fetch('/api/...')`) throws and gets silently swallowed otherwise.

Extension resources used inside Shadow DOM or injected pages (e.g. `icons/icon16.png`) must be declared in `web_accessible_resources`. `ShadowRoot` supports both `querySelector('#id')` and `getElementById('id')` in current Chrome — prefer `querySelector` for consistency with the rest of the codebase.

### YouTube content script critical lessons (confirmed 2026-07-25)

- **`chrome.runtime` is undefined in MAIN world** — `installYouTubeInterceptor()` must NOT guard on `chrome.runtime`; use only `typeof window !== 'undefined'`.
- **YouTube loads the current video's captions via XHR, not fetch** — `XMLHttpRequest.prototype.send` must be wrapped to intercept `/api/timedtext`. The fetch wrapper only catches recommended/sidebar video pre-fetches (whose responses are often HTML error pages or empty).
- **timedtext URLs require a PO token (`exp=xpe`) — but only the WEB-client ones** — re-fetching the watch page's own caption URL (`ytInitialPlayerResponse`, and therefore the `performance` resource-buffer entries) returns 200 + empty body. Verified 2026-09-10 that this is client-specific, not universal: the caption `baseUrl` returned by the **ANDROID** `/youtubei/v1/player` POST carries no `exp=xpe` (it does carry `fmt=srv3`) and returns the full body to a bare `fetch` with no UA, no cookies and no token (11,536 bytes of srv3). That is the URL `activeYouTubeFetch` Stage 3 already uses, so the transcript path does not actually depend on the XHR interception's PO token — the interception is a page-load-time head start, not the only route. (The interception is still what feeds `__browsaTranscriptCache` passively, and remains worth keeping.)
- **Do not modify `fmt=` in the baseUrl** — even though `fmt` is not in `sparams`, re-fetching with a modified URL still fails. Parse the original response body directly (supports both json3 and srv3/ttml XML).
- **字幕文本带标记，必须在离开解析器前归一化**（2026-09-10 用户报告「原生视频字幕带 `<b>`」）— 裁决：timedtext 的文本**逐字带标记**，解析后统一剥标签 + 实体解码；越界或孤立代理项的数字实体**丢弃而不是抛错**（一个坏实体不得让整条字幕变 null）。重写是旧时间戳处理的超集（`<p>` 与 `<text>` 都经同一个 `parseSubtitleStart` 接受 `t`/`tStartMs`/`start`/`begin`），**绝不比之前少提取一行**。
  → 完整机制/事故叙事：wiki **ASR-and-Video-Analysis-zh「字幕文本的标记归一化」**
- **`/player` uses ANDROID client, `/next` uses WEB client** — ANDROID `/next` returns `singleColumnWatchNextResults` with `elementRenderer` blobs (unparseable). Fire both in parallel via `Promise.allSettled`.
- **YouTube SITE_CACHES is always skipped** — the passive interceptor runs in MAIN world without `chrome.runtime`, so `SITE_CACHES` never gets YouTube data. `page-extractor.js` always falls through to `activeYouTubeFetch`.

### X/Twitter tweet extraction — active fallback (`tryXActiveFallback`)

X/Twitter content scripts had the **same passive-interceptor failure as YouTube**: `twitter-content-script.js` is declared in the manifest with `world: MAIN`, and its `installTwitterInterceptor()` guards on `chrome.runtime` — which is **undefined in MAIN world** — so it never installs and `SITE_CACHES.twitter` is never populated. A tweet page therefore fell through to the generic DOM-tree dump (`extractDomTreeInPageWorld`), which for X's div-based layout includes the whole nav/trending/sidebar chrome (Grok/Chat buttons, "Skip to home timeline", "What's happening") — the user-facing bug this fixes.

- **Fix**: `tryXActiveFallback(tab, meta)` in `lib/page-extractor.js` (wired into `extractActiveTab` right after the bilibili fallback, matching the `tryYoutubeActiveFallback`/`tryBilibiliActiveFallback` pattern) injects `twitter-content-script.js` on-demand via `chrome.scripting.executeScript({ world: 'MAIN', files: [...] })`, then calls the new MAIN-world `activeXFetch()`. It reads the tweet + visible replies out of `window.__INITIAL_STATE__.entities.tweets/users` (X embeds the conversation in SSR state, same idea as Bilibili/XHS), falling back to the rendered DOM's stable `[data-testid="tweet"]` / `[data-testid="tweetText"]` / `[data-testid="User-Name"]` attributes when the state object is absent/stale. `synthesizeTwitterResult` now also emits a `## 回复` numbered conversation from the `replies` array (backwards-compatible: old XHR shape with only `data.replies` count still works).
- **llms.txt side-fix** (`fetchLlmsTxt` in `lib/handlers/chat-handler.js`): x.com serves its SPA index.html with HTTP 200 + `Content-Type: text/html` for `/llms.txt`, which used to be treated as "site instructions" and injected hundreds of KB of raw HTML into the page context. The fetch now rejects any `text/html` Content-Type, and (when no Content-Type header is present) rejects a body that starts with `<`.
- **Gotcha**: in `auto` mode, the silent Jina fallback (< 200 chars) can override a *short* tweet's active-fallback result — acceptable: Jina's fetch of a tweet URL returns reasonable tweet markdown, and long tweets keep the structured X path. The `tryXActiveFallback` URL gate matches `twitter.com`/`x.com` `/status/` paths only (not home/search).

### X/Twitter syndication fallback (推文 URL 免登录兜底, 2026-10-16 用户报告)

**裁决：推文 URL（`x.com|twitter.com/…/status/<id>`）的提取不得落到 r.jina.ai**——jina 是匿名服务端抓取，X 的推文页只给登录墙（Log in/Sign up 噪声 + 全部图片丢失）。取而代之的两级权威数据：① 页内 `activeXFetch`（登录页的 `__INITIAL_STATE__`/DOM，含可见回复与图片字节）；② **`cdn.syndication.twimg.com/tweet-result` 兜底**（`fetchTweetViaSyndication`，X 自家 embed 数据源：免登录免 Cookie 免 DOM，全文/作者/计数/mediaDetails 原图 URL；token 是 react-tweet 同款公开公式 `(id/1e15)*π` 六进制去零，非鉴权；`display_text_range` 截掉 text 尾部模型打不开的 t.co 短链；照片 SW 侧下载压缩随 `imageBase64List` 入库，端点不含可见回复——回复以页内路径优先）。接线两处：`tryXActiveFallback` 的 null 兜底（auto/reader/dom/full 级联由此受益）+ background 显式 jina 模式的推文 URL 抢占（拿不到才退回 jina，不困死用户）。**auto 的 jina 回退判据已正解化为 `autoJinaFallbackWarranted`（page-extractor 纯函数，2026-10-16 用户问「怎样算提取失败」）**：绝对下限（<200 字符，原有救援全保留）+ 相对亏空（`body.innerText` 量 >2000 且提取量不足两成 → 失败——付费墙/重 JS 页的救援反而变多，旧判据下 400 字符的半失败不触发；innerText 而非 textContent——后者把脚本字面量算进去，任何提取都像亏空）；`ctx.siteSynthesized`（makeSynthResult 单点标记）永不回退——短推文/短帖天然短，长度不是提取失败的证据（同日用户抓到的残余 bug：级联测试用的 dom 模式恰好没打中 auto 这条门）。探针不可用（tab 关/注入抛）→ 相对层失效、绝对层照旧。行为地板（变异验证×5：删兜底/删抢占/改坏 token 公式/拆 siteSynthesized 门/拆相对亏空层各红其位）：`attach-site-images.test.mjs` 的「X syndication 兜底」节（token 字面量钉死 + 短推文 auto 不回退）+ `site-synthesizers.test.mjs` 的 `twitterFromSyndication` 映射用例（display_text_range 截链、photos `?name=large`、video-only 提示行、垃圾载荷 null）。

### Reddit post+comments extraction — active fallback (`tryRedditActiveFallback`)

Reddit has **no passive content-script interceptor** — it's a componentized SPA with no simple XHR endpoint to hook (unlike Twitter's GraphQL call), so pages used to fall through to the generic DOM-tree dump, which for Reddit's div/web-component layout pulled in the whole chrome: skip links (跳到主要内容/跳至导航/跳至右侧边栏), vote/share/reward buttons, ads (`alb.reddit.com` links), footer links, stray `— Item N —` repeated-group markers, and the raw `SML.load([...])` module-loader strings Reddit's comments leak into their `<summary>` text.

- **Fix**: `tryRedditActiveFallback(tab, meta)` in `lib/page-extractor.js` (wired into `extractActiveTab` right after the X/Twitter fallback) injects `lib/content-scripts/reddit-content-script.js` on-demand via `chrome.scripting.executeScript({ world: 'MAIN', files: [...] })`, then calls the new MAIN-world `activeRedditFetch()`. It reads the post + comments out of `window.__INITIAL_STATE__` (Reddit embeds SSR state — probes `posts.posts`, `profiles.profiles`, `users.users` paths defensively since the shape is route-dependent and has changed over time), falling back to the DOM: `shreddit-post`/`shreddit-comment` web components (author/score/depth live in attributes), then a generic `<h1>`-based post + `<details>/<summary>` comment structure (the exact shape the old DOM dump showed). `stripSmlNoise` removes the `SML.load([...])` leak before synthesis. `synthesizeRedditResult` emits `# title`, a `r/sub · u/author · score · comments` meta line, the body, and a depth-indented `## 评论` tree.
- **No manifest entry needed**: the script is purely an active-fallback library (no auto-install at document_start), and `chrome.scripting.executeScript({ files: [...] })` can inject any packaged path. `.json` API routes are NOT used — Reddit blocks bare server-side fetches (403) and a SW fetch wouldn't carry the user's login cookies anyway; the in-page DOM/SSR path does.
- **Fail-open**: if neither INITIAL_STATE nor the DOM yields a recognizable post, it returns null and falls through to the generic cascade — never a regression from current behavior.

### Selection toolbar inline explain/translate (划词内联解释/翻译, 2026-09-06)

The float bar's 「解释」 and 「翻译」 no longer route through `SELECTION_ACTION` into the side panel — both stream their answer into an **inline popover anchored next to the selection** (product form validated against 沉浸式翻译's on-demand selection/hover translation, PickZ, and Saladict: the answer appears in place, reading flow unbroken; the side panel stays reserved for conversational actions — Ask/Summarize keep the old relay, per the inline-vs-panel rule: 看完就走 → 浮条；要说话/要留存/要工具 → 侧栏). Design constraints baked into the implementation:

- **Streaming leg is a one-shot port** (`browsa-explain`), not `sendMessage`: the content script connects, sends `{type:'EXPLAIN_REQUEST', text, lang}` as the first message, gets `EXPLAIN_CHUNK`/`EXPLAIN_DONE`/`EXPLAIN_ERROR` back. No HELLO handshake needed (unlike browsa-chat/subchat) — `connect()` itself wakes the SW and `onConnect` necessarily registers listeners before any port message arrives, so the reconnect race those handshakes guard against can't exist here. Closing the popover = `port.disconnect()` → background's `AbortController.abort()` kills the upstream fetch (the ONLY dismissal path that cancels the request; scroll/resize merely re-anchor).
- **`lib/handlers/selection-explain.js`** owns the session: `buildExplainRequest(text, lang, mode)` (pure, tested) + `handleExplainPort(port, deps)` (deps-injectable `getAll`/`streams` for tests — no chrome mock needed). Fixed `EXPLAIN_MAX_TOKENS = 700` — deliberately NOT `provider.maxTokens` (that's the chat-output budget, irrelevant to a 150-char dictionary entry) and NOT `DEFAULT_MAX_TOKENS`; anthropicStream needs a mandatory value, this always provides one. apiStyle dispatch mirrors `mermaid-repair.js` (chat/responses/anthropic — Hermes providers also work since the server natively serves `/v1/chat/completions`). Answer language follows the settings `uiLang` override, else browser language, threaded from the content script as `lang`; in `mode: 'translate'` the TARGET language flips zh↔en when the selection is already (mostly) in the UI language (`isMostlyCjk`, CJK-vs-latin counting) — a zh user selecting Chinese gets English and vice versa. Port protocol keeps the `EXPLAIN_*` message names for both modes (renaming to `INLINE_*` is pure churn); the request carries `mode`.
- **Two closed shadow hosts** in selection-toolbar.js (`#browsa-sel-host` for the bar + `#browsa-sel-pop-host` for the popover): independent fixed positioning, same palette incl. the `prefers-color-scheme: light` variant. Popover anchors to the SELECTION (opposite side from the bar, so the highlighted text stays visible; the bar's `.below` flip flips the popover too), re-anchors on scroll/resize via the stored `Range.getBoundingClientRect()` — a long explanation must survive scrolling, unlike the bar which hides.
- **Model output never touches `innerHTML`**: `renderExplainBody` is a deliberately tiny renderer (bold/code inline tokens, `-`/`•`/`1.` bullets, line breaks) that builds nodes with `createTextNode`/`textContent` only — XSS-safe by construction; unparseable markup degrades to literal text. The system prompt simultaneously forbids tables/headings/images so the renderer's poverty isn't visible.
- The bar's document-level guards (`mouseup`/`mousedown` composedPath checks, right-click collapse, Esc, scroll, ✕-suppress) all learned `popHost` — selecting text INSIDE the popover must not reposition the bar, and right-click inside it must not kill the explanation mid-copy. `GET_PENDING_ACTION`/context-menu flows are untouched; the popover's 「在侧栏细聊」 deliberately sends the OLD `SELECTION_ACTION {action:'chat'}` (attach + focus composer, no auto-send).
- Tests: `test/selection-explain.test.mjs` (prompt building, apiStyle dispatch, error envelopes, single-session guard, disconnect→abort).
