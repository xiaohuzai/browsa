## 模块清单与各模块裁决

### `sidepanel.js` module split (`lib/sidepanel/`)

Thirty-two modules (2026-10-24 count — `ls lib/sidepanel/*.js` is authoritative at 35 files: 32 modules + three `*.worker.js` scripts; `media-headers.js` is consumed by BOTH the SW (`background.js` referer/sweep rules) and the panel (`attach-orchestrator.js`)), imported by `sidepanel.js` directly or through each other — none of them import `sidepanel.js` back (avoids ES module cycles; modules that need `sidepanel.js`-owned mutable state get it via an `initX(deps)` call from `init()` instead). The newest is `detail-thread-store.js` (追问卡跨侧栏关闭的持久化, see the detail-thread section); the biggest recent extraction is `attach-orchestrator.js`: it holds the 📎 attach pipelines (`onAttachPage` / `runVideoAnalysisPipeline` / `runAudioTranscribePipeline` / `downloadAndTranscodeAudioBest` / `showAsrModeCard`, ~840 lines moved out of `sidepanel.js`), with `sidepanel.js` injecting its mutable state (`currentTabId`, `ctxRadios`, `nextHistoryIdx` via a `bumpHistoryIdx` callback) and the progress/append helpers through `initAttachOrchestrator(deps)`. **onAttachPage is a thin mode-dispatcher (2026-09-20 refactor pass, was 340 lines)**: the four deferred-storage branch bodies live in same-file functions `attachScreenshotMode(ctx, title)` / `attachPdfPending(ctx)` / `attachOfficePending(ctx)` / `attachAsrPending(ctx)` — all deps are the module-level `deps` + imports, so they move with zero closure threading; onAttachPage dispatches on `ctx.mode` inside its try (a branch throw, e.g. the ASR expired-playurl abort, still lands in the shared catch/finally that restores the attach button). The rest are described below:

- `render.js` — the Markdown/Mermaid/ECharts/Markmap/KaTeX pipeline: `renderStreamingSafe`/`renderSafe` (marked + DOMPurify), `makeStreamRenderer`, `addCodeCopyButtons`/`highlightDiffBlocks`, `renderMermaid`/`renderEcharts`/`renderMarkmap`. 裁决与不变量（机制与事故叙事见 wiki Rendering-Pipeline「Contracts & incident notes」）：
  - **围栏渲染器无按钮**（ADR-0010）：`CAPABILITY_HINTS` 教模型吐 ` ```markmap ` 等围栏，render.js 探测语言换活渲染——勿加 UI 按钮。
  - **Vega-Lite 不引入**（2026-10-23 用户拍板，勿再提议）：评估过「模型吐 ` ```vega-lite ` 围栏→活渲染」后放弃——数据图表槽位只留 echarts（两个渲染器会让模型二选一，输出不确定、体验割裂）；流行度一边倒（npm 周下载 echarts 363万 vs vega-lite 73万，stars 6.7万 vs 5.5千，2026-10 实测）；vega-lite 独有项（内建统计变换/分面小倍数/selection 跨图联动）在对话场景几乎不被要求；另有 MV3 CSP 硬坑（vega 表达式默认 `new Function`，需换 vega-interpreter）。重评条件：出现 echarts 覆盖不了的具体诉求（分面小倍数/联动仪表盘）。

## 面板交互面

### `onSend()` vs `resumeInFlightStream()` — formerly two independent DONE handlers, now shared via `wireChatStreamPort()`

`sidepanel.js` used to have **two separate, hand-maintained copies** of the "stream finished" handling logic: one inside `onSend()`'s `port.onMessage` listener (the common path — user sends a message, this side panel opened the port), and one inside `resumeInFlightStream()`'s own `port.onMessage` listener (the side panel reconnects to a stream that's *already running* — triggered by `STREAM_PEEK` reporting `inFlight:true` on panel init, e.g. after an SW sleep/restart, a tab switch, or the panel being briefly closed and reopened mid-reply). Being independently written meant every feature added to one's `DONE` branch had to be manually mirrored into the other's, or it silently only worked on the "lucky" path where the panel never disconnects mid-stream.

**Found via a real user bug report** (video-note `[mm:ss]` timestamps not seeking): the user's reply took long enough to generate that the SW went idle mid-stream, so the reply completed via `resumeInFlightStream()`'s DONE handler — which was missing the `dataset.videoSrc` stamp entirely (present in `onSend()`'s). Auditing the rest of that handler for the same class of drift found two more gaps (interactive `CHOICE_REQUEST` buttons, the "已达上限" max-turns `→ 继续` button) and a fourth (`ERROR`/`ABORTED` did a raw `el.textContent = ...` instead of the safe-render pipeline, leaving literal markdown and a stuck blinking cursor).

**This class of drift is now structurally impossible for the shared parts**: `wireChatStreamPort({ port, tabId, getEl, getRenderer, state, stopKeepAlive, onRetry, afterDone, onAborted })` holds the ONE implementation of CHUNK/TOOL_PROGRESS/TS_STATUS/APPROVAL/CLARIFY/DONE/ERROR handling, called by both `onSend()` and `resumeInFlightStream()`. Only the genuinely different bits stay as caller-supplied hooks: `onRetry` (onSend wipes the bubble and rebuilds the renderer; resume just shows a toast), `afterDone`/`onAborted` (resume also calls `setStreamingUI(false)`/disconnects the port, onSend's own `port.onDisconnect` already covers that). The STREAM_HELLO/ACK handshake is similarly shared via `waitForStreamHelloAck(port, tabId, { onAck })`.

**If you add a new field to the DONE chunk or a new post-DONE side effect, it now only needs to go in `wireChatStreamPort()` once** — both callers pick it up automatically. The one thing that can still drift is the caller-specific hooks (`onRetry`/`afterDone`/`onAborted`/`getEl`/`getRenderer`) — if a new feature genuinely needs different behavior on resume vs a fresh send, that's exactly where it belongs, and `test/lib-sidepanel-resume-streaming.test.mjs` still exists to catch anything that should have been shared but wasn't.

**Related, independently-discovered bug while adding those regression tests**: `.msg.assistant:last-of-type` (used in `getOrCreateAssistantBubble()`, `ensureAssistantEl()`, and the resume port's `onDisconnect` handler to re-find "the current assistant bubble" after a possible DOM-identity change) is a fragile selector — `:last-of-type` requires the element to be the last **DIV** among its siblings by tag name, not just the last `.msg.assistant` found. Once a sibling `<div>` is inserted right after the bubble — `renderChoiceRequest`'s `.choice-request` wrap, or `appendMsgAction`'s action row, both real and both reachable from this exact resumed-DONE handler — the assistant bubble silently stops matching `:last-of-type` for any *later* lookup in the same resumed session, causing the next turn's re-discovery to spawn a stray empty bubble instead of finding the real one. Fixed by replacing all three call sites with `[...messagesEl.querySelectorAll('.msg.assistant')].pop()` — takes the last element of the already-filtered set, immune to intervening sibling tags of the same name. If you're tempted to use `:last-of-type`/`:first-of-type` anywhere near message bubbles, use this pattern instead — those pseudo-classes only work as "the last of this literal thing" when you can guarantee no same-tag-name sibling ever gets inserted nearby, which the message list can't promise.

### Composer image gate (paste / drop / picker, 2026-09-15)

The per-turn image limits (`lib/image-budget.js`: ≤8 images, ≤3 MB of URL chars ≈ 2.25 MB of actual image bytes, sized for the bridge's 4 MB JSON body) were applied ONLY at send time by `handleChat`, which drops the overflow and appends a model-facing note to `msg.userText`. A send-time drop is invisible to the user: the composer clears the thumbnail strip the moment a turn starts (sidepanel.js's `onSend`), so an image refused there leaves no trace anywhere in the UI — it reads as "pasting an image does nothing", and it was reported as exactly that. `imageRejectReason(current, url)` (pure, exported) now mirrors `pickTurnImages`' rules exactly — same order, same comparisons — so `handleDroppedFiles` can refuse at ATTACH time, with a visible `appendError` (`imageBudgetExceeded` / `imageCountExceeded`, both locales), and the thumbnails the user sees are exactly the images that ship. The two functions must never drift: `test/lib-image-budget.test.mjs` feeds one mixed list through both (sequential gate vs batch pick) and asserts identical survivors, and `test/lib-sidepanel-image-gate.test.mjs` drives a real paste through sidepanel.js in jsdom (accept → thumbnail; over-budget and 9th → no thumbnail + visible notice). The 20 MB per-file pre-check stays — it refuses before the bytes are read into a data URL. `appendError(text, {compact:true})` is what keeps these local refusals as the one-line ⚠ notice: without it a message over 80 chars falls into the provider-failure card ("Something went wrong" + "Raw error" + Copy) — which the longer English wording tripped, since the compact/chip branch was keyed on length alone. Deliberately NOT done: auto-downscaling an over-budget image to fit (canvas re-encode). A pasted screenshot is usually pasted *because* its detail matters, and silently shipping a recompressed version is the same class of surprise as the silent drop; the limit is now stated instead. The detail-thread (SUBCHAT) card has no image support at all — text only.

### Screenshot attach undo

`appendAttachSystem(text, relatedEl)` takes an optional second argument — the DOM element the attach-system message's "撤销" (undo) button should remove on a successful `UNDO_ATTACH`, in addition to fading its own label text. For the screenshot mode specifically, `onAttachPage`'s confirm callback calls `appendScreenshot(dataUrl)` (which now returns the `.screenshot-preview` element it created) *before* `appendAttachSystem`, so the preview element can be passed in as `relatedEl` — otherwise undoing a screenshot attachment left the image visibly stuck in the chat even though the label correctly showed "（已撤销）". The plain (non-screenshot) page-attach call site doesn't pass a second argument — `relatedEl?.remove()` degrades to a no-op there, matching its prior behavior.

### Attach-in-progress visual feedback

`onAttachPage` previously gave almost no visible feedback while an extraction was in flight — just `attachBtn.disabled`/`opacity:0.5` and a `title` hover tooltip (invisible unless the user hovers and waits out the native tooltip delay), which matters because worst-case latency is real: `preExtractCleanup` alone budgets 3.5s, and PDF extraction is raced against a 45s timeout. `chrome.runtime.sendMessage` (used for `ATTACH_PAGE`) is strictly one request/one response — true backend stage-by-stage progress (like the `browsa-chat` streaming port) would require restructuring `ATTACH_PAGE` into a port, which was explicitly out of scope for this pass. Two genuine, non-fake stages are shown: "正在读取页面…" for the whole `ATTACH_PAGE` round trip, and "解析 PDF 中…" once the `pdf-pending` branch is entered and the separate local `extractPdfContent` call starts (a client-side transition `onAttachPage` already knows precisely, not a guess). Both the button state and the progress pill are restored/removed in the existing `finally` block, covering success, error, and thrown-exception paths uniformly.

### Message fold (collapse long replies, sidepanel.css + sidepanel.js)

Every `.done` assistant bubble gets a `.msg-actions` bar (absolutely positioned top-right, hover-revealed) whose fold button toggles `.collapsed` — purely visual and ephemeral (never persisted; `renderHistory` rebuilds fresh). The collapsed state is `max-height: 150px + overflow-y: hidden` with a bottom fade gradient (`.collapsed::after`). **The expand affordance lives INSIDE the window**: the action bar is pinned at `top: 4px`, so the fold button stays within the visible 150px — never move the bar to the bubble bottom, or a collapsed bubble loses its only expand control. **And it must be VISIBLE when collapsed, not hover-gated** (2026-09-23 user report): the bar's `.msg:hover` reveal turns a folded bubble into a dead end whenever something below it (an inline 追问 card) jumps up under the pointer on collapse — `:hover` stops matching the bubble and the icon "never comes out". `.msg.assistant.collapsed .msg-actions .fold-btn` is therefore exempted from the hover gate (persistently visible); the rest of the bar keeps the hover-only rule (unread-text occlusion).

**Flexbox squash incident (2026-09-14, user report: collapsed messages became ~4px slivers, impossible to re-open)**: `.messages` is a fixed-height flex column (`overflow-y: auto`), and flex items default to `flex-shrink: 1`. Ordinary bubbles are protected by the `min-height: auto` content floor — but a flex item whose `overflow` is NOT visible **loses that floor**, so the collapsed bubble (overflow-y:hidden) became the only shrinkable item and absorbed the container's ENTIRE shrink deficit once the history exceeded the viewport: rendered as its 8px padding, invisible, and its hover-only action bar clipped away. Fix: `flex-shrink: 0` on the base `.msg` rule (items in a scrollable list are content-sized, always). Lesson: in a fixed-height flex column, ANY item that ever gets non-visible overflow needs an explicit `flex-shrink: 0`. jsdom has no flex layout, so the contract is pinned structurally in `test/lib-message-fold-css.test.mjs` (base rule carries flex-shrink:0; collapsed = max-height + overflow-Y only; action bar top-pinned).

### Detail-thread ("SUBCHAT") side conversations

Selecting text inside an assistant reply opens an inline card scoped to that excerpt (`lib/sidepanel/detail-thread.js`: `openDetailThread`, `findBlockAnchor`; `lib/handlers/subchat-handler.js`: `handleSubchat`/`handleSubchatAbort`, dispatched from `background.js`'s `SUBCHAT`/`SUBCHAT_ABORT` cases).
